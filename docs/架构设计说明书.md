## 0. 关键前置结论（先看这 4 条）

**① 存储层收敛到一个 PostgreSQL 实例：正文、元数据、向量、词法倒排同库。**

配置面只有一个 `DATABASE_URL`，不再有"第二个库的地址和凭据"：

```bash
DATABASE_URL=postgresql+asyncpg://postgres:<PASSWORD>@127.0.0.1:5432/novel_rag
VECTOR_BACKEND=pgvector          # pgvector | numpy（离线兜底）
PGVECTOR_TABLE=chunk_vectors
PGVECTOR_INDEX=hnsw              # hnsw | ivfflat | none
```

这不是"小规模凑合用"，而是解决了 Milvus 时代最贵的那个问题：**跨库无事务、无外键**。当时的故障长这样——书删了、向量还在、worker 还能给一本不存在的书继续算两小时。现在 `chunk_vectors.chunk_id` 与 `chunk_lexical.chunk_id` 都指向 `chunks(id)` 且 `ON DELETE CASCADE`，孤儿数据在数据库层面就不可表达。

**② pgvector 的两个坑必须提前处理，否则检索会"看起来能用但结果不对"。**

- **带过滤的 HNSW 召回不足**：`ORDER BY embedding <=> :q WHERE novel_id = ? LIMIT 50`，HNSW 先在图里取 `ef_search` 个候选再过滤，若本书只占全库一小部分，候选会被别书吃光，返回不足 50 条甚至 0 条。解法是 pgvector 0.8 的 `SET LOCAL hnsw.iterative_scan = relaxed_order`（本项目在每次检索事务内显式设置）。
- **中文两字词检索失效**：PG 默认分词器不切中文，`to_tsvector('simple','陆沉把刀')` 往往整段算一个 token，`tsquery '铜灯'` 命中不了。项目沿用 **bigram 预切分**：正文切成 `陆沉 沉把 把刀` 再建 `tsvector`，查询同样切分后 `|` 连接。启动时执行 `_probe_cjk()` 自检——若 `to_tsvector('simple','陆沉 沉把 把刀')` 的 lexeme 数 < 3，词法通道主动关闭、检索降级 `dense_only` 并在 `/health` 标红，**宁可少一条通道，也不返回错的排序**。

**③ 大模型换成 360 网关的 `z-ai/glm-5`，协议是 OpenAI Chat Completions，不是任何厂商私有协议。**
这一条决定了整个 LLM 层的写法，三个推论：

- **代码里不出现任何厂商专有 SDK**。统一用 `openai` 官方 SDK + `base_url` 覆盖，`LLMClient` 是唯一出口。将来换回 DeepSeek（`https://api.deepseek.com`）或换任何兼容网关，只改 `.env` 三个变量，零代码改动——这同时满足了原需求"集成 DeepSeek"的可持续性
- **不能假设上游有 prompt 前缀缓存**。DeepSeek 的自动上下文缓存能让固定前缀只收 1/10 价格，第三方网关不一定提供。所以成本控制从"依赖缓存"改为"自己控上下文预算 + 启动时探测一次缓存能力"（见 §9.3）
- **能力必须探测，不能按文档假设**。`z-ai/glm-5` 的实际上下文窗口、是否支持 `response_format={"type":"json_object"}`、是否支持 `stream`、并发上限，全部以网关实测为准。启动时跑一次 `capabilities_probe()`，把结果写入缓存并暴露在 `/health/deps`；JSON 模式不可用则降级为"提示词约束 + 正则修复 JSON"

> 一个必须提前知道的坑：第三方网关的**模型名是带前缀的**（`z-ai/glm-5`），而 OpenAI 兼容层常见的 `model` 校验错误（400 model not found）多是漏了前缀或用了官方名。配置里禁止硬编码模型名，一律读 `LLM_MODEL`。

**④ 切片过程必须"可看见"。**
长文本切块是最容易出问题、也最难解释的一步（字数对不上、章节切错、块被截断）。所以切片阶段不是"后台黑盒"，而是产出一份**完成度档案**：按章进度、块数、token 分布、超长/过短块告警、抽样预览。前端在任务运行时就能看到，跑完还能复核。设计见 §8.3.2。

## 1. 设计目标与约束

### 1.1 业务目标

把一部（或多部）几十万到数百万字的小说，变成三个东西：

1. **可语义检索的向量库**——读者问"主角第一次见到师父是哪一章"，能召回正确段落
2. **可结构化推理的知识图谱**——能回答"谁和谁是什么关系""这个势力有哪些人"，并能可视化
3. **可对话的问答入口**——基于上面两者 + 大模型（`z-ai/glm-5`）生成带引用的答案

### 1.2 非功能性指标（验收基线）

| 维度 | 指标 | 说明 |
|---|---|---|
| 单部小说处理时延 | 100 万字 ≤ **30 min**（P90） | 实测 P0 无图谱：112.7 万字 10.6 min |
| 向量写入吞吐 | ≥ **500 chunks/s**（库侧） | 依赖库的批量 `executemany` upsert；**端到端受本地 Embedding 约束**（CPU 8 线程实测 2.3-2.9 chunk/s），见 §9.1 |
| 检索延迟 | P95 ≤ **300 ms** | 混合检索 + rerank，不含 LLM |
| 问答首字延迟 | P95 ≤ **2 s** | SSE 首 token |
| 问答完整响应 | P95 ≤ **15 s** | 答案 500 字左右 |
| 检索准确率 | Recall@10 ≥ **0.85** | 自建 100 条标注评测集 |
| 图谱抽取准确率 | 实体 P ≥ **0.85**，关系 P ≥ **0.75** | 抽样人工核验 200 条 |
| 并发能力 | 20 QPS 问答（不排队） | 单机 4C8G + 外部 LLM |
| 数据隔离 | 多小说互不串味 | 所有查询强制带 `novel_id` |
| 幂等性 | 管道可重跑不产生重复数据 | 唯一键 + Upsert |

### 1.3 硬约束

- 向量库为**本机/自建 PostgreSQL 18 + pgvector ≥ 0.8**，每个业务库需执行一次 `CREATE EXTENSION vector`；扩展文件缺失时应用启动即报错并给出安装指引（不静默降级）。0.8 以下没有 `hnsw.iterative_scan`，过滤检索会召回不足，不兼容
- 图谱必须**建模实体/关系/属性**（关系带方向、强度、原文证据），不能只把三元组塞进向量库；
  存储上不引 Neo4j —— 三张 PG 表 + 递归 CTE 就够，理由见 §6.3
- 原始文件初期落本地文件夹，**但存储层必须可切对象存储**（接口先行）
- 大模型走第三方 OpenAI 兼容网关（360 / `z-ai/glm-5`），存在限流与并发上限，**且不能假设有 prompt 缓存** → 必须自己做上下文预算、批量、降级
- Python 依赖统一 `uv` 管理（`uv.lock` 锁定），前端统一 `pnpm` 管理（`pnpm-lock.yaml` 锁定），**禁止混用 pip/npm**
- Embedding 必须本地可跑（无 GPU 也要能出结果），不能把向量化绑在外部 API 的可用性上
- 切片阶段必须产出可查看的完成度（按章进度、块统计、异常块告警）

| 向量索引 | **HNSW**（`vector_cosine_ops`） | pgvector 0.8 | `m=16, ef_construction=64`；配 `iterative_scan=relaxed_order` 解决"带 novel_id 过滤后召回不足" | IVFFlat（需预聚类、空表建了没用）、numpy 暴力扫（仅离线兜底） |
| 词法检索 | **`tsvector` + GIN + 自建 bigram 分词** | PG 18 | 不引 jieba / zhparser，避开"索引切词与查询切词两套词典漂移"；中文两字词靠 bigram 精确命中 | FTS5 trigram（已证伪：对两字词直接返回空）、zhparser（Windows 需额外编译） |
| 图存储 | **PostgreSQL 三表** | 18 | 已有实例：`entities` / `relations` / `entity_mentions` + 递归 CTE；删书靠外键 CASCADE，不多一个进程（§6.3） | Neo4j（要先装 JVM + 服务端约 330MB，且跨库一致性得应用层补偿） |
| Embedding | **`BAAI/bge-large-zh-v1.5`**（1024 维，int8 ONNX 量化） | — | CPU 8 线程可跑、中文强、1024 维、量化权重 326MB（fp32 1.3GB）；无稀疏输出，稀疏侧由 PG 倒排承担 | BGE-M3（fp32 需 GPU 才顺手）、OpenAI text-embedding-3（中文长文本弱、出境） |
| Embedding 部署 | **本地进程内 ONNX Runtime**（uv 安装，CPU 可跑）；有 GPU 时可选 TEI 独立服务 | — | 不依赖外部 API，**无 GPU 也能跑通全流程**；进程内调用省一次网络往返；模型走 ModelScope 镜像下载并本地缓存 | 纯云端 Embedding API（出网、按量计费、不可控） |
| Rerank | **`BAAI/bge-reranker-base`**（int8 ONNX，单 logit + sigmoid） | — | 中文 cross-encoder，CPU 可跑；模型未就绪时自动退回 RRF 排序，不阻断问答 | Cohere Rerank（付费、出境） |
| LLM | **360 开放平台** `z-ai/glm-5`（OpenAI 兼容） | — | 指定网关；一个 `openai` SDK 覆盖全部调用；换厂商只改 `base_url` + `model` | 直连 DeepSeek（同协议，改 `base_url` 即切换，保留为备份通道） |
| 图谱抽取 | LLM + 规则/词典 + 别名对齐 三件套 | — | 纯 LLM 幻觉高、纯规则召回低；三层互补 | 纯 LLM（实体漂移严重） |
| 可观测 | structlog + Prometheus + Grafana | — | 结构化日志 + 指标看板 | ELK（重） |
| 部署 | Docker Compose（一期）→ K8s（二期） | — | 首次交付快，后续可平移 | 直接 K8s（一期过重） |

### 2.2 为什么是"模块化单体 + 独立 Worker"，而不是一上来就微服务

一期（≤10 万级 chunk、单租户）用微服务会带来 5 个额外运维面，收益为零。设计取**模块化单体**：

- `api`：FastAPI 单进程，内部按 `services/` 分包，包间只通过接口调用，不互相 import 实现
- `worker-ingest`：**同进程内的 asyncio 后台任务**，跑解析/切分/向量化；队列状态落 `jobs` 表，重启后由 `recover_stale()` 把 PENDING 任务重新 `submit()`，中断的任务不会变成僵尸
- `worker-graph`：现阶段与 ingest 同进程（图谱抽取是 IO 密集的 LLM 调用，靠 `asyncio` 并发即可）；真正需要隔离时再拆独立进程
- `web`：静态站（Vite 构建产物）

拆服务的**触发条件**写死在下文 §10.2：检索 P95 > 500ms 或需独立扩缩时，才把 `retrieval` 拆成独立服务——因为届时它已经有清晰的接口边界（§7.3），拆的成本接近零。

### 2.3 Embedding 的落地方式（关键决策）

```
小说 chunk ──► bge-large-zh-v1.5（int8 ONNX，一次前向）──► chunk_vectors.embedding  vector(1024)
      │
      └─ 同一批文本 ──► bigram 切分("陆沉把刀"→"陆沉 沉把 把刀") ──► to_tsvector('simple', …) ──► chunk_lexical.tsv + GIN
```

- **稠密与词法走两条独立路径**：稠密靠模型，词法靠数据库倒排。缺点是多一次文本切分（微秒级），好处是**词法通道不依赖 Embedding 模型**——模型换了、降级成 hash 伪向量了，词法召回依然正确。
- **模型分档，按硬件自动选**（本地部署的关键）：

| 场景 | 模型 | 维度 | CPU 吞吐（实测） | 说明 |
|---|---|---|---|---|
| **无 GPU（当前默认）** | `BAAI/bge-large-zh-v1.5` + int8 ONNX | **1024** | CPU **8 线程实测 2.3-2.9 chunk/s**（311 字块均 374 token） | 326MB 量化权重（fp32 为 1.3GB）；ModelScope 仓库 `Xenova/bge-large-zh-v1.5` 的 `onnx/model_quantized.onnx` |
| 低配机器 | `BAAI/bge-small-zh-v1.5` | 512 | CPU 4 线程实测 6.7 chunk/s | 112.7 万字全流程 638.8s；内存紧（可用 <2GB）时回退到这一档。**换档必须重建 `chunk_vectors`**（维度不可原地改） |

> 各档位共用同一个 `LocalEmbeddingProvider`，只改 `EMBEDDING_MODEL` / `EMBEDDING_MS_REPO` / `EMBEDDING_ONNX_FILE` / `EMBEDDING_DIM`，代码零改动。启动时 `ensure_ready()` 会读 `pg_attribute` 校验 `embedding` 列的实际维度，不一致直接抛错并给出 `ALTER TABLE … TYPE vector(N)` 的修复指引，**不允许带病运行**。
>
> **v1.2 提升到 1024 维的实测代价**：bge-large 是 bge-small 的 13 倍参数量，即便 int8 量化后 CPU 吞吐也从 6.7 降到 2.3-2.9 chunk/s。同一本 112 万字的书，入库时间从 10.6 min 涨到约 18-20 min（估算，按 1100 字/秒）。这是"维度翻倍"的真实成本，不是配置没生效。

- 归一化后使用 `vector_cosine_ops`（HNSW 用余弦距离），检索时 `embedding <=> :q` 即 1-cos 距离
- 批大小：CPU 16；`onnxruntime` 的 `intra_op_num_threads` 钉死到配置值（`EMBEDDING_THREADS`），`inter_op` 固定 1
- **按长度分桶**：一次把 128 条交给编码器会 pad 到批内最长，短块白算；实测直接整批比按 16 条分桶慢约 15%。`_encode()` 内部先按字符数排序再切桶
- **批大小不是越大越好**：实测 bge-large int8 在可用内存 3.4GB 的机器上，16 条 2.33 块/s、32 条 1.71 块/s、64 条直接崩到 0.2 块/s（激活内存撑爆开始 swap）。内存是这一档的硬约束
- **首启下载**：模型从 ModelScope 拉到 `backend/data/models/`（`EMBEDDING_MS_REPO` 指定仓库），离线环境可预置目录；下载进度推到前端
- **降级路径**：模型加载失败时，自动切 `hash` 伪向量（仅用于跑通链路与单测），响应标 `embedding_mode=hash`，管理台显式红色告警——**不允许静默降级**

> **为什么不用 BGE-M3 的稀疏权重**：M3 的 fp32 权重 2.2GB，CPU 上跑稠密+稀疏两路，吞吐会掉到 1 chunk/s 以下；而它换来的稀疏质量，被 PG 侧的 bigram 倒排 + `ts_rank_cd` 覆盖了大部分收益。这笔账在"无 GPU 是常态"的前提下不划算，所以选 bge-large + 数据库倒排的组合。

### 2.4 大模型用途分工（只有一个模型时的现实做法）

网关同时提供推理模型 `z-ai/glm-5` 与非推理模型 `deepseek-chat-v3`，所以按"**任务需不需要思考**"分工，而不是按"快慢"分工：

| 场景 | 模型 | 温度 | `max_tokens` | 并发 | 说明 |
|---|---|---|---|---|---|
| 章节摘要 | `LLM_MODEL_FAST` | 0.3 | 400 | 4 | 150-200 字，批量跑 |
| 实体/关系抽取 | **`LLM_MODEL_FAST`** | **0** | 4500 | 5（`GRAPH_CONCURRENCY`） | JSON 严格输出，**按 parent 块调用**（不是一章一次）；输出易被截断，故留足预算 |
| 实体对齐仲裁 | `LLM_MODEL_FAST` | 0 | 200 | 4 | 只输入"疑似同一人"的候选对，极短 |
| Query 改写/指代消解 | `LLM_MODEL_FAST` | 0 | 150 | 8 | 50 字内输出，最频繁 |
| 最终答案生成 | `LLM_MODEL`（glm-5） | 0.6 | 1000+ | 8 | 流式，需要推理与长文组织 |

**为什么抽取必须用非推理模型**（v1.7 实测教训）：glm-5 的正文走 `reasoning_content`，`content` 为空；`thinking:{"type":"disabled"}` 实测 6 次全不生效。首版用它做抽取，27 次调用全部返回空 JSON。抽取任务本质是"按 schema 抄写",不需要长思考，用推理模型既贵又容易把 `max_tokens` 全花在思考上。代码里 `extract_chunk()` 直接取 `llm.fast_model`，返回空时打告警指向 `LLM_MODEL_FAST` 这个配置项。

**限流与失败处理**（第三方网关的配额通常不透明，必须假设它随时会 429）：

```
请求 → 信号量(LLM_MAX_CONCURRENCY=4) → 429/5xx?
        → 指数退避 1s/3s/9s + 抖动，最多 3 次
        → 仍失败：抽取降级为规则抽取（标记 low_confidence）
                  问答降级为"返回检索原文摘要 + 提示稍后重试"
```

**成本控制（v1.1 的关键变化）**：不能依赖上游 prompt 缓存，改为三条自己做的手段：
1. **上下文预算硬约束**：检索上下文 ≤ 8K token、图谱事实 ≤ 40 条、历史 ≤ 6 轮原文（更早的压成滚动摘要，见 §8.9.1）
2. **抽取批次合并**：短章节（< 1500 字）两章合并一次请求，减少请求数与重复的 schema 开销
3. **计量留痕（v1.12 落地，v1.14 补齐问答侧）**：`LLMClient` 按 `usage_tag` 累加 `prompt / completion / total` token，
   并分模型记录调用次数。图谱构建以 `job_id` 作 tag，进度与收尾时写入 `job.stats.llm_tokens`；
   问答与摘要以 `session_id` 作 tag，落到 `chat_sessions` 的 `prompt_tokens / completion_tokens / llm_calls`，
   侧栏直接显示这段对话花掉多少。网关不返回 usage 时计入 `llm_calls_without_usage`，让"数字偏小"可解释。
   **坑**：网关会对一次回答重复推送多帧 usage，必须只取最后一帧（实测差 3 倍）。**未做**：`latency` 归集与跨场景汇总报表。

### 3.2 部署拓扑（一期单机）

| 容器 | 镜像 | 端口 | 资源建议 |
|---|---|---|---|
| `web` | nginx:alpine + `pnpm build` 产物 | 80 | 0.5C / 256M |
| `api` | `ghcr.io/astral-sh/uv:python3.11-bookworm-slim` + `uv sync --frozen` | 8000 | 2C / 2G |
| `worker-ingest` | 同 api 镜像，不同 entrypoint | — | 2C / 2G |
| `worker-graph` | 同上 | — | 1C / 1G（IO 密集） |
| `postgres` | **pgvector/pgvector:pg18**（官方带扩展镜像） | 5432 | 2C / 2G（HNSW 建索引吃内存） |
| 外部 | 360 网关 | — | 按量 |

> **`postgres` 镜像必须带 pgvector**：官方的 `postgres:18` 不含扩展，直接 `CREATE EXTENSION vector` 会报 "could not open extension control file"。用 `pgvector/pgvector:pg18`，或在 Dockerfile 里自行编译 `pgvector` 0.8.x（Windows 本地场景可用官方预编译包，见 §14.2）。

**Embedding 不单独起容器（v1.1 变更）**：无 GPU 时 bge-large（int8）在 8 线程 CPU 上实测 2.3-2.9 chunk/s，进程内调用省掉一次 HTTP 往返和一层运维。吞吐随序列长度非线性下降，且受**可用内存**强约束——模型 326MB 之外，激活内存随 batch×seq 线性增长，超出可用内存会直接掉到 swap，吞吐断崖（实测 16 条 2.33 块/s → 64 条 0.2 块/s）。所以块大小、批大小既是质量参数、也是成本参数。阶段划分：

| 阶段 | 部署形态 | 说明 |
|---|---|---|
| 一期（无 GPU） | **进程内**，`worker-ingest` 直接加载模型 | 单进程内存 +300MB；启动时预加载，避免首个请求等 20s |
| 二期（有 GPU） | 可选升级为 TEI 独立容器 | 多 worker 共享一份模型显存，改 `EMBEDDING_PROVIDER=tei` 即可，接口不变 |

> 图谱与正文同库：`entities.novel_id` 直接 `REFERENCES novels(id) ON DELETE CASCADE`，删书不用写补偿逻辑（§6.3）。图规模超过千万级边、或真需要社区发现/PageRank 这类图算法时，再拆到 Neo4j —— 换的是 `services/graph/store.py` 一个文件。

### 3.3 双管道设计（核心思想）

**写入侧与查询侧完全解耦**：写入是异步、可重跑、幂等；查询是同步、低延迟、可降级。二者唯一的契约是**三份共享标识**：

- `novel_id`：全书隔离键（`chunk_vectors` / `chunk_lexical` / `relations` 的普通列 + 关系库主键）
- `chunk_id`：`ck_<hex>`，`chunks` 主键；`chunk_vectors` / `chunk_lexical` 以它为外键（`ON DELETE CASCADE`），图谱证据反查的锚点
- `chapter_no`：时序轴，图谱与向量共用的时间线

这使得"向量化失败但图谱成功"这种中间态可以被独立重试，不需要整本重跑。

## 5. 数据流转链路

### 5.1 全链路数据形态演进

| 阶段 | 数据形态 | 体量（100 万字参考） | 存储位置 |
|---|---|---|---|
| L0 原始 | `.txt` / `.epub` / `.docx` | 3 MB | 本地 `data/raw/{novel_id}/`（可切 S3） |
| L1 规范化 | UTF-8 纯文本 + 章节索引 | 3 MB | `data/parsed/{novel_id}.jsonl` |
| L2 块 | child 400 tokens / parent 1400 tokens | ≈ 4,000 child + 1,200 parent | 关系库 `chunks`（正文可只存偏移） |
| L3 向量 | `vector(1024)`（fp32，单条 4 KB） | 4,000 × 4 KB ≈ 16 MB + HNSW 索引 ≈ 20 MB | `chunk_vectors`（PG 内） |
| L3' 词法 | `tsvector` 倒排（bigram） | ≈ 原文 60% 体积 | `chunk_lexical`（PG 内，GIN 索引） |
| L4 图 | 实体 ≈ 1,500 / 关系 ≈ 6,000 | 边 6k ≈ 3 MB | PG（`entities` / `relations`） |
| L5 摘要 | 章摘要 200 × 150 字 | 60 KB | `chunks`（level=3） |

### 5.2 数据一致性策略

- **单一事实源（SoT）**：正文与章节结构以 PG 的 `novels` / `chapters` / `chunks` 为准；`chunk_vectors` / `chunk_lexical` / `entities` / `relations` / `entity_mentions` 都是**可重建的派生索引**，且全部与 SoT 同库，用外键 + 级联约束住，不会漂移——不存在"需要应用层清理"的第三方库（这是放弃 Milvus / Neo4j 的核心收益）
- 每部书记录 `manifest`：`{parse_version, chunk_version, embedding_model, graph_schema_version}`，任一版本变化触发"标记为 stale → 后台重建"，不做实时双写
- 删除书：先 `cancel(novel_id)` 通知 worker 停手 → 应用层按 `chunks → chapters → novels` 顺序删（**这三张表之间目前没有外键**，见 §6.1 已知缺口）→ `chunk_vectors` / `chunk_lexical` / `entities` / `relations` / `entity_mentions` 由 `ON DELETE CASCADE` 随 `chunks` 自动清空 → 最后删文件
- 向量写入使用 `INSERT … ON CONFLICT (chunk_id) DO UPDATE`，重跑天然幂等；词法索引按书整体"先删后插"，同样幂等；图谱**整书先清空再重建**（`DELETE entity_mentions → relations → entities`），配合 `on_conflict_do_nothing` + 三个唯一约束（`novel+type+name`、`novel+src+dst+relation`、`entity+chunk`）兜住重边——不做增量 diff，因为抽取结果依赖 prompt 与模型版本，口径一变旧的边就不再可比较

### 5.3 失败与重试模型

| 失败点 | 策略 | 兜底 |
|---|---|---|
| Embedding 服务超时 | 指数退避 3 次（1/4/16s） | 该批标记 `pending_embed`，任务 `PARTIAL`，可单独重跑 |
| PG 写入失败 / 连接池耗尽 | 批大小自适应减半 + 事务回滚重试；池上限 8（运行）/16（溢出） | 落本地 `failed_batches.jsonl` 落盘续传 |
| LLM 抽取超时/JSON 不合法 | 重试 2 次（温度 0 → 0 且加"仅输出 JSON"） | 降级为规则抽取（人名/对话引号），标记 `low_confidence` |
| 图谱抽取返回非法 JSON | 重试一次（要求精简输出）+ 括号配平 / 截断救回 | 该块跳过并记 `empty_json`，不阻塞整本 |
| 任务进程崩溃 / 服务重启 | 启动时 `recover_stale()` 扫 `jobs` 表，PENDING 与未开始的一律重新 `submit()` | 已完成的 stage 不重跑（按 stage 字段续跑）；`RUNNING` 但有进度记录的按 checkpoint 恢复 |
| 用户删除书但 worker 还在跑 | `DELETE` 前调 `cancel(novel_id)` 写内存取消信号，向量化循环每批检查一次 | 抛 `IngestCancelled` → 清掉已写的残留向量 → 任务标记取消，不留僵尸 |

## 6. 数据模型设计

### 6.1 关系库（PostgreSQL）表结构

> 以下 DDL 与线上库 `pg_dump --schema-only` 逐字对齐（v1.6 校验）。主键统一用 `varchar(40)` 而不是 UUID，格式是 `前缀_hex`：`nv_`（书）、`ck_`（块）、`cs_`（会话）、`job_`（任务）。理由是这些 id 会出现在 URL、日志、前端状态里，可读前缀带来的排障效率远比 16 字节存储收益重要。

```sql
-- 书籍
CREATE TABLE novels (
  id            varchar(40)  PRIMARY KEY,          -- nv_<16 hex>
  title         varchar(200) NOT NULL,
  filename      varchar(255) NOT NULL,
  storage_key   varchar(512) NOT NULL,             -- 存储层 key，不存绝对路径
  file_size     integer      NOT NULL,
  encoding      varchar(32)  NOT NULL,             -- utf-8 / gb18030 …
  char_count    integer      NOT NULL DEFAULT 0,
  chapter_count integer      NOT NULL DEFAULT 0,
  chunk_count   integer      NOT NULL DEFAULT 0,
  status        varchar(20)  NOT NULL,             -- PENDING|PARSING|CHUNKING|EMBEDDING|READY|FAILED
  meta          jsonb        NOT NULL DEFAULT '{}',
  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now()
);

-- 章节
CREATE TABLE chapters (
  id          varchar(40)  PRIMARY KEY,
  novel_id    varchar(40)  NOT NULL,               -- ⚠ 未加外键，见本节末"已知缺口"

  char_end    integer      NOT NULL,

CREATE INDEX ix_chapters_novel_no ON chapters (novel_id, chapter_no);

-- 块（父子同表，靠 level 区分）

  chapter_no  integer      NOT NULL,

  severity   varchar(10)  NOT NULL,                -- info | warn | error
  detail     text         NOT NULL,
  char_start integer      NOT NULL
);

-- 任务（一个任务一行，进度原地更新）
CREATE TABLE jobs (
  id              varchar(40)  PRIMARY KEY,

  status          varchar(20)  NOT NULL,           -- PENDING|RUNNING|COMPLETED|FAILED|CANCELED|PARTIAL
  stage           varchar(20)  NOT NULL,           -- PARSING|CHUNKING|EMBEDDING|DONE（见 §8.1）

  chars_done      integer      NOT NULL DEFAULT 0,
  chars_total     integer      NOT NULL DEFAULT 0,

  chapters_total  integer      NOT NULL DEFAULT 0,

-- 会话与消息
CREATE TABLE chat_sessions (
  id         varchar(40)  PRIMARY KEY,

CREATE TABLE chat_messages (

```

**已知缺口（有意保留为技术债，不是遗漏）**

| 缺口 | 现状 | 为什么要补 / 什么时候补 |
|---|---|---|
| `chapters.novel_id`、`chunks.novel_id`、`jobs.novel_id` 无外键 | 只有 `chunk_vectors` / `chunk_lexical` 挂了 `REFERENCES chunks(id) ON DELETE CASCADE` | 删书目前靠应用层按"chunks → chapters → novels"顺序删。加了 FK 之后删书就是一句 `DELETE FROM novels`，且不会漏。**建议 P1 补**，代价是一次 `ALTER TABLE`（小表瞬间完成） |
| 没有 `job_steps` 检查点表 | 用 `jobs.stage` + `chunks` 已有行数做断点判断 | 当前粒度够用（重跑按 stage 跳过已完成段）；等出现"同一 stage 内需要细粒度续跑"的真实需求再建 |
| `chunks.parent_id` 无自引用外键 | 只有普通索引 | 自引用外键会让批量删除的约束检查变复杂，而 `level`/`parent_id` 由切块器一次写入、不会中途改，收益低于成本 |

### 6.2 向量与词法表（pgvector）

**两张派生表，不塞进 `chunks`**。原因不是"整洁"，是写入模式不同：入库是"先写正文、再逐批补向量"，而向量 4 KB/条会让 `chunks` 行变宽、触发 TOAST 与整行重写；拆开后 `chunks` 写入后基本只读，向量表可以放心批量 upsert。

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 稠密向量：一条 child chunk 一条
CREATE TABLE chunk_vectors (
  chunk_id  varchar(40) PRIMARY KEY
            REFERENCES chunks(id) ON DELETE CASCADE,
  novel_id  varchar(40) NOT NULL,
  embedding vector(1024) NOT NULL        -- 维度必须等于 EMBEDDING_DIM，换模型要改列类型
);
CREATE INDEX ix_chunk_vectors_novel_id ON chunk_vectors (novel_id);
CREATE INDEX ix_chunk_vectors_hnsw
  ON chunk_vectors USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 词法倒排：bigram 串 + tsvector
CREATE TABLE chunk_lexical (
  chunk_id  varchar(40) PRIMARY KEY
            REFERENCES chunks(id) ON DELETE CASCADE,
  novel_id  varchar(40) NOT NULL,
  bigrams   text NOT NULL,               -- "陆沉 沉把 把刀"，留原文便于排查分词问题
  tsv       tsvector NOT NULL
);
CREATE INDEX ix_chunk_lexical_tsv ON chunk_lexical USING gin (tsv);
CREATE INDEX ix_chunk_lexical_novel ON chunk_lexical (novel_id);
```

**三个设计决定**

| 决定 | 理由 |
|---|---|
| `novel_id` 冗余存在向量表（本可从 `chunks` join） | 检索时 `WHERE novel_id=?` 是热路径，join 会让 HNSW 的 `ORDER BY` 走不了索引下推；多存 40 字节换一次 join |
| **不建** `(novel_id, embedding)` 复合索引 | pgvector 0.8 的 HNSW 不支持多列复合；带过滤的召回靠 `iterative_scan` 而不是复合索引 |
| `bigrams` 列保留 | 出问题时能直接看到"这句话是怎么被切的"，比只存 `tsv` 可诊断得多（tsv 的 lexeme 顺序已被排序，看不出原文） |

**索引是懒建的，这是个运维坑**：`ensure_ready()` 在首次进入入库流水线或向量后端初始化时才建索引，**迁移脚本不会触发**。所以"迁完数据但检索很慢"往往是 HNSW 没建。判断方法：

```sql
SELECT indexname FROM pg_indexes WHERE tablename = 'chunk_vectors';
-- 没有 ix_chunk_vectors_hnsw 就手工补：
-- CREATE INDEX ix_chunk_vectors_hnsw ON chunk_vectors USING hnsw (embedding vector_cosine_ops)
--   WITH (m = 16, ef_construction = 64);
```

**检索参数**

| 参数 | 取值 | 依据 |
|---|---|---|
| 距离算子 | `<=>`（余弦距离） | 向量已归一化，余弦与内积等价，余弦距离 `1-cos` 更直观 |
| `hnsw.ef_search` | 100（配置）/ 40（pgvector 默认） | 越大召回越好、延迟越高；10 万级用 100 足够 |
| `hnsw.iterative_scan` | `relaxed_order` | **必开**：HNSW 先取候选再过滤，`WHERE novel_id` 会把候选吃掉导致召回不足；relaxed 允许边扫边过滤 |
| `limit`（每通道） | 50 | 给 RRF 与 rerank 留冗余 |
| 词法排序 | `ts_rank_cd` | 覆盖密度排序，比 `ts_rank` 更适合长块 |
| 词法 0 分过滤 | `score > 1e-9` 才保留 | 只命中高频 bigram（"的了""是在"）时 `ts_rank_cd` 会返回 0，这批行的相对顺序是噪声，喂进 RRF 会把好结果挤下去 |

> **不设 `IVFFlat` 备选**：IVFFlat 必须先有数据才能聚类出合理中心，空表建索引等于白建；而且它对过滤检索的召回问题比 HNSW 更严重。真要兜底，用 `VECTOR_BACKEND=numpy` 全量扫描（离线、单机、数据量小的时候反而更准）。

### 6.3 知识图谱的数据模型（PostgreSQL，不用 Neo4j）

原设计（v1.0–v1.6）用 Neo4j 存图谱。P1-M5 落地时改成了 PG 三张表，是算过账的：

| 维度 | Neo4j | PG 三表（现方案） |
|---|---|---|
| 部署成本 | 需 JVM（约 180MB）+ 服务端（约 150MB），多一个常驻进程 | 零新增 |
| 删书一致性 | 两库各删一次，没有约束兜底 | `ON DELETE CASCADE`，一条 DELETE 清干净 |
| 本项目实际查询 | 实体定位 / N 跳邻域 / 章节时间线 | 递归 CTE 全覆盖 |
| 实测延迟 | 冷启动要等页缓存预热 | 2 跳子图 22–35 ms（87 实体 / 164 边，含 HTTP 开销） |
| 图算法 | 自带 GDS（社区发现、PageRank） | 需要自己写迭代 SQL |
| 规模上限 | 亿级边 | 千万级边（单机） |

决定性因素不是性能，是**"删书"这件事**。Milvus 时代已经吃过一次"书删了、派生数据还在跑"的亏（§5.6），再引一个没有外键关系的库，等于把同一个坑重挖一遍。而 GDS 那类图算法目前并不需要——真要时换掉 `services/graph/store.py` 一个文件即可。

#### 6.3.1 三张表

```sql
-- 规范实体：同一人物的不同称谓在这里合并
CREATE TABLE entities (
  id            VARCHAR(40) PRIMARY KEY,               -- ent_xxxx
  novel_id      VARCHAR(40) NOT NULL REFERENCES novels(id) ON DELETE CASCADE,
  name          VARCHAR(120) NOT NULL,
  type          VARCHAR(20)  NOT NULL,                 -- Character/Faction/Location/Item/Event/Concept
  aliases       JSONB        NOT NULL DEFAULT '[]',    -- 别名：本名/字/号/绰号
  desc          TEXT         NOT NULL DEFAULT '',
  first_chapter INT          NOT NULL DEFAULT 0,
  importance    DOUBLE PRECISION NOT NULL DEFAULT 0,   -- 0-1，mention 的对数缩放
  mention_count INT          NOT NULL DEFAULT 0,
  meta          JSONB        NOT NULL DEFAULT '{}',
  CONSTRAINT uq_entities_novel_type_name UNIQUE (novel_id, type, name)
);
CREATE INDEX ix_entities_novel_type       ON entities (novel_id, type);
CREATE INDEX ix_entities_novel_importance ON entities (novel_id, importance);

-- 关系边
CREATE TABLE relations (
  id           VARCHAR(40) PRIMARY KEY,                -- rel_xxxx
  novel_id     VARCHAR(40) NOT NULL REFERENCES novels(id) ON DELETE CASCADE,
  src_id       VARCHAR(40) NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  dst_id       VARCHAR(40) NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  relation     VARCHAR(30) NOT NULL,                   -- 中文枚举，见 6.3.2
  raw_relation VARCHAR(30) NOT NULL DEFAULT '',        -- 模型原词（不在枚举内时留档）
  strength     DOUBLE PRECISION NOT NULL DEFAULT 0.5,
  confidence   DOUBLE PRECISION NOT NULL DEFAULT 0,
  status       VARCHAR(10) NOT NULL DEFAULT 'active',  -- active | pending
  evidence     TEXT NOT NULL DEFAULT '',
  chapter_no   INT  NOT NULL DEFAULT 0,
  chunk_id     VARCHAR(40) REFERENCES chunks(id) ON DELETE SET NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uq_relations_edge UNIQUE (novel_id, src_id, dst_id, relation)
);
CREATE INDEX ix_relations_novel_status ON relations (novel_id, status);

-- 实体出现在哪个块（章节-实体倒排）
CREATE TABLE entity_mentions (
  id         VARCHAR(40) PRIMARY KEY,
  novel_id   VARCHAR(40) NOT NULL REFERENCES novels(id) ON DELETE CASCADE,
  entity_id  VARCHAR(40) NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  chapter_no INT NOT NULL DEFAULT 0,
  chunk_id   VARCHAR(40) REFERENCES chunks(id) ON DELETE SET NULL,
  count      INT NOT NULL DEFAULT 1,
  CONSTRAINT uq_mentions_entity_chunk UNIQUE (entity_id, chunk_id)
);
```

**三个设计决定**

1. **唯一键是 `(novel_id, type, name)` 而不是 `(novel_id, name)`**。"青云"既可能是门派也可能是地名，只按名字唯一会把两类强行合并。
2. **`relations.chunk_id` 用 `SET NULL` 而不是 `CASCADE`**。重新入库会重建 `chunks`；若级联删边，一次切片参数微调就把几千条 LLM 抽出来的边全清了（重抽很贵）。宁可"有边无证据"，也不让正文重跑牵动图谱。
3. **用 `status` 两态，不另建审核表**。置信度低于 0.6 的边标 `pending`：不进可视化主图，但仍在库里可查。比"直接丢弃"覆盖率高一倍，比"单开一张候选表"少一次 join。

#### 6.3.2 关系词表

前 17 个是人对人，后 4 个是跨类型的结构关系（人→势力/事件/地点/物品）：

```
师徒 父子 母子 父女 母女 兄弟 姐妹 夫妻 道侣 爱慕 敌对 盟友
上下级 同门 朋友 主仆 亲戚 | 归属 参与 位于 持有 | OTHER
```

用中文而不是 `MASTER_DISCIPLE` / `ENEMY_OF`：中文小说里"道侣/宿敌/同门"的信息量比英文枚举细，而模型直接输出中文的准确率明显更高，少一层映射就少一处漂移。不在枚举内的词落到 `OTHER`，原词留在 `raw_relation`——攒够频次就能反推该往词表里加什么，而不是拍脑袋定。

#### 6.3.3 N 跳邻域：递归 CTE

```sql
WITH RECURSIVE nb(entity_id, depth) AS (
    SELECT CAST(:seed AS VARCHAR(40)), 0
  UNION
    SELECT CASE WHEN r.src_id = nb.entity_id THEN r.dst_id ELSE r.src_id END, nb.depth + 1
    FROM relations r
    JOIN nb ON (r.src_id = nb.entity_id OR r.dst_id = nb.entity_id)
    WHERE r.novel_id = :novel_id
      AND nb.depth < :hops
      AND (:include_pending OR r.status = 'active')
)
SELECT DISTINCT entity_id FROM nb LIMIT :max_nodes
```

两个必须注意的点：

- **`depth < :hops` 不能省**。只靠 `UNION`（而非 `UNION ALL`）去重是不够的：`(a,1)` 和 `(a,2)` 是两行不同记录，环上的边会让递归发散。
- **`LIMIT` 放最外层**。放进递归项里并不会限制发散，只是每层少返回几行。

前端首屏不带 `center` 时走另一条路：按 `importance` 取前 200 个实体当骨架，只连骨架之间的边——一本书几千个实体全画出来既看不清、也会让力导向退化成毛球。

#### 6.3.4 为什么图谱一定要给 RAG 用

图谱不是为了好看。问答时先用"实体名出现在问题里"做精确匹配（不走向量——短专名在向量空间里区分度很差），命中后取这些实体的**一跳**关系，作为【人物关系】注入 prompt：

```
【人物关系】（图谱抽取，仅辅助理清关系）
- 刘备 —兄弟→ 关羽（第1章）
- 刘备 —兄弟→ 张飞（第1章）
- 关羽 —盟友→ 张飞（第1章）
```

只取一跳不做多跳：多跳关系的边际收益远低于"这两个人到底有没有关系"这件事本身，而多跳会把上下文预算吃光、还容易引出与问题无关的旁支。命中实体上限 6 个、事实上限 20 条、总条数受 `GRAPH_RAG_MAX_FACTS` 约束。

这条路径**整条可缺席**：没建图谱、没命中实体、查询抛异常，都只是少一段提示，问答照常返回。

### 6.4 各存储的分工边界

| 数据 | 放哪 | 不放哪（原因） |
|---|---|---|
| 正文长文本 | PG `chunks.content` + 原文文件 | 不进向量表（正文是 SoT，且行宽会拖慢向量批量写） |
| 向量 | PG `chunk_vectors`（`vector(1024)` + HNSW） | 不进应用内存（重启即失、多进程不共享）；不回到独立向量库（跨库一致性无解，见 §0①） |
| 词法倒排 | PG `chunk_lexical`（`tsvector` + GIN） | 不进外部搜索引擎（Elasticsearch 为此多一套集群，收益在百万级才显现） |
| 实体与关系 | PG `entities` / `relations` / `entity_mentions` | 不进独立图库（本项目的查询只有定位/N 跳/时间线，递归 CTE 覆盖，且能靠外键跟着书一起删；见 §6.3） |
| 检索日志 | PG（分区表按月） | 不进缓存（要可分析与回放） |
| 热点缓存 | 进程内 LRU（一期）→ Redis（多实例时） | 不进 PG（延迟） |

> **P1-M5 落地后仍然是单库**：图谱直接建在 PG 里，删书时 `entities` → `relations` → `entity_mentions` 全部由外键级联清掉，不存在"正文删了、图还在"的可能。这也是当初放弃 Neo4j 的主要理由 —— Milvus 时代为跨库一致性写的补偿代码是纯负债。

> 视觉上什么都不丢。`done` 仍带同一个 id，作为预建失败时的兜底。见 §8.12.2。

> `thinking:{"type":"disabled"}`（探测结果 `thinking_switch=false`），所以它**一定会想**。
> 实测一个普通问题：首思考 1.0~2.5s，首正文 15~43s。只转发 `content` 的话，
> 用户点完发送要盯着空气半分钟，看起来就是卡死。思考增量还顺带把"检索/精排/图谱"
> 的命中情况摆出来，慢回答的归因不用再翻日志。

### 7.2 鉴权与限流

- 管理端：JWT（`Authorization: Bearer`），角色 `admin` / `viewer`
- 问答端：可匿名但按 `IP + session` 限流（`slowapi`，20 QPS/实例）
- 上传：单文件 ≤ 100 MB，扩展名白名单，`python-magic` 校验真实 MIME，防止伪造扩展名
- 所有写接口要求 `Idempotency-Key` 头（可选），重复提交返回同一 `job_id`

### 7.3 内部模块接口（Python Protocol）

模块间只依赖协议，不依赖实现——这是二期拆微服务的提前量。

```python
# adapters/protocols.py
from typing import Protocol, AsyncIterator, Sequence, BinaryIO, Any
from dataclasses import dataclass

@dataclass(slots=True)
class Chunk:
    chunk_id: str; novel_id: str; chapter_no: int; level: int
    seq: int; content: str; parent_id: str | None = None
    speakers: list[str] | None = None; entities: list[str] | None = None
    token_count: int = 0

@dataclass(slots=True)
class RetrievedChunk:
    chunk: Chunk; score: float; channel: str      # dense|sparse|hybrid|rerank

class ObjectStorage(Protocol):
    """本地文件夹与对象存储的统一抽象（要求 6：预留迁移）"""
    async def put(self, key: str, data: BinaryIO, content_type: str = "text/plain") -> str: ...
    async def get(self, key: str) -> bytes: ...
    async def open_stream(self, key: str) -> AsyncIterator[bytes]: ...
    async def delete(self, key: str) -> None: ...
    async def exists(self, key: str) -> bool: ...
    async def presigned_url(self, key: str, expires: int = 3600) -> str | None:
        """本地实现返回 None，前端走 /files/{key} 代理下载"""
```

## 8. 关键实现细节

### 8.1 任务状态机

```
PENDING ──► PARSING ──► CHUNKING ──┬──► EMBEDDING ──► VECTOR_INDEXED ──┐
                                   │                                  ├─► COMPLETED
                                   └──► GRAPH_EXTRACTING ──► GRAPH_WRITING ──┘
                         任一阶段失败 ──► FAILED（可 retry 从断点续）
                         部分批次失败 ──► PARTIAL（可单独重跑失败批）
```

`VECTOR_INDEXED` 与 `COMPLETED` 分开的意义：**向量先就绪就能开放问答**，图谱晚到只是少了关系增强，前端可显示"图谱构建中（62%）"，用户体验不阻塞。

**取消与重试（v1.7 补，任务中心用）**：

```
PENDING  ──取消──►  CANCELED（还没被 worker 取走，直接改状态，取到就跳过）
RUNNING  ──取消──►  CANCELED（置信号 → 长循环每批次检查一次 → 1-3 秒内停手，已写数据保留）
FAILED / CANCELED ──重试──► PENDING（复用同一行 job，只重置进度字段，重新入队）
```

两条**刻意分开**的取消通道很关键：`cancel(novel_id)` 表示"这本书被删了"，收尾时要清空它的向量；`cancel_job(job_id)` 表示"先别算了"，**一个字节都不删**。早期两者共用一个信号，导致"取消重算向量"会顺手把一本好书的全库向量删掉——这类错误在数据层不可逆，所以信号必须分家。

### 8.2 分章与清洗（中文小说的坑）

小说文本没有标准结构，按以下顺序兜底：

1. **目录法**：若末尾 5% 文本包含 `第一章…第N章` 且行首重复，识别为目录页，剔除
2. **标题正则**：`^\s*(第[零一二三四五六七八九十百千万0-9]+[章节回卷][^\n]{0,40})\s*$`，另兼容 `Chapter \d+`、`序章`、`楔子`、`尾声`
3. **长度约束**：单章 > 5 万字视为漏切，二次按空行 + 段落密度切；单章 < 200 字合并到下一章
4. **编码**：`charset-normalizer` 探测；GBK/GB18030 常见，探测失败按 GB18030 强解
5. **清洗**：去 BOM、去 `&nbsp;`、合并 3 个以上连续空行、去掉"（本章完）""求月票"等噪声行、全角半角统一
6. **对话识别**：`“…”` / `"…"` / `「…」` 三种引号，配合前后 `说|道|问|答|喊|笑道` → 说话人候选

### 8.3 分层切块（质量的核心）

```
Chapter(整章)
 ├─ parent  P1 (1400 tokens, 边界对齐场景/段落)
 │   ├─ child C1 (400 tokens, overlap 60)
 │   ├─ child C2
 │   └─ child C3
 ├─ parent  P2 …
 └─ summary S (150 字, 由 glm-5 生成, 也写向量库 level=3)
```

- **child 用于检索**（小而准），**parent 用于生成**（大而全）——命中 child 后回溯 `parent_id` 取原文，这是 small-to-big 的精髓：检索精度和上下文完整度不再互相牺牲
- 切分优先级：章节边界 > 场景分隔（`***`、空行×2、时间/地点转换句）> 段落 > 句子（`。！？…`）> 硬切
- 用**中文 tokenizer 估算**（`tiktoken` 对中文偏差大，用 `transformers` 的 BGE tokenizer 精确计数，或按 1 汉字≈0.75 token 估算后校准）
- 每个 chunk 带 `chapter_no` + `seq`，保证**检索结果可回溯到原文位置**

### 8.3.2 切片完成度查看（v1.1 新增需求）

**为什么单独做一层**：切块是整条链路里"最容易错、又最没人能核实"的一步。用户只看到"处理中 60%"，但 60% 是按什么算的？块切歪了没有？某一章是不是被整体吞掉了？不把过程摊开，出问题只能靠猜。

**完成度的定义（避免假进度）**

进度不能用"块数"算——切块是流式的，总块数事前未知，用块数算会出现"90% 停住不动"或"越跑越退"。定义如下：

```
progress = 已切分字符数 / 全文有效字符数 × 100
```

块数、token 分布、告警数都是**副指标**，用于判断质量，不参与进度计算。三个阶段各自有独立进度条，因为它们的耗时差异极大（切块秒级、向量化分钟级）：

| 阶段 | 计量单位 | 典型耗时（100 万字） |
|---|---|---|
| 解析分章 `PARSING` | 章节数 | 2-5 s |
| 切块 `CHUNKING` | 字符数 | 5-15 s |
| 向量化 `EMBEDDING` | 已编码块数 | CPU 3-5 min / GPU 30 s |

**完成度档案（`chunk_reports` 表，一次任务一行，实时更新）**

```jsonc
{
  "novel_id": "8f2c…",
  "job_id": "b31a…",
  "stage": "CHUNKING",
  "progress": 62.4,
  "chars_done": 623180, "chars_total": 998442,
  "chapters_done": 128, "chapters_total": 201,
  "chunks": { "child": 2480, "parent": 812, "summary": 128 },
  "tokens": { "avg": 386, "p50": 372, "p95": 452, "max": 1786 },
  "warnings": [
    { "level": "warn",  "code": "CHUNK_TOO_LONG", "chapter_no": 57,
      "chunk_id": "8f2c:57:2", "detail": "1786 tokens，超过 parent 上限 1.3 倍" },
    { "level": "error", "code": "CHAPTER_EMPTY",  "chapter_no": 88,
      "detail": "正文仅 32 字，疑似把‘本章完’误判为章节标题" }
  ],
  "eta_sec": 42,
  "updated_at": "2026-10-27T11:40:22+08:00"

```

**异常检测规则（每条都可关、阈值可配）**

| code | 触发条件 | 为什么重要 |
|---|---|---|
| `CHAPTER_EMPTY` | 章节正文 < 200 字 | 目录页/广告行被误判为章节 |
| `CHAPTER_TOO_LONG` | 单章 > 5 万字 | 漏切，后续时序检索全错 |
| `CHUNK_TOO_LONG` | 块 > 1.3 × 目标 token | 硬切没生效，会被 embedding 截断 |
| `CHUNK_TOO_SHORT` | 块 < 60 token | 噪声块，污染检索结果 |
| `PARENT_MISSING` | child 的 `parent_id` 找不到 | 切块逻辑 bug，生成时回溯失败 |
| `OVERLAP_ANOMALY` | 相邻块重叠 < 20 或 > 200 token | 上下文断裂或大量重复 |
| `DUP_CHUNK` | 两章内容相似度 > 0.95 | 原文件本身重复（盗版合并常见） |
| `ENCODING_SUSPECT` | 乱码字符占比 > 1% | 编码猜错，向量全废 |

**实时推送（复用任务 SSE，不新开通道）**

```
event: chunk_progress
data: {"stage":"CHUNKING","progress":62.4,"chapters_done":128,"chapters_total":201,
       "chunks":{"child":2480,"parent":812},"warnings":2,"eta_sec":42}
```

节流：**500 ms 合并一次**（`CHUNK_PROGRESS_PUSH_MS`），否则每切一章推一帧会把 SSE 打满，前端反而卡。

**前端呈现（`/novels/{id}/chunk-review` 页面，P0 就要有）**


关键设计：**每个告警都能一键跳到对应章节原文**（用 `chapter_no` 定位），不然告警等于噪音；**抽样预览固定抽 10 条**，让人 30 秒内就能判断"切得对不对"，而不是翻 4000 条。

**跑完之后还能复核**（不只是过程中的一次性展示）：`GET /novels/{id}/chunks` 支持按章节/层级/关键字筛选，`/chunk-review` 页保留完整统计与告警清单，作为"这部书能不能用"的准入判断。

### 8.4 图谱抽取 Prompt 设计（质量的关键）

三层抽取，逐层收敛（v1.7 按真实实现重写，与 `backend/app/services/graph/` 一致）：

| 层 | 实现位置 | 手段 | 作用 | 输出 |
|---|---|---|---|---|
| L1 规则 | `candidates.py` | 对话引导正则 + 称谓后缀词表 + 姓氏起始高频窗口（**零依赖，不用 jieba**） | 捞人名候选，作为"已知人物"提示喂给 LLM | 人名候选集（约 60 条） |
| L2 LLM | `extractor.py` | `LLM_MODEL_FAST`（温度 0，`json_mode`），**按 parent 块**调用 | 抽实体 + 关系 + 证据 | 结构化 JSON |
| L3 对齐 | `aligner.py` + `lexicon.py` | 并查集：同名同类型 + **专名**别名指向；连通分量上限 6；规范名按字面结构打分 | 解决"曹操/曹孟德"分裂，同时不让泛称把半本书焊成一个 | 规范化实体 |

**L1 为什么不用 jieba**：P1 的依赖已经砍到 `onnxruntime + tokenizers`（不装 torch、不装 FlagEmbedding），为了人名识别再引一个分词器不划算。而且 L1 的产物**不直接入库**，只作 prompt 提示，精度要求低于召回。三个信号源按精度排序：

1. **对话引导** `沈鹤道："……"` / `林薇薇冷笑道："……"` —— 中文小说里最稳定的人名位置
2. **称谓后缀** `玄阳真人` / `沈师兄` / `柳掌门` —— 抓没姓的道号（修真、武侠里这类角色往往还最重要）
3. **姓氏开头的 2-3 字高频窗口** —— 噪声最大（"白天""何必"都会被当人名），权重压到最低且要求频次 ≥ 5

**L2 为什么按块抽而不是按章抽**：一本百万字的书，一章可能几万字，一次调用塞不下——输出 JSON 会长到不可控，而且模型在长上下文里对"某条关系的证据在哪"会开始编。按 parent 块（800-1400 字）抽，token 预算可控、证据可定位到块，抽完还能点开原文看。

**Prompt 骨架**（固定前缀命中缓存）：

```
[SYSTEM: 六个实体类型 + 22 个人际关系词 + 13 条抽取规则 + 取舍原则 + 1 个示例]   ← 字节级不变
[USER: 第 {no} 章《{title}》正文：\n{text}\n（本章已确认人名：{known[:30]}）]
```

**JSON 输出约束**（走 `json_mode`；解析用 `parse_json_loose`，含括号配平 + 截断救回）：

```jsonc
{
  "entities": [
    {"name":"张飞","type":"Character","aliases":["翼德"],"desc":"涿郡人，卖酒屠猪"}
  ],
  "relations": [
    {"src":"张飞","dst":"刘备","relation":"盟友","strength":0.8,
     "confidence":0.85,"evidence":"当招募乡勇，与公同举大事"}
  ]
}
```

**注意：没有 `events` 数组**。事件不单独建表——`Event` 只是一个实体类型，事件名用简短动宾短语（"桃园结义"），涉及人物用 `参与` 关系连过去。这样事件天然进入同一张图，子图查询、证据回链、前端渲染都不用为它单写一套逻辑。

**三道质量闸门**（全部在 `parse_extraction()` 里执行，不放到后续阶段——三个检查都需要当前块原文）：

1. **置信度分档，但不丢弃**：`confidence < 0.6` 的关系标 `status='pending'`，仍写入 `relations` 表，管理台"待确认"标签页可人工过一遍。模型自评 0.55 的关系里有一半是对的，直接丢弃等于白烧 token。
2. **证据必须原文命中**：归一化（只去空白）后逐段校验，返回 `exact / partial / none`。
   - 整串命中 → `exact`
   - 按中文标点切段，**每段**都命中 → `exact`（模型常把逗号补成句号，这种改写不算编造）
   - 命中段数 ≥ 60% → `partial`，置信度 ×0.9 折扣后入库，并计入 `evidence_partial`
   - 其余 → 丢弃
   - 为什么不做简单 `str.find()`：模型很爱把两句话拼成一条证据（前半句抄对、后半句按人名套模板编）。整串比对能拦住，但"只截前 16 字比对"一定会放行——正好是错得最隐蔽那种。分段校验让"三段句里混一句编造的"也过不去。
3. **关系词收敛**：不在 22 个枚举内 → 映射为 `OTHER`，原始值存 `raw_relation`。`OTHER` 的占比可直接当"词表够不够用"的指标，扩展词表时按 raw 值聚类即可。

#### 8.4.1 落地时踩的三个坑（v1.7 实测）

**① 推理模型抽不出东西**
首版用 `z-ai/glm-5`，27 次调用全部返回空 JSON。原因不在 prompt：glm-5 是推理模型，正文走 `reasoning_content`，`content` 为空。试过 `thinking: {"type":"disabled"}`，实测 0/6 生效。**结论**：结构化抽取改用 `LLM_MODEL_FAST`（`deepseek-chat-v3`，非推理模型）——抽取任务不需要长思考，用推理模型既贵又容易把 token 全花在 reasoning 上。代码里 `extract_chunk()` 直接用 `llm.fast_model`，并在返回空时打印明确告警指向这个配置项。

**② 长块输出被截断 → 整块作废**
《三国演义》有些块抽出来 JSON 超过 6000 字符，`max_tokens=4500` 直接截断，括号配平也救不回（尾部缺的是内容不是括号）。两条对策：
- `parse_json_loose()` 做截断救回：从截断处向前找最后一个完整对象并补齐闭合括号，能保住已输出的实体和前面的关系
- 解析失败返回空时**重试一次**，重试 prompt 追加"上次输出无法解析，这次最多 6 个实体、6 条关系"——这一块里通常有一两条关键关系，丢掉就是图上的一个洞

**③ 首版图谱质量严重偏斜**
《长夜将明》首轮抽出 Item 28 条、Event 24 条、Character 只有 8 条，关系一水儿的"持有/位于"——图能跑但没用。prompt 收紧三处后重跑，Character 与"人与人"的关系成为主体：
- 明确写出**人物关系是重点**，"谁站在哪、谁手里拿着什么"价值低得多
- **物品只抽关键道具**（信物、凶器、证物、法宝、秘籍），桌椅茶具饭菜一律不抽
- **控制输出规模**：每块最多 10 实体 / 12 关系，宁可漏次要的也不要让 JSON 被截断

最终《长夜将明》87 实体 / 164 关系（133 确认 + 31 待确认）/ 696 提及，证据零丢弃，耗时 5.6 分钟。这个量级是合理的：宁可图小一点、每条边都能点开看原文，也不要一张满是"某人持有某物"的大图。

#### 8.4.2 图谱画布（Cytoscape.js）的四个坑

M9 首版是自研 SVG 力导向（374 行，坐标存 ref、直接改 DOM 属性绕开 React diff）。能跑，但每加一个交互都要碰坐标变换，且布局质量全靠调常数。v1.8 换成 **Cytoscape.js + `cytoscape-fcose`**，React 只负责"有哪些节点和边"，位置/动画/命中测试全交给 canvas。迁移过程中踩了这四个坑，都是排查起来不像直觉的：

**① `animate: true` 的布局在 StrictMode 下永远收不到 `layoutstop`**
React 18 开发模式会把组件挂载两次。fcose 的动画阶段靠 `requestAnimationFrame` 逐帧推进，第一次挂载的实例被销毁时动画没跑完，`layoutstop` 不来，节点就停在初始位置——**画布全空，但 `layoutstart` 已经触发过**。改成 `animate: 'end'`：同步算完一次性落位。代价是 200 节点会阻塞主线程 1-3 秒（可接受，图谱页不是高频页面）。

**② 零度节点被 tiling 成一块方格**
子图里常有几十个"没抽到任何关系"的实体。cose-base 对互不相连的节点会做 tiling——它们不是散在周围，而是排成整整齐齐的 6×5 网格，看起来就像布局算法坏了。`packComponents: false` 管不到这一步。最终方案：**画布只画有关系的实体**，孤立实体数量写进左下角提示（"另有 44 个无关系实体未画出"）；如果选中的实体自己就没有关系，退回 `grid` 布局把它平铺出来。

**③ fcose 的 `fit` 不可靠**
容器尺寸在布局计算期间可能变化（右侧详情栏加载、响应式重排），布局结束后的视野会偏移甚至把图推到屏幕外。在 `layoutstop` 里再 `cy.fit(undefined, 30)` 兜一次；重新布局前先 `cy.resize()`。

**④ 子图里没有中心节点（后端 bug，被画布暴露）**
递归 CTE 写的是 `SELECT DISTINCT entity_id FROM nb LIMIT :max_nodes`——**没有 ORDER BY 的 LIMIT 是"随机砍尾"**。邻域超过 200 时，中心节点可能正好被砍掉，于是"点开诸葛亮"的图里没有诸葛亮，前端高亮逻辑自然找不到人。修法：子查询按 `MIN(depth)` 排序，中心（depth 0）优先级最高；应用层再兜一次 `if center not in node_ids: insert(0)`。

顺带修掉同一轮暴露的另一个 bug：实体搜索接口用 `func.cast(Entity.aliases, text("text"))` 再 `.ilike()`，抛出 `TypeError: TextClause ... is not a TypeEngine`——`func.cast` 生成的是函数调用节点，没有类型信息。正确写法是 `sqlalchemy.cast(col, Text)`。这个接口一挂，左侧搜索框就是 500。

#### 8.4.3 实体对齐的 blob 事故（v1.10 重建）

《三国演义》首版图谱（1209 实体 / 2723 关系）看起来规模正常，但**曹操、刘备、关羽、诸葛亮四个主要人物在实体表里根本不存在**。问"曹操和刘备是什么关系"时 `graph_facts` 恒为 0，RAG 的图谱注入等于没生效。成因是一条完整的因果链，四步全部可复现：

**① 模型把尊称/官职写进了 aliases**

```text
董卓   aliases=[西凉刺史, 相国, 鳌乡侯, 恩相, 前将军, 尚父, 太师, 丞相, 董太师, 老贼, 仲颖, 董公]
孙权   aliases=[吴王, 孙仲谋, 大王, 吴侯, 孙将军, 碧眼儿, 吴主, 仲谋, 主公, 孙氏]
陈留王 aliases=[文皇帝, 天子, 高贵乡公, 元仲, 平原王, 汉中王, 阿瞒, 明公, 费亭侯, 武王, 汉献帝, 大王]
```

`丞相`、`将军`、`主公`、`天子`、`大王` 在全书里指向很多人。全书共 **59 个实体**的别名里含这类泛称。

**② 并查集顺着泛称链做传递闭包**

L3 的合并规则是"A 的 aliases 里有 B 的名字就 union"，且**没有链长上限**。泛称一进别名表，`曹操(孟德, 丞相)`、`董卓(丞相)`、`诸葛武侯(丞相)` 就被串成一张网，最终长出：

| blob | 提及量 | 实际是 |
|---|---|---|
| 诸葛武侯 | 2961 | 诸葛亮 + 所有被叫过"丞相/先生"的人 |
| 司马懿 | 1515 | 司马懿 + 司马昭 + 司马氏群像 |
| 吕布 | 1382 | 吕布 + 被叫过"将军/贤弟"的人 |
| 关云长 | 1130 | 关羽 + 被叫过"关将军/君侯"的人 |
| 陈留王 | 496 | 汉献帝 + 曹丕 + 曹髦 + 刘备(汉中王) + 曹操(阿瞒) |

**③ 提及量被泛称灌水，规范名因此选错**

`mention_count` 用 name + **全部别名**做子串计数。`丞相`全书 547 次，其中七成记到了董卓头上（董卓本名只有约 120 次）；`孔明` 1690 + `丞相` 547 + `诸葛亮` 157 ≈ 2961。而规范名按"提及最多"选，于是 `诸葛亮` 显示成 `诸葛武侯`、`关羽` 显示成 `关云长`。副作用在提及表里直接可见：**第 21 章董卓已死十年，仍有 13 条提及**。

**④ 别名的 `[:12]` 上限把本名挤掉**

正好 4 个 blob 触到上限。被并进去的人**连作为别名都不保留**，于是曹操（全书 941 次）、刘备（297 次）在图里彻底蒸发。

**修复：四道闸门**

1. **L2 提示词 + 代码双保险**：prompt 明确"别名只填专名（字/号/小名/绰号/别称），严禁填官职、尊称、泛称"；`parse_extraction` 再按 `lexicon.HONORIFICS`（约 190 个词）过滤一层，命中数计入 `dropped_honorific_alias`。
2. **L3 只认专名别名**：`is_mergeable_alias()` 要求 2-4 字、非泛称、不以封号收尾（`汉中王`/`汉献帝`/`温侯` 只能展示、不能当合并依据）。
3. **连通分量上限 `MAX_GROUP_SIZE=6`**：合并对按证据强度排序后逐个 union，超限就跳过。宁可让一个人拆成两个节点（看得见、能人工合），也不要把半本书焊成一个（不可逆）。
4. **规范名改结构打分**：`canonical_score()` 只看字面——2 字最像本名、3 字"姓+双名"次之、尾字落在表字表（德/明/长/龙/瑾…）里的往下压、封号收尾的再压。**不用提及量当选主名依据**，它本身就是被污染的量，只在同分时做 tie-break（用"被多少块抽到"）。
5. **别名截断不再吃掉本名**：`alias_map` 覆盖全部成员名（回填关系用），`entities.aliases` 字段只保留 16 条且**成员本名排在最前**。

**验收指标**（`backend/scripts/diag_graph_align.py` 直接输出）：关键实体（曹操/刘备/关羽/诸葛亮）在实体表中存在；提及量 > 800 的实体数为 0；别名里不再出现泛称；`dropped_honorific_alias` 有非零计数。

**一个反证值得记下**：拿第 5、21 章真实父块重跑完整链路，抽取层能稳定吐出 `曹操(孟德)`×8、`刘备(刘玄德,玄德)`×7、`关羽(云长)`×7，`align()` 后曹操仍在。**首版那张图是一次不可复现的历史构建产物**（当天连跑 3 次 build、其中 1 次 FAILED），不是"再对齐一次"能修好的——必须先改规则再整本重建。

#### 8.4.4 详情面板"展示不全"的两个原因（v1.11）

图谱页右侧详情栏在 1080×600 这类小窗口下只露出六七条关系，且没有滚动条——内容被硬切。两层原因叠在一起：

**① 卡片高度写死 620，面板的 `height:100%` 又没有参照物**

`.detail` 原本是 `height:100%; overflow:auto`。但它是 `.semi-card-body` 的子元素，而 body 的高度是 `auto`——**百分比高度在 `auto` 高度的父元素上解析不出来**，实际退化成内容高度，`overflow:auto` 等于没写。于是 277 条关系撑出一个 4000px 高的 div，被卡片的 `height:620` 裁掉，而卡片底部又在窗口之外（视口只有 600），看起来就是"内容丢了"。

两处都要改：
- **卡片当 flex 容器**（`display:flex; flex-direction:column`），body 用 `flex:1; min-height:0` 撑满剩余高度；`.detail` 改成 `flex:1; min-height:0; overflow:auto`。`min-height:0` 不能省——flex item 默认 `min-height:auto`，内容再长也不会缩，滚动条依旧不出现。
- **高度按剩余空间算**，不再写死 620：测量三栏容器相对 `.app-content` 的偏移，用 `clientHeight - top - padding-bottom - 图例高` 得到。图例高度必须实测（窄窗口下会折成两行），写常量要么留白过多、要么整行顶出视口多出滚动条。测量用相对 `.app-content` 的偏移而非 `getBoundingClientRect().top`，否则页面一滚高度就变一次。

**② 后端 `LIMIT 200` 是静默截断**

`get_entity` 的出入边查询写死 `.limit(200)`，且不返回总数。曹操全书 343 条、刘备 277 条，前端拿到 200 条加上"关系 200"的标题，**看起来就是全部**，用户无从知道少了三分之一。改为：单独 `COUNT(*)` 返回 `relation_total`，明细上限提到 `GRAPH_ENTITY_RELATIONS`（默认 500），前端显示"关系 277 / 仅列出前 N 条"。

**前端同时做关系分页**：默认 20 条 + 「显示更多 / 全部展开」。刘备 277 条关系一次全铺，既拖慢渲染也让滚动毫无意义；切换实体时回到 20 条并滚回顶部，否则新实体会继承上一个人的滚动位置。

### 8.5 混合检索与融合

```python
# 1) 并行召回（两条通道互不依赖，用 asyncio.gather 并发）
dense_hits = await store.search(novel_id, q_vec, limit=50)        # pgvector：HNSW + iterative_scan
lex_hits   = await lexical.search(novel_id, question, limit=50)   # tsquery + ts_rank_cd

# 2) RRF 融合（无需归一化，对两路分值尺度不敏感）
score(d) = Σ_channel 1 / (60 + rank_channel(d))

# 3) cross-encoder 精排（top 50 → top 24）
ranked = await reranker.rerank(question, fused[:50], top_n=24)

# 4) 回溯父块（同 parent 去重，最多 CONTEXT_PARENTS=8 个父块，控制 token）
parents = await store.fetch_parents(novel_id, {c.parent_id for c in ranked}, limit=8)

# 5) 图谱事实增强（可选，use_graph=true 时）
facts = await _graph_facts(novel_id, question)   # 问题点名实体 → 一跳关系，最多 6 个实体
```

**图谱这一路是"可缺席"的**：没建图谱、没命中实体、查询报错，都只是少一段提示，不阻塞问答。实体匹配用**名字/别名子串命中问题**，不走向量相似——实体名是 2-4 字短专名，向量对短文本区分度很差，精确子串在这个场景既快又准。只拿 `Character / Faction / Event` 三类去匹配：`Location`、`Item` 的名字常是普通词（"桌上""门外"），出现在问题里不代表用户想问它。

**为什么 RRF 而不是加权分数**：稠密分是 cosine（0-1），稀疏分是无界内积，加权需要归一化，而归一化参数在换模型后全部失效。RRF 只依赖排名，换 embedding 模型不用调参。

**降级链**：`hybrid → dense only → sparse only → 空结果走"全书摘要"兜底`。每一级在响应里带 `mode` 字段，前端可提示。

#### 8.5.1 落地补充（v1.4 实测，v1.6 随存储换 PG 校正）

设计和实现之间有三处必须校正，记在这里免得后人重踩：

**① 中文词法通道不能用 trigram 类分词**
trigram 只认 **≥3 字** 的连续片段，而中文小说里最高价值的检索单位恰恰是两字词：
人名（陆沉/苏晚）、物名（铜灯/暗渠）、称谓（师父/掌门）。实测 `MATCH '"铜灯"'` 直接空结果。
最终方案：把正文切成 **bigram 序列**（"陆沉把刀" → `陆沉 沉把 把刀`）交给 `to_tsvector('simple', …)` 建倒排，
查询同样转 bigram 后用 `|` 连接。两字词精确命中，长查询走部分匹配 + `ts_rank_cd` 排序，
不引 jieba（少一个依赖，也避免"索引切词"和"查询切词"两处词典漂移）。
代价：索引体积约为正文 60%（2 万块 ≈ 30MB），可接受。

**② 词法排序分可能归零，必须当作"无信号"处理**
一个 bigram 在超过半数文档里出现时区分度为 0，`ts_rank_cd` 会返回 0，
于是所有命中**并列**——排序退化成物理行序，喂给 RRF 就是纯噪声。
处理：过滤掉 ≤1e-9 的命中，若一路全为 0 则判定"词法无区分度"直接放弃该通道
（`mode` 记成 dense_only）。语料越小越容易触发，这一点在 144 块的小样本上尤其明显。

**③ 精排必须可缺席**
cross-encoder 首启要下 279MB。做法是：模型没就绪时 `rerank.ready=False`，
检索自动退回"RRF 排序"并在 `detail.rerank_error` 里写明原因，问答不中断。
实测 `bge-reranker-base` int8：50 条候选批量打分 ~0.3s（8 线程，与入库任务抢核时会翻倍）。

**④ pgvector 的过滤检索必须开 `iterative_scan`（v1.6 新增，最容易漏）**
HNSW 的执行顺序是"先在图上取 `ef_search` 个候选，再套 WHERE 过滤"。当本书只占全库一小部分时，
`WHERE novel_id = ?` 会把候选吃得七零八落，返回条数远少于 50，极端情况返回 0——**且不报错**。
表现是"检索结果质量莫名变差"，很难归因。解法：每次检索事务内
`SET LOCAL hnsw.iterative_scan = relaxed_order`，让引擎边扫过滤边补候选。

**⑤ HNSW 索引是懒建的（运维坑）**
`ensure_ready()` 只在入库流水线或向量后端初始化时执行建索引 DDL，**迁移脚本不触发**。
迁完数据直接查会很慢，检查 `pg_indexes` 里有没有 `ix_chunk_vectors_hnsw` 即可确认。详见 §6.2。

**落地的三段式**（对应代码 `services/retrieval/hybrid.py`）：

```
两路召回(各 50) → RRF(k=60) → 取头 50 → cross-encoder 打分 → 父块去重 → 取 8 段进 prompt
```

**评测工具**：`make eval NOVEL=nv_xxx BUILD=30`，脚本 `backend/scripts/eval_retrieval.py`。
造题方式是"从真实切片里让 LLM 出题，答案是这一段"（自动标注 gold parent），
指标按**父块**算 Recall@k——按 chunk_id 严格比对会把"同段相邻子块"误判成未命中，指标虚低。

长夜将明（144 块 / 25 题）首轮实测：

| 链路 | Recall@10 | p50 | p95 |
|---|---|---|---|
| dense（P0 基线） | 0.920 | — | — |
| rrf（双路 + 融合，无精排） | 0.960 | 485ms | 586ms |
| hybrid（双路 + RRF + 精排） | 0.960 | 442ms | 524ms |

结论要谨慎读：这本样本书是**机器生成的句式重复文本**，稠密通道本来就接近天花板，
所以提升只有 +4pt、精排也没体现增量。真正能验证 P1-2 指标（+8pt）的是《赘婿》这类
21,552 块的真实长篇，需等其 1024 维向量化跑完后复测。延迟数据同样受当时并发的
向量化任务影响（8 核被占满），空载需重测。

### 8.6 Prompt 组装与引用


### 8.7 流式与背压

- FastAPI `StreamingResponse(media_type="text/event-stream")`，每帧 `data: {...}\n\n`
- 上游网关的 `stream=True`，逐 chunk 转发；**客户端断开时立即 `aclose()` 上游连接**，避免继续计费（这点不做会白烧钱）
- Nginx 侧必须关缓冲：`proxy_buffering off; proxy_read_timeout 300s;`
- LLM 并发用 `asyncio.Semaphore(LLM_MAX_CONCURRENCY)` 控制，超限排队而非报错，队列长度 > 50 时直接返回 429
- **思考增量与正文分通道**（v1.9）：`LLMClient.stream_events()` yield `(kind, text)`，
  `stream()` 只是它丢掉 reasoning 的薄封装——抽取/摘要类调用方要的是干净正文，
  问卷答才需要思考。前端把 reasoning 攒在闭包里每 90ms 刷一次 state，
  不按 token 触发 setState（413 个事件/44 秒，逐条 setState 会把整棵聊天树重绘 400 次）

### 8.8 对话记忆（v1.13）

**先说结论：这一版不是"从零加记忆"，而是"后端做了一半、前端零接入，且历史只进 prompt 不进检索"。**

上线前库里已经有 34 个会话、56 条消息，`rag.py` 也早就会把历史拼进 prompt。但两个断点让"记忆"形同没有：

| 断点 | 表现 | 真因 |
|---|---|---|
| 前端从不调会话接口 | 刷新页面 `sessionId` 丢在内存里，对话"不见了" | `Chat.tsx` 的 `sessionId` 是组件 state，没有 URL/localStorage 承载 |
| 历史只进 prompt，不进检索 | 追问"他后来怎么样了"召回第 79、120 回的无关章节（0.31 分） | `retrieve()` 只吃当前 query；指代型问句里没有任何可检索实体，词法通道直接空，向量通道靠"后来/怎么样"硬凑 |

#### 8.8.1 存储：为什么必须加 `seq`

原表只按 `created_at` 排序回放。实测**同一会话里有 2 组 user/assistant 的 `created_at` 完全相同**（`now()` 在同一事务里取到同一微秒），排序退化成不稳定排序——回放出来的对话可能是"助手先答、用户后问"，模型读了直接误解轮次。

所以给 `chat_messages` 加 `seq INTEGER`，同一会话内单调递增，`ORDER BY seq` 才是真正的对话顺序。迁移用幂等 DDL（`ADD COLUMN IF NOT EXISTS`）+ `ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY created_at, id)` 回填，历史 34 个会话一次性补齐，无一残留 `seq=0`。

> 并发下 `seq` 用 `MAX(seq)+1` 在单进程内够用；多 worker 部署要换成 `SELECT … FOR UPDATE` 或序列，这里明确留了注释。

#### 8.8.2 上下文进入检索：三段式消歧

`memory.py` 负责把"上文聊的是谁"变成"检索的锚点"，三步：

1. **提候选**：不要用模型/NER（每轮都要跑，规则法是微秒级，模型要多花 1–3 秒；且漏召回只是退化成原 query，不会答错——这个不对称性决定了规则法更划算）。
   切分不能直接 `findall(r"[一-龥]{2,6}")`：它会把"华佗的著作有哪些"贪婪切成"华佗的著作有"，实体反而丢了。实现是**按非汉字切段 → 段内枚举 2–6 字子串 → 用「专名不以虚词/助词开头结尾」过滤**（`_HEAD_STOP` / `_TAIL_STOP`），能砍掉约九成垃圾（"佗的""了刘备""有哪"）。
2. **对齐实体表**：候选必须**在本书记载的 `entities.name` 里存在**才算数（`context_entities(novel_id, session_id)`）。这一步是噪声归零的关键——正则永远会有毛刺，查表后"作有""后来在长"自动消失。
3. **只在指代型问句里继承**：命中 `_ANAPHORA`（他/她/那个/后来/那呢…）才生成增强 query。独立问题"曹操和刘备是什么关系"不继承，硬塞一个不相干实体会稀释主题。

`retrieve(novel_id, question, extra_queries=[...])` 对每路 query 各跑稠密 + 词法，通道命名 `dense@0` / `lexical@0` / `dense@1` …，再统一 RRF。**原 query 永远保留一路**，增强只是多一票，不会把正确答案挤掉。

实测（《三国演义》，第 1 轮问"华佗的著作有哪些"，第 2 轮问"他后来怎么样了"）：

| 指标 | 只吃原 query | 加实体增强 |
|---|---|---|
| 词法召回 | 13~15 条 | **50 条（满额）** |
| top1 章节 | 第 79 回（无关） | **第 78 回「治风疾神医身死」** |
| 上下文实体 | — | `["华佗"]`（噪声为 0） |

#### 8.8.3 落库时序：先存提问，再存回答

原来的 `save_turn` 把问答一起写在生成器末尾。问题在于：**客户端刷新/关页时，Starlette 会取消这个流式生成器**，代码根本走不到末尾——实测第二轮刷新后库里只有第一轮的 2 条消息，追问整轮蒸发，且日志里既没有异常也没有"客户端断开"。

改成拆开：

```
save_question(session_id, question) -> seq    # 生成前先存，拿回 seq
...SSE 流式...
save_answer(session_id, seq, answer, cites)   # 正常结束：await，done 事件即代表已落库
```

被取消的分支走 `finally` 兜底：用 `asyncio.create_task` 落库（不能用 `await`——生成器被 `aclose()` 时在 `finally` 里 await 会抛 `RuntimeError: async generator ignored GeneratorExit`），存已生成的部分并标注"（本轮生成被中断）"。用户回来能看到答到一半，而不是空白。

#### 8.8.4 前端：侧栏、URL 与一个真实的竞态

- `SessionList` 侧栏：按小说隔离，显示标题 / 条数 / 相对时间，支持新建、切换、重命名、删除；`<1180px` 自动折成横向一行。
- `?session=` 深链接：`openSession()` 用 `history.replaceState` 把当前会话写进 URL（不用 push，切会话不该塞满历史栈）；首屏/切书时读回该参数，**先校验它确实属于当前这本书**再恢复，否则清掉参数——不校验的话刷新会载入别的书的对话，或者每次刷新都去请求一个已删的会话。
- 恢复会话时把**最后一条答案的引用**直接铺到右侧面板（`activeId` 指向它）。原先恢复后 activeId 为空，面板永远显示"提问后这里显示…"，用户得点进消息才知道当初引了哪几段原文。
- **竞态**：`createSession()` 是异步的，之后立刻发问时 `sessionId` 这个 state 还是旧值，请求带的是 `session_id: null` → 后端另建一个会话 → 上下文当场断掉。修法是用 `sessionRef` 承载当前会话 ID（同步写 ref、异步同步 state），发送时读 ref。
- 答案上方显示「承接上文 华佗 已用这些实体消歧检索（1 轮历史）」——让用户能**看见**记忆生效，而不是靠猜。

### 8.9 长对话压缩与成本台账（v1.14）

v1.13 把记忆打通了，但留下两个"越用越贵"的问题：上下文无上限地线性增长，以及问答成本在账上是空的。

#### 8.9.1 为什么不能靠"截断最近 N 轮"

最省事的做法是 `turns[-6:]`。但对话是链式的——第 20 轮的"他"依赖第 3 轮引入的人名，截断等于把锚点扔了，用户会觉得"聊久了它就忘了"。

滚动摘要（rolling summary）是更划算的折中：**旧回合压成一段自然语言摘要常驻，最近 `keep_turns` 轮保留原文**。

| 参数 | 默认 | 说明 |
|---|---|---|
| `chat_summary_enabled` | `true` | 总开关，关掉即退回纯原文窗口 |
| `chat_summary_trigger_turns` | `8` | **未被摘要覆盖的回合数**超过它就触发压缩 |
| `chat_summary_keep_turns` | `3` | 压缩后保留最近几轮原文 |
| `chat_summary_model` | `deepseek-chat-v3` | 与主链路同模型（`z-ai/glm-5` 是推理模型，`content` 为空，不能用） |

存储只加两列：`summary TEXT` + `summary_seq INTEGER`。

**`summary_seq` 是关键**——它记录"摘要已经覆盖到第几条消息"。没有它就不知道哪些回合已经压过，会重复压缩、重复计费。`prepare()` 里的用法是：

```python
summary, covered = await memory.load_summary(session_id)
if covered:
    turns = [t for t in turns if int(t.get("seq") or 0) > covered]
memory_block = memory.build_memory_block(turns, summary)   # 摘要前置 + 原文在后
```

⚠️ 两个我踩过的坑，都写进了回归测试：

1. **触发条件要用"回合数"，不是"消息条数"**。第一版写的是 `len(turns) - keep_turns`，而 `turns` 里一问一答各占一条——`turns[:-3]` 只砍掉 3 *条消息*，实际不到 2 个回合，压缩完几乎没释放上下文。正确是 `trigger * 2` 与 `turn_list[: -keep * 2]`。
2. **摘要要「累积」不要「重算」**。新一轮压缩的输入是「旧摘要 + 新增待压回合」，不是全量历史；否则每一轮都在重读整段对话，成本随轮数线性涨。

摘要 prompt 明确要求"保留人物、地点、因果、未解决事项，丢掉寒暄与重复"，并要求把"资料未提及"这类结论也留下——否则用户追问两次同样的问题，模型会重新说一遍"没找到"。

#### 8.9.2 token 台账：三处细节决定数字对不对

`LLMClient.stream_events()` 新增 `usage_tag` 参数，非空时把本轮用量累加到对应行。真正麻烦的是三个细节：

| 细节 | 不做会怎样 | 做法 |
|---|---|---|
| 并发累加 | 读-改-写会丢数（同一会话两个请求同时结账） | SQL 侧原子累加：`SET prompt_tokens = prompt_tokens + :n`，不在 Python 里 `x = x + n` |
| 流式网关不吐 usage | 台账永远是 0 | 请求体带 `stream_options.include_usage`；网关不支持时（400/422）**降级重连一次**并记住 `_stream_usage_ok`，后续不再试 |
| 用量帧重复 | token 被算成 2–3 倍（实测 360 网关一个短回答推了 **3 帧** usage，`prompt_tokens` 直接 3 倍） | 只留最后一帧 `pending`，循环结束后记**一次**（改前 `2942 tok / 3 calls`，改后 `1465 / 1`） |

落账时机不能用 `finally` 里的 `await`（生成器被取消时会抛 `GeneratorExit` RuntimeError，与 §8.8.3 同款），必须走 `asyncio.create_task`。为此把「存回答 → 结 token 账 → 调度摘要」收进 `_persist_and_housekeep()`，三件事各自兜异常：任何一个失败都不该让另外两个连带丢。

会话列表接口顺带返回 `prompt_tokens` / `completion_tokens` / `llm_calls` / `summary_chars` / `summary_seq`，侧栏直接显示成 `2 条 | 8.6k tok | 摘要 | 1 分钟前`，让用户不必翻日志就知道这段对话花了多少。

#### 8.9.4 用量必须跟着 `done` 事件走（v1.15 补）

v1.14 把 token 记进了库，但前端只有侧栏那一个 11px 的小字，用户聊完一轮的第一反应
是"花多少了？"——视线在答案上，不在侧栏。更糟的是**翻遍界面也找不到**：
`done` 事件只回了字符数和耗时，没有任何消耗信息。

正确的做法不是"前端再查一次会话列表"，而是**让落账的那一端顺手把结果带回来**：

```
_persist_and_housekeep()  →  {"round": 本轮用量, "total": 会话累计}
        ↓
done 事件 usage 字段       →  前端直接渲染，不额外发请求
```

三个理由：

| 理由 | 说明 |
|---|---|
| 时序 | 会话列表是异步刷新的，`done` 到列表返回之间有窗口；这期间界面显示旧值，用户会以为"没记上" |
| 请求成本 | 每答一轮就多一次列表请求；`round` 本来就只在服务端内存里（`pop_usage` 取走就没了），不趁那时回传就永久丢失 |
| 语义 | `round`（这一轮）和 `total`（这个会话）是两个数。列表接口只能给 `total`，`round` 必须由生成链路自己产出 |

前端渲染分三种情况，缺一不可：

1. **刚答完**：`本轮 8.7k tok　入 7.5k · 出 1.2k ｜ 会话累计 8.7k tok`
2. **刷新/重开会话**：历史消息没有按条存 token（存了也没意义，无法再拆），所以只显示
   `会话累计 8.7k tok`。这行数据来自 `GET /chat/sessions/{id}/messages` 新增的 `usage` 字段——
   不给的话用户刷新一次就以为台账没了
3. **老会话**（该功能上线前产生的）：`total=0`，不渲染，不留一条"0 tok"的假账

侧栏那行 `2 条 | 8.7k tok | 刚刚` 保留，作为"这个对话总共花了多少"的常驻位；
同时给 `.sess-meta` 加 `flex-wrap`——四个字段在窄侧栏里一行放不下，不允许换行就会
被容器的 `overflow` 横向裁掉，而 token 那一格正好在中间，最先被切。

验收（`tools/shot_usage.cjs`，无头 Edge）：

| 项 | 结果 |
|---|---|
| 气泡用量条 | `.tok-bar` 出现，`本轮 8.7k tok 入 7.5k · 出 1.2k ｜ 会话累计 8.7k tok` |
| 侧栏累计 | `2 条 \| 8.7k tok \| 刚刚` |
| 刷新回放 | `.tok-bar` 仍在，文本变成 `会话累计 8.7k tok` |
| 控制台 | 0 error / 0 warning |

### 8.10 三项工程债（v1.16）

这一轮修的是"功能都在，但用起来别扭"的三处：答案不满意只能重发、会话多了翻不动、
图谱里同一个人的称谓占两个节点。

#### 8.10.1 重新生成：删掉上一轮，而不是再问一遍

最直觉的实现是"把同一个问题再发一次"。问题是历史会变成：

```
我：华佗是怎么死的
助手：……（第一版答案）
我：华佗是怎么死的     ← 同一个问题又问了一遍
助手：……（第二版答案）
```

下一轮提问时，模型看到"同一问题被问两次、答了两遍"，会以为自己上一版答错了
而过度自我修正，或者把两个答案揉在一起。所以 `regenerate=true` 的语义必须是
**先删掉上一轮，再按全新提问走一遍**。

三个位置必须对齐，错一个就出问题：

| 位置 | 为什么必须在这里删 |
|---|---|
| `rag.prepare()` **之前** | prepare 会读历史做实体消歧。先不删的话，要重答的这一轮会被当成"上文"塞进 prompt 和检索——等于让模型参考着自己上一版答案再答一遍 |
| 前端 `setChats(prev => prev.slice(0, idx))` | 界面上的旧答案要先消失，否则新旧两条会同时存在一会儿，用户以为没生效 |
| `drop_last_turn(expect=question)` | 校验"最后一轮确实是这个问题"。两个标签页同时操作、或点了重新生成又切了会话，都可能错位——那时**宁可不删**、退化成普通提问，也不能静默删掉用户另一段对话 |

实测（`scripts/verify_regenerate.py`）：

```
1) 首轮提问 → 消息 2 条，答案 1555 字
2) 重新生成 → 消息 2 条，答案 1701 字     ← 条数不变，内容变了
3) 问题不匹配的 regenerate → 消息 4 条     ← 安全退化成普通提问
```

#### 8.10.2 会话检索与导出

会话涨到十几个之后，侧栏一排"首句截断"的标题就没人能认出来。两处改动：

**搜索** (`GET /chat/sessions?q=`) 必须搜正文，不能只搜标题。标题是首句截断，
而用户记得的往往是"我问过 XX 那件事"，XX 可能出现在第三轮。实现是
`title ilike` OR `id in (select session_id from chat_messages where content ilike)`，
命中正文时额外返回 `hit` 片段：

- 片段取**最早的一条命中消息**；`role.desc()` 让 `user` 排在 `assistant` 前——
  "我问过什么"比"它答了什么"更能帮人认出这是哪个对话
- 片段只截关键词前后各 28 字，高亮交给前端做（后端不该关心怎么渲染）
- 前端 300ms 防抖：中文输入法下每次敲键都发请求，几乎全是废的

**导出** (`GET /chat/sessions/{id}/export`) 出 Markdown 而不是 JSON。用户导出对话是
为了**带走结论**（贴笔记、发给别人、存档），JSON 对他没用；Markdown 里引用章节号、
精排分、token 消耗都能顺手带上。文件名用 RFC 5987 的 `filename*=UTF-8''` 写法——
`filename=` 里直接塞中文，部分浏览器会把文件名变成乱码或截断。

实测：搜索"华佗" 7 条 → 4 条，4 条都带命中片段、5 处关键词高亮；导出 149 行，
头部带 `共 8 条消息 · 消耗 18611 tok（入 16020 / 出 2591）`。

#### 8.10.3 人工别名表：规则合不上的称谓怎么办

对齐层只有两条合并路径（同名、专名别名桥），而这两条都要求"别名本身是专名"。
实测《三国演义》卡在这里：

| 称谓 | 提及 | 该并到 | 为什么合不上 |
|---|---|---|---|
| `武侯` | 46 | 诸葛亮 | 封号（武乡侯的简称），被 `TITLE_SUFFIXES` 拦下 |
| `诸葛武侯` | 6 | 诸葛亮 | 同上，且没进过任何实体的别名表 |
| `献帝` | 40 | 汉献帝 | 是"汉献帝"的省略，没有任何别名桥 |
| `陈留王` | 24 | 汉献帝 | 刘协登基前的封号，字面上毫无关系 |

**163 次提及被切碎在图谱外**（诸葛亮 2432 旁边挂着 46+6，汉献帝 12 旁边挂着 40+24）。
这不是模型抽错了，是**规则天然覆盖不到**——要靠知识，靠不了模式。

解法是 `backend/data/graph_aliases.json` 人工表，两条通道分工：

| 通道 | 管什么 |
|---|---|
| 配置表（`aligner(manual=...)`） | **下次重建**时别再分裂 |
| `scripts/merge_entities.py` | 库里**已经**分裂的怎么办（重建图谱要几十分钟 LLM，为两条别名不值） |

人工通道有三条硬约束，都是踩出来的：

1. **跳过 `is_mergeable_alias`**。表里的词正是因为被判成封号才合不上的，
   再过一遍同样的闸门等于白写。
2. **规范名以人工表右边为准**，优先级高于 `canonical_score`。否则「献帝」（2 字 45 分）
   会压过「汉献帝」（封号结尾 5 分），合并后主名变成简称，越合越离谱。
3. **只认"只被指向、不被并入"的名字**。`甲→乙`、`乙→丙` 并存时，乙既是 value 又是 key，
   说明它只是中间态；取全部 value 会让规范名停在链条中间。

迁移脚本的四件事，漏一件数据就丢：mention 改指（撞唯一键时累加 count）、
关系改指（走 upsert，因为 `(novel_id, src_id, dst_id, relation)` 有唯一约束，
直接 UPDATE 会炸）、源名进别名表、`importance` 按全书重新归一化（它是 log 缩放的
**归一化**值，相加会溢出 1，前端节点大小直接失真）。

实测结果：

| 实体 | 合并前 | 合并后 |
|---|---|---|
| 诸葛亮 | 2432 提及，8 个别名 | **2484**，11 个别名（含武侯、诸葛武侯） |
| 汉献帝 | 12 提及，1 个别名 | **76**，4 个别名（含献帝、陈留王、伯和） |
| 实体总数 | 1211 | **1207** |

### 8.11 消息栏操作与正文排版（v1.17）

#### 8.11.1 三个"看着有、点着没反应"的图标

Semi 的 `Chat` 组件在 **不传回调时也会把操作按钮画出来**：复制 / 赞 / 踩 / 刷新 / 删除。
只传 `chats` 和 `onChatsChange`，五个图标一个不少，但点下去全是空转。用户分不清
"功能坏了"还是"根本没做"—— 这比不显示更糟。

| 图标 | 回调 | 落点 |
|---|---|---|
| 复制 | `onMessageCopy` | Semi 内置 `copy-text-to-clipboard` + toast，不用自己实现 |
| 赞 / 踩 | `onMessageGoodFeedback` / `onMessageBadFeedback` | `chat_messages.feedback`（`up` / `down` / 空） |
| 刷新 | `onMessageReset` | 复用已有的 `regenerate`，先删上一轮再重答 |
| 删除 | `onMessageDelete` | `DELETE /chat/messages/{id}` |

同时删掉了自己画的「⟳ 重新生成」文字按钮：图标行里已经有刷新图标，两个入口指向
同一个动作，只会让人怀疑它们行为不同。

#### 8.11.2 临时 id：假删除的真正成因

前端发送时用的是本地生成的占位 id（`a-<ts>-<rand>`），真正的 `cm_xxx` 由服务端在
落库时生成。于是拿界面上的 id 去调 `/chat/messages/{id}` 只会得到 **404**——
界面看起来删了（Semi 内部把消息从列表里摘了），库里什么都没发生。

v1.17 的解法是"答完再换"：`done` 事件带 `message_id`，前端把占位 id 换成真 id，
同时把 5 个以 id 为 key 的 Map（引用 / 用量 / 思考 / 检索 / 记忆）一起搬家。
这修好了 404，但换 id 的时机有副作用 —— 见 §8.12.2。v1.18 改成**开流前预建**
（`create_answer()` 先插一条空消息、id 随 `meta` 下发），`done` 里的 id 降级为兜底。

**代码上还有一个必踩的坑**（v1.17 遗留，v1.18 的兜底路径仍在用）：id 替换写在
`setChats(prev => ...)` 里，而 updater 是 React 渲染阶段才执行的——那时 `answerId`
早被赋值成新 id 了，`m.id === answerId` 一条都匹配不上，消息永远停在 `loading`
（表现为图标栏是灰的 `-hidden`、点赞删除全 404）。必须先把旧 id 存成常量再进 updater。

#### 8.11.3 删除的语义边界

`DELETE /chat/messages/{id}` 只删点中的那一条，**不连带删配对的另一条**：
垃圾桶就长在这条消息底下，用户的预期是"这个消失"。偷偷把上面的提问一起删掉，
反而制造了"我删的不是我点的那条"的意外。删空了会话（0 条消息）就连会话一起收掉，
不留"点进去什么都没有"的幽灵行。

#### 8.11.4 字号不一致：列表漏在了 Typography 外面

用户反馈"AI 回答的字比我的提问大"。但两边正文都由同一个 `MarkdownRender` 渲染，
`p` 的量出来是 **14px / 20px**，一模一样。真正的问题是列表：

| 元素 | 修复前 | 修复后 |
|---|---|---|
| `p` / `strong` | 14px / 20px（Semi 套了 Typography） | 14px / 20px |
| `ul` / `ol` / `li` | **16px / normal**（裸元素，继承 body） | **14px / 20px** |

用户提问通常是一行纯文本，看不出差异；AI 回答里大量用编号列表，那些 `li` 一律
16px，于是"回答整体比提问大一号"。

只补列表、不动 `.semi-markdownRender` 的 `font-size`：标题按 `em` 相对计算，
改基线会让所有标题一起缩水，而标题本来就该比正文大。回归检查见
`tools/probe_font.cjs`（断言 `p` 与 `li` 数值相等）。

### 8.12 流式正文为什么"看起来不流"（v1.18）

用户反馈"正文回答好像不是流式输出"。后端从第一天就是逐 `delta` 推的
（`curl -N` 能看到 40~90ms 一帧），所以问题一定在消费端。实测定位到两处，
都不是"没做流式"，而是**做完了但被别的东西挡住 / 打散**。

#### 8.12.1 `status:'loading'` 把正文整个藏起来

Semi 的 `ChatBoxContent` 只看一个字段决定渲染什么：

```js
if (status === MESSAGE_STATUS.LOADING) return <span className="…-content-loading" />;
// 否则才渲染 <MarkdownRender raw={content} />
```

我们发送时给占位消息挂 `status:'loading'`，然后**一直挂到整段结束**才改成
`complete`。于是这中间：`content` 在 state 里一帧帧累加，`setChats` 也在正常
触发重渲染，但 `status` 还是 `loading`，`ChatBoxContent` 每一步都只画那个转圈点，
把刚到的正文全部丢掉。等 `done` 一来才一次性铺出来 —— 用户看到的自然是
"憋半天、然后整篇砸下来"。

修法：**第一个 `delta` 到达就把 status 从 `loading` 切到 `incomplete`**。
选 `incomplete` 而不是 `complete`，是因为操作图标行用 `finished = status !== loading
&& status !== incomplete` 控制显隐 —— 用 `complete` 会让复制/赞踩/删除在生成过程中
就亮起来（此时正文还没写完，复制到的是半截）。`incomplete` 同时满足两件事：
内容渲染、图标仍隐藏。

> 诊断脚本：`tools/probe_stream.cjs`（每 150ms 采样正文 innerText 长度）。
> 修复前 1 次跳变、修复后 10~63 次渐进变化，平均 173~192ms 一次。
> 注意别拿"停止生成按钮消失"当结束信号，那个 class 随 Semi 版本变，很容易永远
> 为 false，采样在首帧就 break，看起来像"只有一次变化"，反而把真问题掩盖掉。

#### 8.12.2 末尾换 id 会让正文闪一下

`done` 里换 id（§8.11.2）本身是对的，但时机不对：Semi 用 `key={item.id}` 渲染
每一条消息，id 一变 React 就卸载重建那个气泡。以前这一下发生在 `done`，正好是
"答案已经铺满一屏"的时刻 —— 重建后先空一帧再出现，肉眼就是**答完闪一下**。

v1.18 把 id 提前到 `meta`：

```
gen() 开头： save_question() → create_answer()（插一条空回答，拿到 cm_xxx）
meta 事件： 带 message_id
前端 meta 分支：换 id（此刻正文 0 字，重建也看不见）
done 事件： 同一个 message_id（兜底，正常情况前端直接跳过）
```

后端配套：`create_answer()` 预建、`fill_answer()` 回填。空回答（异常 / 客户端
一进来就断开）由 `fill_answer(mid, "")` **删掉空壳** —— 留着会在回放里变成一个
空气泡，还会让摘要按"多了一轮回答"去配对。`save_answer()` 保留为两者的组合版，
给 `save_turn()`（测试与离线补录）用。

回归见 `backend/scripts/verify_stream.py`：断言 meta 带 id、delta 多帧、
done 与 meta 的 id 一致、库里能查到、拿 meta 的 id 直接打反馈返 200。

#### 8.12.3 剩下的等待不是"没流"，是链路本来就慢

修完上面两条后实测一次提问的时间轴（`tools/probe_stream2.cjs`，把 SSE 事件和
DOM 上屏放在同一条时间轴上）：

| 阶段 | 实测 | 说明 |
|---|---|---|
| 点击 → `meta` | **1.8s ~ 93s** | 检索 + 精排，见下方 |
| `meta` → 首思考 | 1.6s | |
| 思考 | 10 ~ 110s | 上游推理模型行为，面板在滚字，不算卡死 |
| 思考末帧 → 正文首帧 | **82ms** | 连续，没有空白期 |
| 正文 | 85 帧 / 43ms 一帧 / 4.7s | 真流式 |
| DOM 上屏 | 173~192ms 一次 | 跟得上，MDX 编译不是瓶颈 |

`meta` 之前的 60~90 秒是**检索**，其中几乎全部是本地 cross-encoder 精排
（`bge-reranker-base`，50 条 × 512 token，CPU 单次 64~76s）。分段数据见
`backend/scripts/profile_retrieval.py`：embed 0.7s、pgvector 0.45s、词法 0.02s、
精排 64s。这一段是下一步要处理的重点，和流式本身无关。

## 9. 性能优化点

### 9.1 写入侧

| 优化点 | 手段 | 预期收益 |
|---|---|---|
| Embedding 批量 | 批 16（CPU，实测最优），长度分桶（同长度一起跑，减少 padding 浪费） | 吞吐 ↑ 2-3× |
| 长度分桶而非整批 | 128 条整批会 pad 到批内最长，短块白算 | 实测比不分桶快约 15% |
| PG 批量 upsert | 一批 16-64 条走一次 `executemany`，`INSERT … ON CONFLICT (chunk_id) DO UPDATE`；不逐条提交 | 写入 ↑ 10× |
| 章节级并行 | worker 内 `asyncio.gather` 处理多章；embedder 内部 8 线程 | 受 CPU 上限约束，100 万字约 18-20 min |
| 词法索引分离 | 切片落库后立即重建 `chunk_lexical`，不等向量 | 词法通道先可用；Embedding 失败也能检索 |
| 分批提交词法 | 2000 条一批 commit，避免长时间握写锁堵住 progress 更新 | 入库与检索互不阻塞 |
| LLM 章节抽取 | 4 并发 + JSON 模式 + 短章合并 + 失败不重试同一 prompt | 抽取阶段 40min → 约 15min（无缓存前提） |
| 图谱批量写 | 实体一批 `INSERT`，关系一批 `INSERT … ON CONFLICT DO NOTHING`；单书 551 块约 1600 条边 < 1s | 6k 边 < 3s |
| 跳过重复计算 | `chunk_id` 已存在且向量齐全则跳过 embedding | 增量重跑只处理变更块 |

### 9.2 检索侧

| 优化点 | 手段 | 预期收益 |
|---|---|---|
| 过滤下推 | 检索必带 `WHERE novel_id = ?`，`novel_id` 单列索引 | 候选集从全库降到单书 |
| 过滤召回补偿 | `SET LOCAL hnsw.iterative_scan = relaxed_order` | 避免"过滤后召回条数不足"，是**正确性问题**而非性能问题 |
| 索引参数 | HNSW `m=16 / ef_construction=64`，查询 `ef_search=100` | 10 万级 P95 < 100ms；M 调大只增内存，收益递减 |
| 只索引 child | parent/summary 不进 `chunk_vectors`（词法侧同样只索引 `level=1`） | 索引规模 ↓ 3×，召回反而更准 |
| Query 改写缓存 | 相同问题（含历史 hash）结果缓存 1h | 重复提问 0 成本 |
| Rerank 限流 | 只对 top 50 重排，`rerank_top_n=24`，CPU 8 线程批 16 | 80ms 内完成 |
| 并行召回 | 稠密与词法用 `asyncio.gather` 并发（两条独立 SQL/连接） | 延迟取 max 而非 sum |
| 结果去重 | 同一 parent 下多个 child 只保留最高分 | 上下文不重复，token ↓ 30% |
| 单连接池复用 | asyncpg 池 8（运行）/ 16（溢出），不每次新建连接 | 省掉三次握手，检索少 2-5ms |

### 9.3 生成侧（成本）

| 优化点 | 手段 | 收益 |
|---|---|---|
| 上下文预算 | 检索 ≤8K、图谱 ≤40 条、历史 ≤6 轮；固定前缀保持字节稳定 | 输入 token 可控，成本可预测（不依赖上游缓存） |
| 上下文预算 | child 8 条 → parent 4 个（每个 ≤1400 token），总计 ≤ 8K | 单次问答成本可控 |
| 快慢模型分工 | 改写/摘要用 flash，仅抽取用 pro | 综合成本 ↓ 60% |
| 历史压缩 | 超过 6 轮的对话压成 200 字摘要 | 长会话不爆 token |
| 语义缓存 | 问题向量相似度 > 0.95 且同书 → 复用答案（可配置关闭） | 高频问题 0 成本 |

### 9.4 该做的实验：三档检索的实测对比

> v1.0–v1.5 这里写的是"内置 BM25 vs 客户端学习型稀疏"——那套 A/B 随 Milvus 下线已经失去意义。现在的对比项是三档召回链路：

| 链路 | 说明 | 长夜将明（144 块 / 25 题）Recall@10 | p50 | p95 |
|---|---|---|---|---|
| `dense` | 仅 HNSW | 0.920 | — | — |
| `rrf` | 稠密 + 词法 + RRF(k=60)，无精排 | 0.960 | 485ms | 586ms |
| `hybrid` | 双路 + RRF + cross-encoder | 0.960 | 442ms | 524ms |

跑法：`make eval NOVEL=nv_xxx BUILD=30 MODES=dense,rrf,hybrid`。

结论要谨慎读：这本样本书是**机器生成的句式重复文本**，稠密通道本来就接近天花板，所以提升只有 +4pt、精排也没体现增量。延迟数据还被当时并发的向量化任务污染（8 核被占满），需要空载重测。真正能验证 P1-2 指标（+8pt）的是《赘婿》这类 21,552 块的真实长篇。

**仍然值得做的 A/B**：`ef_search` 取 40 / 100 / 200 三档，看召回与延迟的拐点在哪。这是 pgvector 最直接的一组调参，且随数据量增长会漂移，建议每翻 10 倍数据量复测一次。

### 9.5 容量与扩展估算

| 规模 | chunks | PG 中向量数据（1024d fp32） | HNSW 索引 | 图谱表 |
|---|---|---|---|---|
| 1 部 100 万字 | 4,000 | ≈ 16 MB | ≈ 20 MB | ≈ 3 MB |
| 50 部 | 200,000 | ≈ 800 MB | ≈ 1 GB | ≈ 150 MB |
| 500 部 | 2,000,000 | ≈ 8 GB | ≈ 10 GB | 8 GB |

> 千万级（>2M chunk）时 HNSW 的内存占用会成为瓶颈：可改用 `halfvec`（fp16，体积减半、召回损失很小），或把 `m` 降到 8、把历史书迁到独立表只保留热数据。真要上到亿级再考虑独立向量库——那时候"跨库一致性"的代价才值得用分片和补偿逻辑去换。
>
> **图谱三张表实测占比极小**：《长夜将明》192 块 → 87 实体 / 164 关系 / 696 提及，三表合计不到 1 MB；《三国演义》551 块量级下也在个位数 MB。图谱的存储成本可以忽略，真正的成本在 LLM 调用（见 §9.3）。

## 10. 可扩展预留设计

### 10.1 存储层：本地 → 对象存储（要求 6）

**接口先行的具体落地**：

```python
# adapters/storage/local.py
class LocalStorage:
    def __init__(self, root: Path): self.root = root
    def key_for(self, novel_id: str, filename: str) -> str:
        return f"raw/{novel_id}/{filename}"
    async def put(self, key, data, content_type="text/plain") -> str:
        path = self.root / key; path.parent.mkdir(parents=True, exist_ok=True)
        await anyio.to_thread.run_sync(lambda: path.write_bytes(data.read()))
        return key
    async def presigned_url(self, key, expires=3600): return None

# adapters/storage/s3.py
class S3Storage:
    def __init__(self, endpoint, bucket, ak, sk):
        self.client = boto3.client("s3", endpoint_url=endpoint,
                                   aws_access_key_id=ak, aws_secret_access_key=sk)
    async def put(self, key, data, content_type="text/plain") -> str:
        await anyio.to_thread.run_sync(
            lambda: self.client.upload_fileobj(data, self.bucket, key,
                                               ExtraArgs={"ContentType": content_type}))
        return key
    async def presigned_url(self, key, expires=3600) -> str:
        return self.client.generate_presigned_url("get_object",
            Params={"Bucket": self.bucket, "Key": key}, ExpiresIn=expires)
```

**三条必须遵守的纪律**（否则迁移时会返工）：

1. 数据库只存 **key**（`raw/{novel_id}/{filename}`），**绝不存绝对路径或 URL**
2. 前端下载统一走 `GET /api/v1/files/{key}`（后端 302 到预签名 URL），不直连存储
3. 存储实现里**不允许出现 `Path` 拼接业务逻辑**，路径规则只在 `key_for()` 里

**迁移路径**：改 `STORAGE_BACKEND=s3` → 写一个 `scripts/migrate_storage.py`（按 PG 里的 key 列表批量 `put`）→ 校验 sha256 一致 → 切流量。全程业务代码零改动。

**PG 侧的额外预留（加分项）**：
- **原生分区表**：`chunks` 与 `chunk_vectors` 可按 `novel_id` 的 hash 分区（`PARTITION BY HASH`），归档老书时 `DETACH PARTITION` 即完成冷热分离，不需要一条条删。
- **`halfvec`**：pgvector 0.7+ 提供 fp16 向量类型，体积减半、召回损失通常 <1%，是千万级规模时最省事的扩容手段（代价是重建列类型与索引）。
- **外部数据可查**：PG 的 `file_fdw` / `postgres_fdw` 能直接读外部表，历史书归档成 Parquet 之后仍可通过 FDW 挂回来做"冷数据可查"，不必重灌向量。

### 10.2 服务拆分预留

| 触发条件 | 拆分动作 | 成本 |
|---|---|---|
| 检索 P95 > 500ms 或需独立扩缩 | `retrieval-service` 独立部署，暴露 gRPC/HTTP | 低（接口已在 §7.3） |
| 图谱抽取排队 > 30min | 拆独立进程跑 graph worker（`asyncio` 队列 → 独立 consumer） | 低 |
| 多租户 | 加 `tenant_id` 字段 + 向量/词法/图谱表跟随分区 | 中（需数据迁移） |
| 多模态（封面/插图） | 新增 `chunk_images` 表 + 视觉编码器，`modality` 字段分流 | 中 |
| 多语言 | `EmbeddingProvider` 换 multilingual 模型 + `lang` 字段过滤 | 低 |

### 10.3 模型可替换

`manifest` 里记录 `embedding_model` / `embedding_version`。换模型的正确姿势：

1. 新 collection `novel_chunks_v2`（新维度/新索引），旧 collection 保持在线
2. 后台任务按书重建，双写期间查询走旧库
3. 灰度：按 `novel_id % 10` 分流到新库，对比 Recall
4. 全量切换后删旧 collection

**禁止**在同一个 collection 里混不同模型的向量——维度相同也不行，分布不同会让 ANN 结果崩坏，且这种 bug 极难排查。

### 10.4 图谱能力扩展

- **算法层**：社区发现（人物派系自动聚类）、PageRank（人物重要性）、最短路径（"两人如何认识"）。PG 侧用迭代 SQL 也能写，但代码量不小；真到必须做的时候，把这个模块单独抽出去接图算法库，而不是为了它把整个图谱搬到一个新数据库
- **Schema 扩展**：`relation` 用字符串而非枚举类型，新增关系类型只改配置 `graph_relation_vocab.yaml`
- **增量抽取**：新增章节时只抽新章，`MERGE` 天然合并；实体属性用 `ON MATCH` 保留首次出现的描述

### 10.5 接口版本化

- URL 前缀 `/api/v1`，破坏性变更升 `/api/v2`，v1 保留 6 个月
- SSE 事件类型只增不改（前端用 `switch` 默认分支忽略未知事件），保证前后端可独立发布

### 11.4 评测集怎么做（别跳过）

- **规模**：100 条，覆盖 6 类问题：事实型（谁是谁）、时序型（第几章发生）、关系型（两人什么关系）、总结型（这一卷讲了什么）、比较型（A 和 B 谁更强）、不可答型（书中没有，应回答"未提及"）
- **标注**：每条标注标准答案 + 应命中的 `chunk_id` 列表
- **指标**：Recall@10（检索）、答案准确率（人工 1-5 分）、引用正确率（引用段落真的支撑结论）、拒答准确率（不可答型）
- **不可答型必须占 10%**——这是检验幻觉的唯一有效手段，很多项目栽在这

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| 目标库没装 pgvector（`CREATE EXTENSION` 报 control file 不存在） | 完全跑不起来 | 中 | 启动时查 `pg_extension`，缺失即抛带安装指引的 `RuntimeError`；Docker 用 `pgvector/pgvector:pg18`（§3.2） |
| pgvector 版本 < 0.8（无 `iterative_scan`） | 带过滤检索召回不足，且**不报错** | 中 | 启动校验版本号；见 §8.5.1④ |
| HNSW 索引没建（懒建机制） | 检索退化为全表扫描，随数据量线性变慢 | **高** | `/health` 里暴露 `index` 字段；迁移后按 §6.2 检查 `pg_indexes` |
| Embedding 模型换档但没重建向量表 | 维度不匹配，写入直接失败或召回全错 | 中 | `ensure_ready()` 校验列维度，不一致即拒启并给出 `ALTER TABLE` 指引 |
| 单机 PG 无备份 | 数据全丢 | 低 | 每日 `pg_dump`（业务库仅几十 MB）；向量可重建，正文不可，所以备份优先级是正文 > 元数据 > 向量 |
| LLM 抽取幻觉（编造关系） | 图谱污染，问答胡说 | 高 | 三道闸门（置信度/证据回查/枚举校验）+ 人工审核队列 |
| 同一人物多称谓导致图谱碎裂 | 关系查询不准 | 高 | 别名对齐三件套；管理台提供"合并实体" |
| 章节切分错误（无章节号的长文） | 时序检索失效 | 中 | 多级兜底正则 + 长度约束二次切；管理台支持手动修章节边界 |
| 360 网关限流 / 超时 / 配额不透明 | 抽取中断、问答失败 | **高** | 信号量 4 + 429 指数退避 + 抽取失败转规则抽取；`/health` 暴露能力探测；保留 DeepSeek 备份通道（改 `LLM_BASE_URL` 即切） |
| 中文 token 估算偏差 | 切块超长被截断 | 中 | 用真实 tokenizer 计数，不拍脑袋 |
| 前端大图卡死 | 可视化不可用 | 中 | 后端强制 `limit`（`GRAPH_SUBGRAPH_MAX_NODES=200` / `MAX_EDGES=400`），超限返回 `truncated=true` 提示缩小范围；前端默认 2 跳、按 `importance` 取骨架，不在首屏画全书 |
| 成本超预算 | 项目停滞 | 中 | 上下文预算 + 短章合并 + 语义缓存；管理台按场景出 token 与费用报表 |

### 14.3 一句话总结这套架构的判断依据

- **写入异步、查询同步**：长任务绝不阻塞请求，但用户能实时看到进度（SSE）
- **三份标识贯穿全链路**（`novel_id` / `chunk_id` / `chapter_no`）：这是向量、词法、图谱能互相对上的唯一原因
- **单库优先**：能用外键约束住的，就不靠应用层补偿；图谱也遵守这条，不为例
- **父子块 + 混合检索 + rerank**：这三件事决定了问答质量的下限，不该省
- **接口先行**：存储、模型、检索器全部走 Protocol，才敢说"可扩展"
- **指标先行**：没有评测集，"优化"就是玄学

三个要点值得单独记：

1. **临时 id 是"假删除"的唯一成因**。`a-<ts>-<rand>` 只活在界面里，服务端的 `cm_xxx`
   在落库时才生成。Semi 的 `deleteMessage` 会先把消息从自己的列表摘掉再回调，
   所以界面立刻"删掉了"，库里纹丝不动——看起来像删除成功。
2. **updater 里不能直接读被改写的变量**。`setChats(prev => prev.map(m => m.id === answerId ? …))`
   里的 `answerId` 在 React 执行 updater 时早已被赋成新 id，一条都匹配不上，
   消息会永远停在 `loading`（图标栏 `-hidden`、后续操作全 404）。
3. **同一动作只留一个入口**。文字按钮和图标指向同一个 `regenerate`，并存只会让人
   怀疑它们行为不同；`regenerate` 的 `cut` 计算也顺势兜住 Semi 的 `resetMessage`
   先把最后一条换成 loading 占位（换了新 id）这个前置动作。

实测：图标 5 个、点赞落库 `assistant:up`、刷新后图标仍亮（`aria-label="like_thumb"`）、
点踩自动取消赞（0/1）、重新生成 2→2 条、删除 2→1 条、侧栏删会话 10→9 且消息归零；
字号 `p` / `li` 均 14px / 20px；控制台 0 error 0 warning；`59 passed`。
