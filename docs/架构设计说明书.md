## 0. 关键前置结论（先看这 4 条）

**① 设置 `MILVUS_URI` 为 Milvus 实例的 URL和端口。**

因此设计上必须拆成两个参数：

```bash
# 真实形态（示例，需替换为你的实例地址）
MILVUS_URI=https://in03-xxxxxxxxxxxx.serverless.<region>.cloud.zilliz.com:443
MILVUS_TOKEN=a0fb14319c198a0c1ff0de82cc96108c3123122efad912a903c8f83b1d9b526d755fc360699499c5458b660b1a7808ebd478704e
```

自建集群则是 `MILVUS_URI=http://10.0.0.8:19530`，`MILVUS_TOKEN` 留空。
配置加载层做**格式兜底**：若 `MILVUS_URI` 中不含 `://`，则判定为 Token，自动与 `MILVUS_ENDPOINT` 组合，并在启动自检里显式报错提示，避免上线后才发现连不上。

**② Milvus 3.0 不只是"版本号变大"，它改变了我们的写入与检索分工。**
3.0（2026-07 发布，Lake-Native）带来三项对本项目直接生效的能力，架构据此优化：

- **内置 BM25 + 新稀疏索引**：可在服务端从文本列生成 BM25 稀疏向量，混合检索不再需要客户端跑 BM25 编码器，稀疏索引体积约为 2.6 版的 1/3
- **SINDI**：面向学习型稀疏（BGE-M3 / SPLADE 的 lexical weights）的检索算法，已成为稀疏内积的默认算法
- **服务端 ORDER BY / 聚合 / faceted search**：管理台的统计面板、时间线排序可以下推到引擎，省掉"取回全量再算"的开销

**③ 大模型换成 360 网关的 `z-ai/glm-5`，协议是 OpenAI Chat Completions，不是任何厂商私有协议。**
这一条决定了整个 LLM 层的写法，三个推论：

- **代码里不出现任何厂商专有 SDK**。统一用 `openai` 官方 SDK + `base_url` 覆盖，`LLMClient` 是唯一出口。将来换回 DeepSeek（`https://api.deepseek.com`）或换任何兼容网关，只改 `.env` 三个变量，零代码改动——这同时满足了原需求"集成 DeepSeek"的可持续性
- **不能假设上游有 prompt 前缀缓存**。DeepSeek 的自动上下文缓存能让固定前缀只收 1/10 价格，第三方网关不一定提供。所以成本控制从"依赖缓存"改为"自己控上下文预算 + 启动时探测一次缓存能力"（见 §9.3）
- **能力必须探测，不能按文档假设**。`z-ai/glm-5` 的实际上下文窗口、是否支持 `response_format={"type":"json_object"}`、是否支持 `stream`、并发上限，全部以网关实测为准。启动时跑一次 `capabilities_probe()`，把结果写入缓存并暴露在 `/health/deps`；JSON 模式不可用则降级为"提示词约束 + 正则修复 JSON"

> 一个必须提前知道的坑：第三方网关的**模型名是带前缀的**（`z-ai/glm-5`），而 OpenAI 兼容层常见的 `model` 校验错误（400 model not found）多是漏了前缀或用了官方名。配置里禁止硬编码模型名，一律读 `LLM_MODEL`。

**④ 切片过程必须"可看见"。**
长文本切块是最容易出问题、也最难解释的一步（字数对不上、章节切错、块被截断）。所以切片阶段不是"后台黑盒"，而是产出一份**完成度档案**：按章进度、块数、token 分布、超长/过短块告警、抽样预览。前端在任务运行时就能看到，跑完还能复核。设计见 §8.3.2。

## 1. 设计目标与约束

### 1.1 业务目标

把一部（或多部）几十万到数百万字的小说，变成三个东西：

1. **可语义检索的向量库**——读者问"主角第一次见到师父是哪一章"，能召回正确段落
2. **可结构化推理的知识图谱**——能回答"谁和谁是什么关系""这个势力有哪些人"，并能可视化
3. **可对话的问答入口**——基于上面两者 + 大模型（`z-ai/glm-5`）生成带引用的答案

### 1.2 非功能性指标（验收基线）

| 维度 | 指标 | 说明 |
|---|---|---|
| 单部小说处理时延 | 100 万字 ≤ **30 min**（P90） | 实测 P0 无图谱：112.7 万字 10.6 min |
| 向量写入吞吐 | ≥ **500 chunks/s** | 批量 500 条/请求，Milvus 侧 |
| 检索延迟 | P95 ≤ **300 ms** | 混合检索 + rerank，不含 LLM |
| 问答首字延迟 | P95 ≤ **2 s** | SSE 首 token |
| 问答完整响应 | P95 ≤ **15 s** | 答案 500 字左右 |
| 检索准确率 | Recall@10 ≥ **0.85** | 自建 100 条标注评测集 |
| 图谱抽取准确率 | 实体 P ≥ **0.85**，关系 P ≥ **0.75** | 抽样人工核验 200 条 |
| 并发能力 | 20 QPS 问答（不排队） | 单机 4C8G + 外部 LLM |
| 数据隔离 | 多小说互不串味 | 所有查询强制带 `novel_id` |
| 幂等性 | 管道可重跑不产生重复数据 | 唯一键 + Upsert |

### 1.3 硬约束

- 向量库为**线上托管 Milvus 3.0.x**，不可本地起 2.x 兼容降级；网络出网需白名单
- 图数据库为 Neo4j，**必须建模实体/关系/属性**，不能只把三元组塞进向量库
- 原始文件初期落本地文件夹，**但存储层必须可切对象存储**（接口先行）
- 大模型走第三方 OpenAI 兼容网关（360 / `z-ai/glm-5`），存在限流与并发上限，**且不能假设有 prompt 缓存** → 必须自己做上下文预算、批量、降级
- Python 依赖统一 `uv` 管理（`uv.lock` 锁定），前端统一 `pnpm` 管理（`pnpm-lock.yaml` 锁定），**禁止混用 pip/npm**
- Embedding 必须本地可跑（无 GPU 也要能出结果），不能把向量化绑在外部 API 的可用性上
- 切片阶段必须产出可查看的完成度（按章进度、块统计、异常块告警）

### 2.2 为什么是"模块化单体 + 独立 Worker"，而不是一上来就微服务

一期（≤10 万级 chunk、单租户）用微服务会带来 5 个额外运维面，收益为零。设计取**模块化单体**：

- `api`：FastAPI 单进程，内部按 `services/` 分包，包间只通过接口调用，不互相 import 实现
- `worker-ingest`：Celery worker，跑解析/切分/向量化
- `worker-graph`：Celery worker，跑 LLM 抽取（IO 密集，独立扩缩）
- `web`：静态站

拆服务的**触发条件**写死在下文 §10.2：检索 P95 > 500ms 或需独立扩缩时，才把 `retrieval` 拆成独立服务——因为届时它已经有清晰的接口边界（§7.3），拆的成本接近零。

### 2.3 Embedding 的落地方式（关键决策）

```
小说 chunk ──► BGE-M3（一次前向） ──┬──► dense_vector  (1024, FLOAT_VECTOR)
                                    └──► sparse_vector (lexical weights, SPARSE_FLOAT_VECTOR)
```

- **一次编码产出双向量**，混合检索的两个召回通道共用一次推理，避免两次模型调用
- **模型分档，按硬件自动选**（本地部署的关键）：

| 场景 | 模型 | 维度 | CPU 吞吐（实测） | 说明 |
|---|---|---|---|---|
| 有 GPU / 追求质量 | `BAAI/bge-m3` | 1024 | GPU 200-400 chunk/s | 稠密 + 稀疏一次出，混合检索最佳 |
| **无 GPU（当前默认）** | `BAAI/bge-large-zh-v1.5` + int8 ONNX | **1024** | CPU **8 线程实测 2.3-2.9 chunk/s**（311 字块均 374 token） | 326MB 量化权重（fp32 为 1.3GB）；无稀疏输出，稀疏通道由 Milvus 服务端 BM25 承担 |
| 低配机器 | `BAAI/bge-small-zh-v1.5` | 512 | CPU 4 线程实测 6.7 chunk/s | 112.7 万字全流程 638.8s；内存紧（可用 <2GB）时回退到这一档 |

> 这是 v1.1 相对 v1.0 的实质性调整：**本地 Embedding 不承诺一定有 GPU**，所以"稠密由本地模型出、稀疏由 Milvus 服务端 BM25 出"必须成为一条正当路径，而不是降级方案。各档位共用同一个 `LocalEmbeddingProvider`，只改 `EMBEDDING_MODEL` / `EMBEDDING_MS_REPO` / `EMBEDDING_ONNX_FILE` / `EMBEDDING_DIM`，代码零改动。
>
> **v1.2 提升到 1024 维的实测代价**：bge-large 是 bge-small 的 13 倍参数量，即便 int8 量化后 CPU 吞吐也从 6.7 降到 2.3-2.9 chunk/s。同一本 112 万字的书，入库时间从 10.6 min 涨到约 18-20 min（估算，按 1100 字/秒）。这是"维度翻倍"的真实成本，不是配置没生效。

- 归一化后使用 `COSINE`（等价于 IP），省掉检索时的模长计算
- 批大小：GPU 32 / CPU 16；CPU 下 `onnxruntime` 的 `intra_op_num_threads` 钉死到配置值（`EMBEDDING_THREADS`），`inter_op` 固定 1
- **按长度分桶**：一次把 128 条交给编码器会 pad 到批内最长，短块白算；实测直接整批比按 16 条分桶慢约 15%。`_encode()` 内部先按字符数排序再切桶
- **批大小不是越大越好**：实测 bge-large int8 在可用内存 3.4GB 的机器上，16 条 2.33 块/s、32 条 1.71 块/s、64 条直接崩到 0.2 块/s（激活内存撑爆开始 swap）。内存是这一档的硬约束
- **首启下载**：模型从 HF 镜像（`HF_ENDPOINT=https://hf-mirror.com`）拉到 `~/.cache/huggingface`，离线环境可预置目录并设 `HF_HUB_OFFLINE=1`；下载进度也推到前端（与切片完成度同一套 SSE 通道）
- **降级路径**：模型加载失败时，自动切 `hash` 伪向量（仅用于跑通链路与单测），响应标 `embedding_mode=hash`，管理台显式红色告警——**不允许静默降级**

> 备选方案：完全使用 Milvus 3.0 服务端 BM25（不产出 sparse_vector）。两者取舍见 §9.4，建议**先双写做过对比**，再决定是否关掉客户端稀疏。

### 2.4 大模型用途分工（只有一个模型时的现实做法）

网关只给了 `z-ai/glm-5` 一个型号，所以不做"快慢模型分工"，改做**同模型不同参数档**：

| 场景 | 温度 | `max_tokens` | 并发 | 说明 |
|---|---|---|---|---|
| 章节摘要 | 0.3 | 400 | 4 | 150-200 字，批量跑 |
| 实体/关系抽取 | **0** | 3000 | 2 | JSON 严格输出，一章一次；并发压低是因为单请求最重 |
| 实体对齐仲裁 | 0 | 200 | 4 | 只输入"疑似同一人"的候选对，极短 |
| Query 改写/指代消解 | 0 | 150 | 8 | 50 字内输出，最频繁 |
| 最终答案生成 | 0.6 | 1000 | 8 | 流式，用户直接感知 |

**必须保留 `LLM_MODEL_FAST` 这个空位**：一旦网关开放轻量型号（或改回 DeepSeek 的 flash 档），把改写/摘要/对齐三个场景搬过去，成本能降一个数量级，而这只需要改环境变量——因为代码里只有 `model` 一个参数在变。

**限流与失败处理**（第三方网关的配额通常不透明，必须假设它随时会 429）：

```
请求 → 信号量(LLM_MAX_CONCURRENCY=4) → 429/5xx?
        → 指数退避 1s/3s/9s + 抖动，最多 3 次
        → 仍失败：抽取降级为规则抽取（标记 low_confidence）
                  问答降级为"返回检索原文摘要 + 提示稍后重试"
```

**成本控制（v1.1 的关键变化）**：不能依赖上游 prompt 缓存，改为三条自己做的手段：
1. **上下文预算硬约束**：检索上下文 ≤ 8K token、图谱事实 ≤ 40 条、历史 ≤ 6 轮（超出压成 200 字摘要）
2. **抽取批次合并**：短章节（< 1500 字）两章合并一次请求，减少请求数与重复的 schema 开销
3. **计量留痕**：每次调用记录 `prompt_tokens / completion_tokens / latency / scene`，管理台按场景出成本报表——没有这张表，成本一定失控

### 2.5 工程化：uv + pnpm 的落地规范

**项目根布局**

```
jiansuoandzhishitupi/
├── backend/
│   ├── pyproject.toml          # 唯一依赖声明源
│   ├── uv.lock                 # 必须提交，全量锁定
│   ├── .python-version         # 3.11
│   └── app/
├── frontend/
│   ├── package.json            # 含 "packageManager": "pnpm@9.x"
│   ├── pnpm-lock.yaml          # 必须提交
│   └── src/
├── Makefile                    # 统一入口，避免成员记两套命令
└── .env.example
```

**uv 使用规范**

| 场景 | 命令 | 说明 |
|---|---|---|
| 首次安装 | `cd backend && uv sync` | 自动建 `.venv` 并按 `uv.lock` 精确安装，不需要 `activate` |
| 加依赖 | `uv add fastapi pymilvus` | 自动写 `pyproject.toml` + 更新锁 |
| 加开发依赖 | `uv add --dev pytest ruff mypy` | 进 `dev` 依赖组，不进生产镜像 |
| 运行 | `uv run uvicorn app.main:app --reload` | 自动用项目 venv，无需激活 |
| 跑测试 | `uv run pytest -q` | CI 同款命令 |

### 3.2 部署拓扑（一期单机）

| 容器 | 镜像 | 端口 | 资源建议 |

| `postgres` | postgres:16 | 5432 | 1C / 1G |

| 外部 | Milvus 3.0 云实例、Neo4j 5.x、360 网关 | — | 按量 |

**Embedding 不单独起容器（v1.1 变更）**：无 GPU 时 bge-large（int8）在 8 线程 CPU 上实测 2.3-2.9 chunk/s，进程内调用省掉一次 HTTP 往返和一层运维。吞吐随序列长度非线性下降，且受**可用内存**强约束——模型 326MB 之外，激活内存随 batch×seq 线性增长，超出可用内存会直接掉到 swap，吞吐断崖（实测 16 条 2.33 块/s → 64 条 0.2 块/s）。所以块大小、批大小既是质量参数、也是成本参数。阶段划分：

| 阶段 | 部署形态 | 说明 |
|---|---|---|
| 一期（无 GPU） | **进程内**，`worker-ingest` 直接加载模型 | 单进程内存 +300MB；启动时预加载，避免首个请求等 20s |
| 二期（有 GPU） | 可选升级为 TEI 独立容器 | 多 worker 共享一份模型显存，改 `EMBEDDING_PROVIDER=tei` 即可，接口不变 |

> Neo4j 一期可跟 api 同机部署 Community 版；图规模超过 500 万边或需读写分离时，换 Enterprise / Aura。

### 3.3 双管道设计（核心思想）

**写入侧与查询侧完全解耦**：写入是异步、可重跑、幂等；查询是同步、低延迟、可降级。二者唯一的契约是**三份共享标识**：

- `novel_id`：全书隔离键（Milvus partition key + Neo4j 属性 + 关系库主键）
- `chunk_id`：`{novel_id}:{chapter_no}:{seq}`，向量库主键，图谱证据反查的锚点
- `chapter_no`：时序轴，图谱与向量共用的时间线

这使得"向量化失败但图谱成功"这种中间态可以被独立重试，不需要整本重跑。

## 5. 数据流转链路

### 5.1 全链路数据形态演进

| 阶段 | 数据形态 | 体量（100 万字参考） | 存储位置 |
|---|---|---|---|
| L0 原始 | `.txt` / `.epub` / `.docx` | 3 MB | 本地 `data/raw/{novel_id}/`（可切 S3） |
| L1 规范化 | UTF-8 纯文本 + 章节索引 | 3 MB | `data/parsed/{novel_id}.jsonl` |
| L2 块 | child 400 tokens / parent 1400 tokens | ≈ 4,000 child + 1,200 parent | 关系库 `chunks`（正文可只存偏移） |
| L3 向量 | dense 1024 float32 + sparse | 4,000 × 4KB ≈ 16 MB | Milvus |
| L4 图 | 实体 ≈ 1,500 / 关系 ≈ 6,000 | 边 6k | Neo4j |
| L5 摘要 | 章摘要 200 × 150 字 | 60 KB | 关系库 + 向量库（level=3） |

### 5.2 数据一致性策略

- **单一事实源（SoT）**：正文与章节结构以关系库 + 解析产物为准；Milvus/Neo4j 都是**可重建的派生索引**
- 每部书记录 `manifest`：`{parse_version, chunk_version, embedding_model, graph_schema_version}`，任一版本变化触发"标记为 stale → 后台重建"，不做实时双写
- 删除书：先软删关系库 → 异步清 Milvus partition（`delete(filter=novel_id==..)`）→ 异步清 Neo4j（`MATCH (n {novel_id:$id}) DETACH DELETE n` 分批）→ 最后删文件
- 向量写入使用 `upsert`（主键为 `chunk_id`），重跑天然幂等；图谱使用 `MERGE` + 唯一约束，重跑不产生重边

### 5.3 失败与重试模型

| 失败点 | 策略 | 兜底 |
|---|---|---|
| Embedding 服务超时 | 指数退避 3 次（1/4/16s） | 该批标记 `pending_embed`，任务 `PARTIAL`，可单独重跑 |
| Milvus 写入限流 | 批大小自适应减半 + 客户端限速 500/s | 落本地 `failed_batches.jsonl` 落盘续传 |
| LLM 抽取超时/JSON 不合法 | 重试 2 次（温度 0 → 0 且加"仅输出 JSON"） | 降级为规则抽取（人名/对话引号），标记 `low_confidence` |
| Neo4j 事务冲突 | 批 1000 + 单批事务，冲突退避重试 | 跳过该批，记 `graph_errors` 表 |
| 任务进程崩溃 | Celery `acks_late=True` + `visibility_timeout` | 重启后按 checkpoint 从失败 stage 续跑 |

### 6.1 关系库（PostgreSQL）表结构

```sql
-- 书籍
CREATE TABLE novels (
  id            UUID PRIMARY KEY,
  title         VARCHAR(255) NOT NULL,
  author        VARCHAR(128),
  source_type   VARCHAR(16)  NOT NULL DEFAULT 'upload',  -- upload|import
  file_key      VARCHAR(512) NOT NULL,                   -- 存储层 key，不存绝对路径

  chunk_id     VARCHAR(64) PRIMARY KEY,      -- {novel_id}:{chapter_no}:{seq}

  parent_id    VARCHAR(64),                  -- child 指向 parent
  level        SMALLINT NOT NULL,            -- 1=child 2=parent 3=chapter_summary
  seq          INT  NOT NULL,
  content      TEXT NOT NULL,
  token_count  INT,
  speakers     TEXT[],                       -- 对话归属人物
  entities     TEXT[],                       -- 预标注实体（供图谱交叉校验）
  embed_status SMALLINT DEFAULT 0,           -- 0未做 1成功 2失败
  created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON chunks (novel_id, chapter_no, level);

-- 切片完成度档案（一行一任务，实时 upsert；前端 /chunk-review 页主数据源）
CREATE TABLE chunk_reports (
  job_id        UUID PRIMARY KEY REFERENCES jobs(id) ON DELETE CASCADE,
  novel_id      UUID NOT NULL,
  stage         VARCHAR(32)  NOT NULL,
  progress      NUMERIC(5,2) DEFAULT 0,      -- 已切字符 / 总字符
  chars_done    BIGINT DEFAULT 0, chars_total BIGINT DEFAULT 0,
  chapters_done INT DEFAULT 0,    chapters_total INT DEFAULT 0,
  chunks_child  INT DEFAULT 0, chunks_parent INT DEFAULT 0, chunks_summary INT DEFAULT 0,
  token_avg     INT, token_p50 INT, token_p95 INT, token_max INT,
  token_hist    JSONB DEFAULT '[]',          -- [[0,120],[120,240],...] 直方图桶

  updated_at    TIMESTAMPTZ DEFAULT now()
);

-- 任务与阶段（可观测 + 断点续跑）
CREATE TABLE jobs (
  id          UUID PRIMARY KEY,
  novel_id    UUID REFERENCES novels(id) ON DELETE CASCADE,
  type        VARCHAR(32) NOT NULL,          -- ingest|graph|reembed|rebuild
  status      VARCHAR(16) NOT NULL,          -- PENDING|RUNNING|PARTIAL|COMPLETED|FAILED|CANCELED
  stage       VARCHAR(32),                   -- 当前阶段，见 §8.1
  progress    SMALLINT DEFAULT 0,            -- 0-100
  stats       JSONB DEFAULT '{}',            -- {chunks:4000, entities:1500, edges:6000}
  error       TEXT,
  started_at  TIMESTAMPTZ, finished_at TIMESTAMPTZ,
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- 阶段检查点（幂等重跑的依据）
CREATE TABLE job_steps (
  job_id     UUID REFERENCES jobs(id) ON DELETE CASCADE,
  stage      VARCHAR(32) NOT NULL,
  status     VARCHAR(16) NOT NULL,
  cursor     JSONB DEFAULT '{}',             -- {batch_index: 12, last_chunk_id: "..."}
  attempts   SMALLINT DEFAULT 0,
  updated_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (job_id, stage)
);

-- 会话与消息
CREATE TABLE chat_sessions (
  id UUID PRIMARY KEY, novel_id UUID, title VARCHAR(255),
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE chat_messages (
  id BIGSERIAL PRIMARY KEY,
  session_id UUID REFERENCES chat_sessions(id) ON DELETE CASCADE,
  role VARCHAR(16) NOT NULL,                 -- user|assistant
  content TEXT NOT NULL,
  citations JSONB DEFAULT '[]',              -- [{chunk_id, chapter_no, score, snippet}]
  graph_paths JSONB DEFAULT '[]',
  latency_ms INT, token_in INT, token_out INT,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

### 6.2 Milvus 3.0 Collection Schema

**单 Collection 多书共存**，用 `partition key` 做隔离——比"一 book 一 collection"好：避免 collection 数量爆炸（Milvus 单集群 collection 数有上限）、避免每次上传都触发 load、且索引内存共享。

```python
from pymilvus import DataType, MilvusClient

DIM = settings.embedding_dim   # 必须与模型一致：bge-large-zh=1024（当前）/ bge-base=768 / bge-small-zh=512
# 换维度 = 新建 collection（v2），不能原地改——Milvus 的向量维度不可变更

schema = client.create_schema(auto_id=False, enable_dynamic_field=False)
schema.add_field("chunk_id",    DataType.VARCHAR, is_primary=True, max_length=64)
schema.add_field("novel_id",    DataType.VARCHAR, max_length=64, is_partition_key=True)
schema.add_field("chapter_no",  DataType.INT32)
schema.add_field("chapter_title", DataType.VARCHAR, max_length=512)
schema.add_field("level",       DataType.INT8)          # 1 child / 2 parent / 3 summary
schema.add_field("parent_id",   DataType.VARCHAR, max_length=64)
schema.add_field("seq",         DataType.INT32)
schema.add_field("content",     DataType.VARCHAR, max_length=8192)   # 3.0 亦可换 TEXT LOB
schema.add_field("token_count", DataType.INT32)
schema.add_field("speakers",    DataType.ARRAY, element_type=DataType.VARCHAR, max_capacity=16, max_length=64)
schema.add_field("entities",    DataType.ARRAY, element_type=DataType.VARCHAR, max_capacity=32, max_length=64)
schema.add_field("dense",       DataType.FLOAT_VECTOR, dim=DIM)
schema.add_field("sparse",      DataType.SPARSE_FLOAT_VECTOR)
schema.add_field("meta",        DataType.JSON)
schema.add_field("created_ts",  DataType.INT64)
```

**索引参数**

```python
idx = client.prepare_index_params()
idx.add_index(field_name="dense",  index_type="HNSW", metric_type="COSINE",
              params={"M": 32, "efConstruction": 256})
idx.add_index(field_name="sparse", index_type="SINDI", metric_type="IP")
#  若启用 Milvus 内置 BM25（服务端从 content 生成稀疏），改用 BM25 索引并省略客户端 sparse 写入
idx.add_index(field_name="chapter_no", index_type="INVERTED")
idx.add_index(field_name="level",      index_type="INVERTED")
client.create_index("novel_chunks_v1", idx)
client.load_collection("novel_chunks_v1")
```

> **注意**：3.0 的稀疏索引算法名（`SINDI` / `SPARSE_INVERTED_INDEX` / `BM25`）随 SDK 小版本可能不同。设计上在服务启动时做一次 **index 能力探测**（`client.list_indexes` / 试探创建 + 回滚），把可用算法写入 `capabilities` 缓存，配置项写"首选 SINDI，失败回退 SPARSE_INVERTED_INDEX"。这样不会因为 SDK 升级把服务搞挂。

**两种稀疏模式（由 `SPARSE_MODE` 决定，同一份 schema 兼容）**

| 模式 | 触发条件 | `sparse` 字段来源 | 索引 |
|---|---|---|---|
| `client` | 模型能出 sparse（bge-m3 / SPLADE） | 客户端写入学习型稀疏权重 | `SINDI`（IP） |
| `server-bm25` | 模型无 sparse（bge-large-zh，**当前默认**） | Milvus 从 `content` 列**服务端自动生成**（建 collection 时挂 BM25 Function） | `BM25` 或 `SPARSE_INVERTED_INDEX` |

两种模式对上层透明：`VectorStore.hybrid_search()` 内部判断走哪个通道，RAG 层拿到的都是 `RetrievedChunk`。这样"先本地跑通、以后换大模型"不需要重建业务代码，只需重灌向量。

**检索参数**

| 参数 | 取值 | 依据 |
|---|---|---|
| `metric_type` | COSINE | 向量已归一化 |
| `ef`（HNSW 搜索） | 64（默认）/ 128（高精度模式） | ef↑ 召回↑ 延迟↑，64 在 10w 级足够 |
| `limit`（每通道） | 50 | 给 rerank 留冗余 |
| `filter` | `novel_id == "{id}" and level == 1` | partition key 命中后自动裁剪 |
| `offset` | ≤ 1000 | Milvus 深翻页有代价，管理台分页用 `iterator` |

**写入模板（批量 MERGE，批 1000）**

```cypher
UNWIND $chars AS c
MERGE (n:Character {novel_id: $novel_id, name: c.name})
ON CREATE SET n.uid = c.uid, n.desc = c.desc, n.first_chapter = c.chapter_no,
              n.importance = c.importance, n.created_at = timestamp()
ON MATCH  SET n.aliases  = apoc.coll.toSet(coalesce(n.aliases,[]) + c.aliases),
              n.desc     = coalesce(n.desc, c.desc)
SET n.updated_at = timestamp();

UNWIND $rels AS r
MATCH (a:Character {novel_id: $novel_id, name: r.src})
MATCH (b:Character {novel_id: $novel_id, name: r.dst})
MERGE (a)-[e:RELATED_TO {relation: r.relation}]->(b)
ON CREATE SET e.strength = r.strength, e.evidence = r.evidence,
              e.since_chapter = r.since_chapter, e.confidence = r.confidence
ON MATCH  SET e.strength = (coalesce(e.strength,0) + r.strength) / 2,
              e.confidence = CASE WHEN r.confidence > e.confidence THEN r.confidence ELSE e.confidence END;
```

**为什么 `RELATED_TO` + `relation` 属性，而不是 `:MASTER_OF` / `:ENEMY_OF` 等独立类型**
关系类型会随小说题材爆炸（仙侠有"道侣/炉鼎/同门"，宫斗有"嫡庶/主仆"），拆成独立 label 会让可视化配色和查询模板都要改代码。用属性 + `relation` 枚举（可扩展字符串）意味着新增题材只改配置。代价是关系类型过滤要走属性索引（已建）。

### 6.4 三个存储的分工边界

| 数据 | 放哪 | 不放哪（原因） |
|---|---|---|
| 正文长文本 | PG `chunks.content` + 原文文件 | 不进 Milvus 主存储（3.0 虽支持 TEXT LOB，但正文是 SoT，应可重建） |
| 向量 | Milvus | 不进 PG（pgvector 只适合小规模） |
| 实体关系 | Neo4j | 不进 Milvus（图查询无法表达） |
| 检索日志 | PG（分区表按月） | 不进 Redis（要可分析） |
| 热点缓存 | Redis | 不进 PG（延迟） |

模块间只依赖协议，不依赖实现——这是二期拆微服务的提前量。

from typing import Protocol, AsyncIterator, Sequence, BinaryIO, Any
from dataclasses import dataclass

@dataclass(slots=True)
class Chunk:
    chunk_id: str; novel_id: str; chapter_no: int; level: int
    seq: int; content: str; parent_id: str | None = None
    speakers: list[str] | None = None; entities: list[str] | None = None
    token_count: int = 0

@dataclass(slots=True)
class RetrievedChunk:
    chunk: Chunk; score: float; channel: str      # dense|sparse|hybrid|rerank

class ObjectStorage(Protocol):
    """本地文件夹与对象存储的统一抽象（要求 6：预留迁移）"""
    async def put(self, key: str, data: BinaryIO, content_type: str = "text/plain") -> str: ...
    async def get(self, key: str) -> bytes: ...
    async def open_stream(self, key: str) -> AsyncIterator[bytes]: ...
    async def delete(self, key: str) -> None: ...
    async def exists(self, key: str) -> bool: ...
    async def presigned_url(self, key: str, expires: int = 3600) -> str | None:
        """本地实现返回 None，前端走 /files/{key} 代理下载"""
    def key_for(self, novel_id: str, filename: str) -> str: ...

class EmbeddingProvider(Protocol):
    async def embed_documents(self, texts: Sequence[str]) -> tuple[list[list[float]], list[dict[int, float]]]:
        """返回 (dense_vectors, sparse_vectors)"""
    async def embed_query(self, text: str) -> tuple[list[float], dict[int, float]]: ...
    @property
    def dim(self) -> int: ...
    @property
    def model_id(self) -> str: ...          # 写入 manifest，用于向量版本管理

class Reranker(Protocol):
    async def rerank(self, query: str, docs: Sequence[str], top_n: int = 8) -> list[tuple[int, float]]: ...

class VectorStore(Protocol):
    async def ensure_collection(self) -> None: ...
    async def upsert(self, chunks: Sequence[Chunk],
                     dense: Sequence[list[float]], sparse: Sequence[dict[int, float]]) -> int: ...
    async def hybrid_search(self, novel_id: str, dense: list[float], sparse: dict[int, float],
                            top_k: int = 50, level: int = 1,
                            chapter_range: tuple[int, int] | None = None) -> list[RetrievedChunk]: ...
    async def fetch_by_parent(self, novel_id: str, parent_ids: Sequence[str]) -> list[Chunk]: ...
    async def delete_by_novel(self, novel_id: str) -> int: ...
    async def stats(self, novel_id: str | None = None) -> dict[str, Any]: ...

class GraphStore(Protocol):
    async def upsert_entities(self, novel_id: str, entities: Sequence[dict]) -> int: ...
    async def upsert_relations(self, novel_id: str, relations: Sequence[dict]) -> int: ...
    async def subgraph(self, novel_id: str, center: str | None = None, depth: int = 2,
                       labels: Sequence[str] | None = None, rel_types: Sequence[str] | None = None,
                       limit: int = 200) -> dict[str, list]: ...
    async def resolve_entities(self, novel_id: str, names: Sequence[str]) -> list[dict]: ...
    async def neighbors_text(self, novel_id: str, names: Sequence[str], hops: int = 2,
                             limit: int = 40) -> list[str]: ...   # 供 RAG 使用的事实文本
    async def delete_by_novel(self, novel_id: str) -> int: ...
    async def stats(self, novel_id: str) -> dict[str, int]: ...

class LLMClient(Protocol):
    async def complete_json(self, system: str, user: str, schema: dict,
                            model: str | None = None, max_retries: int = 2) -> dict: ...
    async def stream(self, messages: list[dict], model: str | None = None,
                     temperature: float = 0.6) -> AsyncIterator[str]: ...

class DocumentParser(Protocol):
    def supports(self, filename: str) -> bool: ...
    def parse(self, raw: bytes) -> tuple[str, list[dict]]: ...   # (全文, 章节列表)

class Chunker(Protocol):
    def split(self, novel_id: str, text: str, chapters: list[dict]) -> list[Chunk]: ...

class EntityExtractor(Protocol):
    async def extract(self, chapter_no: int, text: str) -> dict:
        """返回 {entities:[...], relations:[...], events:[...]}"""

## 8. 关键实现细节

### 8.1 任务状态机

```
PENDING ──► PARSING ──► CHUNKING ──┬──► EMBEDDING ──► VECTOR_INDEXED ──┐
                                   │                                  ├─► COMPLETED
                                   └──► GRAPH_EXTRACTING ──► GRAPH_WRITING ──┘
                         任一阶段失败 ──► FAILED（可 retry 从断点续）
                         部分批次失败 ──► PARTIAL（可单独重跑失败批）
```

`VECTOR_INDEXED` 与 `COMPLETED` 分开的意义：**向量先就绪就能开放问答**，图谱晚到只是少了关系增强，前端可显示"图谱构建中（62%）"，用户体验不阻塞。

### 8.2 分章与清洗（中文小说的坑）

小说文本没有标准结构，按以下顺序兜底：

1. **目录法**：若末尾 5% 文本包含 `第一章…第N章` 且行首重复，识别为目录页，剔除
2. **标题正则**：`^\s*(第[零一二三四五六七八九十百千万0-9]+[章节回卷][^\n]{0,40})\s*$`，另兼容 `Chapter \d+`、`序章`、`楔子`、`尾声`
3. **长度约束**：单章 > 5 万字视为漏切，二次按空行 + 段落密度切；单章 < 200 字合并到下一章
4. **编码**：`charset-normalizer` 探测；GBK/GB18030 常见，探测失败按 GB18030 强解
5. **清洗**：去 BOM、去 `&nbsp;`、合并 3 个以上连续空行、去掉"（本章完）""求月票"等噪声行、全角半角统一
6. **对话识别**：`“…”` / `"…"` / `「…」` 三种引号，配合前后 `说|道|问|答|喊|笑道` → 说话人候选

### 8.3 分层切块（质量的核心）

```
Chapter(整章)
 ├─ parent  P1 (1400 tokens, 边界对齐场景/段落)
 │   ├─ child C1 (400 tokens, overlap 60)
 │   ├─ child C2
 │   └─ child C3
 ├─ parent  P2 …
 └─ summary S (150 字, 由 glm-5 生成, 也写向量库 level=3)
```

- **child 用于检索**（小而准），**parent 用于生成**（大而全）——命中 child 后回溯 `parent_id` 取原文，这是 small-to-big 的精髓：检索精度和上下文完整度不再互相牺牲
- 切分优先级：章节边界 > 场景分隔（`***`、空行×2、时间/地点转换句）> 段落 > 句子（`。！？…`）> 硬切
- 用**中文 tokenizer 估算**（`tiktoken` 对中文偏差大，用 `transformers` 的 BGE tokenizer 精确计数，或按 1 汉字≈0.75 token 估算后校准）
- 每个 chunk 带 `chapter_no` + `seq`，保证**检索结果可回溯到原文位置**

### 8.3.2 切片完成度查看（v1.1 新增需求）

**为什么单独做一层**：切块是整条链路里"最容易错、又最没人能核实"的一步。用户只看到"处理中 60%"，但 60% 是按什么算的？块切歪了没有？某一章是不是被整体吞掉了？不把过程摊开，出问题只能靠猜。

**完成度的定义（避免假进度）**

进度不能用"块数"算——切块是流式的，总块数事前未知，用块数算会出现"90% 停住不动"或"越跑越退"。定义如下：

```
progress = 已切分字符数 / 全文有效字符数 × 100
```

块数、token 分布、告警数都是**副指标**，用于判断质量，不参与进度计算。三个阶段各自有独立进度条，因为它们的耗时差异极大（切块秒级、向量化分钟级）：

| 阶段 | 计量单位 | 典型耗时（100 万字） |
|---|---|---|
| 解析分章 `PARSING` | 章节数 | 2-5 s |
| 切块 `CHUNKING` | 字符数 | 5-15 s |
| 向量化 `EMBEDDING` | 已编码块数 | CPU 3-5 min / GPU 30 s |

**完成度档案（`chunk_reports` 表，一次任务一行，实时更新）**

```jsonc
{
  "novel_id": "8f2c…",
  "job_id": "b31a…",
  "stage": "CHUNKING",
  "progress": 62.4,
  "chars_done": 623180, "chars_total": 998442,
  "chapters_done": 128, "chapters_total": 201,
  "chunks": { "child": 2480, "parent": 812, "summary": 128 },
  "tokens": { "avg": 386, "p50": 372, "p95": 452, "max": 1786 },
  "warnings": [
    { "level": "warn",  "code": "CHUNK_TOO_LONG", "chapter_no": 57,
      "chunk_id": "8f2c:57:2", "detail": "1786 tokens，超过 parent 上限 1.3 倍" },
    { "level": "error", "code": "CHAPTER_EMPTY",  "chapter_no": 88,
      "detail": "正文仅 32 字，疑似把‘本章完’误判为章节标题" }
  ],
  "eta_sec": 42,
  "updated_at": "2026-10-27T11:40:22+08:00"
}
```

**异常检测规则（每条都可关、阈值可配）**

| code | 触发条件 | 为什么重要 |
|---|---|---|
| `CHAPTER_EMPTY` | 章节正文 < 200 字 | 目录页/广告行被误判为章节 |
| `CHAPTER_TOO_LONG` | 单章 > 5 万字 | 漏切，后续时序检索全错 |
| `CHUNK_TOO_LONG` | 块 > 1.3 × 目标 token | 硬切没生效，会被 embedding 截断 |
| `CHUNK_TOO_SHORT` | 块 < 60 token | 噪声块，污染检索结果 |
| `PARENT_MISSING` | child 的 `parent_id` 找不到 | 切块逻辑 bug，生成时回溯失败 |
| `OVERLAP_ANOMALY` | 相邻块重叠 < 20 或 > 200 token | 上下文断裂或大量重复 |
| `DUP_CHUNK` | 两章内容相似度 > 0.95 | 原文件本身重复（盗版合并常见） |
| `ENCODING_SUSPECT` | 乱码字符占比 > 1% | 编码猜错，向量全废 |

**实时推送（复用任务 SSE，不新开通道）**

```
event: chunk_progress
data: {"stage":"CHUNKING","progress":62.4,"chapters_done":128,"chapters_total":201,
       "chunks":{"child":2480,"parent":812},"warnings":2,"eta_sec":42}
```

节流：**500 ms 合并一次**（`CHUNK_PROGRESS_PUSH_MS`），否则每切一章推一帧会把 SSE 打满，前端反而卡。

**前端呈现（`/novels/{id}/chunk-review` 页面，P0 就要有）**

```
┌─ 切片完成度 ─────────────────────────────── 62.4% ─┐
│ 解析 ████████████████████ 201/201 章               │
│ 切块 ████████████░░░░░░░░ 128/201 章 · 3,292 块     │
│ 向量 ░░░░░░░░░░░░░░░░░░░░ 等待中                    │
├─ 质量指标 ─────────────────────────────────────────┤
│ 平均 386 tok │ P95 452 │ 最长 1786 │ 过短块 12      │
│ token 分布直方图（横轴 0-2000，纵轴块数）           │

└────────────────────────────────────────────────────┘
```

关键设计：**每个告警都能一键跳到对应章节原文**（用 `chapter_no` 定位），不然告警等于噪音；**抽样预览固定抽 10 条**，让人 30 秒内就能判断"切得对不对"，而不是翻 4000 条。

**跑完之后还能复核**（不只是过程中的一次性展示）：`GET /novels/{id}/chunks` 支持按章节/层级/关键字筛选，`/chunk-review` 页保留完整统计与告警清单，作为"这部书能不能用"的准入判断。

### 8.4 图谱抽取 Prompt 设计（质量的关键）

三层抽取，逐层收敛：

| 层 | 手段 | 作用 | 输出 |
|---|---|---|---|
| L1 规则 | jieba 人名识别 + 对话引号 + 称谓词表（师父/师兄/掌门/大人） | 高精度候选，压低 LLM 幻觉 | 人名候选集 |
| L2 LLM | `z-ai/glm-5`（温度 0），一章一次调用，JSON schema 强约束 | 抽关系、事件、属性 | 结构化 JSON |
| L3 对齐 | 别名合并（编辑距离 + 字符重叠 + 向量相似）→ 冲突交 LLM 仲裁 | 解决"林三/三哥/林道友"是同一人 | 规范化实体 |

**Prompt 骨架**（固定前缀命中缓存）：

```
[SYSTEM: 60 行 schema 定义 + 12 条抽取规则 + 3 个 few-shot 示例]   ← 字节级不变，走缓存
[USER: 第 {no} 章《{title}》正文\n{text}\n已知人物：{known_chars}]
```

**JSON 输出约束**（优先用 `response_format={"type":"json_object"}`；启动探测不支持时，退化为"提示词强约束 + 括号配平修复"）：

```jsonc
{
  "entities": [
    {"name":"林三","type":"Character","aliases":["三哥"],"gender":"男",
     "desc":"主角，青云宗外门弟子","first_chapter":12}
  ],
  "relations": [
    {"src":"林三","dst":"玄阳真人","relation":"师徒","strength":0.9,
     "evidence":"林三跪地叩首：“弟子林三，拜见师父。”","confidence":0.92}
  ],
  "events": [
    {"name":"拜师","summary":"林三在青云殿拜玄阳真人为师","participants":["林三","玄阳真人"],
     "location":"青云殿","chapter_no":12,"importance":0.8}
  ]
}
```

**三道质量闸门**：
1. `confidence < 0.6` 的关系不入库，落 `graph_candidates` 表进人工审核队列（管理台"待确认"标签页）
2. `evidence` 必须能在原文中 `str.find()` 命中（归一化后），否则丢弃——这条能干掉约 90% 的编造关系
3. `relation` 不在枚举内时映射到 `OTHER` 并记录原始值，便于扩展词表

### 8.5 混合检索与融合

```python
# 1) 并行召回
dense_hits  = await vs.search_dense(novel_id, q_dense,  limit=50, ef=64)
sparse_hits = await vs.search_sparse(novel_id, q_sparse, limit=50)
# 或直接用 Milvus 3.0 的 hybrid_search(AnnSearchRequest x2, RRFRanker(k=60))

# 2) RRF 融合（无需归一化，对两路分值尺度不敏感）
score(d) = Σ_channel 1 / (60 + rank_channel(d))

# 3) cross-encoder 精排（top 50 → top 8）
pairs = [(query, c.content) for c in fused[:50]]
ranked = await reranker.rerank(query, [p[1] for p in pairs], top_n=8)

# 4) 回溯父块（同 parent 去重，最多 4 个父块，控制 token）
parents = await vs.fetch_by_parent(novel_id, {c.chunk.parent_id for c in ranked})

# 5) 图谱事实增强（可选，use_graph=true 时）
facts = await gs.neighbors_text(novel_id, entities=query_entities, hops=2, limit=40)
```

**为什么 RRF 而不是加权分数**：稠密分是 cosine（0-1），稀疏分是无界内积，加权需要归一化，而归一化参数在换模型后全部失效。RRF 只依赖排名，换 embedding 模型不用调参。

**降级链**：`hybrid → dense only → sparse only → 空结果走"全书摘要"兜底`。每一级在响应里带 `mode` 字段，前端可提示。

#### 8.5.1 落地补充（v1.4 实测）

设计和实现之间有三处必须校正，记在这里免得后人重踩：

**① 中文词法通道不能用 FTS5 的 trigram**
trigram 分词只认 **≥3 字** 的连续片段，而中文小说里最高价值的检索单位恰恰是两字词：
人名（陆沉/苏晚）、物名（铜灯/暗渠）、称谓（师父/掌门）。实测 `MATCH '"铜灯"'` 直接空结果。
最终方案：把正文切成 **bigram 序列**（"陆沉把刀" → `陆沉 沉把 把刀`）交给 unicode61 建索引，
查询同样转 bigram 后用 OR 连接。两字词精确命中，长查询走部分匹配 + BM25 排序，
不引 jieba（少一个依赖，也避免"索引切词"和"查询切词"两处词典漂移）。
代价：索引体积约为正文 2 倍（2 万块 ≈ 30MB），可接受。

**② BM25 的 IDF 会归零，必须当作"无信号"处理**
一个词在超过半数文档里出现时 IDF ≤ 0，SQLite 的 `bm25()` 直接返回 0，
于是所有命中**并列**——排序退化成 rowid 序，喂给 RRF 就是纯噪声。
处理：过滤掉 ≤1e-6 的命中，若一路全为 0 则判定"词法无区分度"直接放弃该通道
（`mode` 记成 dense_only）。语料越小越容易触发，这一点在 144 块的小样本上尤其明显。

**③ 精排必须可缺席**
cross-encoder 首启要下 279MB。做法是：模型没就绪时 `rerank.ready=False`，
检索自动退回"RRF 排序"并在 `detail.rerank_error` 里写明原因，问答不中断。
实测 `bge-reranker-base` int8：50 条候选批量打分 ~0.3s（8 线程，与入库任务抢核时会翻倍）。

**落地的三段式**（对应代码 `services/retrieval/hybrid.py`）：

```
两路召回(各 50) → RRF(k=60) → 取头 50 → cross-encoder 打分 → 父块去重 → 取 8 段进 prompt
```

**评测工具**：`make eval NOVEL=nv_xxx BUILD=30`，脚本 `backend/scripts/eval_retrieval.py`。
造题方式是"从真实切片里让 LLM 出题，答案是这一段"（自动标注 gold parent），
指标按**父块**算 Recall@k——按 chunk_id 严格比对会把"同段相邻子块"误判成未命中，指标虚低。

长夜将明（144 块 / 25 题）首轮实测：

| 链路 | Recall@10 | p50 | p95 |
|---|---|---|---|
| dense（P0 基线） | 0.920 | — | — |
| rrf（双路 + 融合，无精排） | 0.960 | 485ms | 586ms |
| hybrid（双路 + RRF + 精排） | 0.960 | 442ms | 524ms |

结论要谨慎读：这本样本书是**机器生成的句式重复文本**，稠密通道本来就接近天花板，
所以提升只有 +4pt、精排也没体现增量。真正能验证 P1-2 指标（+8pt）的是《赘婿》这类
21,552 块的真实长篇，需等其 1024 维向量化跑完后复测。延迟数据同样受当时并发的
向量化任务影响（8 核被占满），空载需重测。

### 8.7 流式与背压

- FastAPI `StreamingResponse(media_type="text/event-stream")`，每帧 `data: {...}\n\n`
- 上游网关的 `stream=True`，逐 chunk 转发；**客户端断开时立即 `aclose()` 上游连接**，避免继续计费（这点不做会白烧钱）
- Nginx 侧必须关缓冲：`proxy_buffering off; proxy_read_timeout 300s;`
- LLM 并发用 `asyncio.Semaphore(LLM_MAX_CONCURRENCY)` 控制，超限排队而非报错，队列长度 > 50 时直接返回 429

## 9. 性能优化点

### 9.1 写入侧

| 优化点 | 手段 | 预期收益 |
|---|---|---|
| Embedding 批量 | 批 32（GPU）/ 8（CPU），`fp16`，长度分桶（同长度一起跑，减少 padding 浪费） | 吞吐 ↑ 2-3× |
| 双向量单次前向 | BGE-M3 一次输出 dense+sparse，不做两次调用 | 省 50% 推理时间 |
| Milvus 批量写 | 批 500，`upsert` 而非 `insert`+`delete`；写满 5 万行再 `flush`（不要每条 flush） | 写入 ↑ 10× |
| 章节级并行 | worker 内 `asyncio.gather` 处理 4 章；Celery 并发 4 进程 | 100 万字 30min 内 |
| LLM 章节抽取 | 4 并发 + JSON 模式 + 短章合并 + 失败不重试同一 prompt | 抽取阶段 40min → 约 15min（无缓存前提） |
| Neo4j 批量 MERGE | 单事务 1000 条 + `UNWIND`，禁用自动索引重建 | 6k 边 < 5s |
| 跳过重复计算 | `chunk_id` 存在则跳过 embedding（内容 hash 相同） | 增量重跑只处理变更块 |

### 9.2 检索侧

| 优化点 | 手段 | 预期收益 |
|---|---|---|
| 分区裁剪 | `partition_key = novel_id`，检索必带该 filter | 候选集从全库降到单书，延迟 ↓ 一个数量级 |
| 索引参数 | HNSW `M=32/efC=256`，查询 `ef=64` | 召回 0.95+ 时 P95 < 100ms |
| 只索引 child | parent/summary 不参与 ANN（`level==1` filter） | 索引规模 ↓ 3×，召回反而更准 |
| Query 改写缓存 | 相同问题（含历史 hash）结果缓存 1h | 重复提问 0 成本 |
| Rerank 限流 | 只对 top 50 重排，CPU 8 线程批 16 | 80ms 内完成 |
| 并行召回 | dense/sparse 用 `asyncio.gather` 并发 | 延迟取 max 而非 sum |
| 结果去重 | 同一 parent 下多个 child 只保留最高分 | 上下文不重复，token ↓ 30% |

### 9.3 生成侧（成本）

| 优化点 | 手段 | 收益 |
|---|---|---|
| 上下文预算 | 检索 ≤8K、图谱 ≤40 条、历史 ≤6 轮；固定前缀保持字节稳定 | 输入 token 可控，成本可预测（不依赖上游缓存） |
| 上下文预算 | child 8 条 → parent 4 个（每个 ≤1400 token），总计 ≤ 8K | 单次问答成本可控 |
| 快慢模型分工 | 改写/摘要用 flash，仅抽取用 pro | 综合成本 ↓ 60% |
| 历史压缩 | 超过 6 轮的对话压成 200 字摘要 | 长会话不爆 token |
| 语义缓存 | 问题向量相似度 > 0.95 且同书 → 复用答案（可配置关闭） | 高频问题 0 成本 |

### 9.4 一个必须做的实验：内置 BM25 vs 客户端稀疏

Milvus 3.0 支持服务端从文本列生成 BM25，理论上可以省掉客户端的 sparse 计算与存储。但 BGE-M3 的 lexical weights 是**学习型稀疏**，在中文小说的人名/招式名匹配上通常优于纯 BM25（同义词、别称覆盖更好）。

**做法**：同一批数据双写（`sparse` 字段 + 服务端 BM25 索引），用 §11.4 的评测集跑 A/B，比较 Recall@10 与 P95 延迟，跑完再决定砍掉哪一路。**不要凭直觉选**，这一步的收益差异可能到 10 个点召回。

### 9.5 容量与扩展估算

| 规模 | chunks | Milvus 内存（HNSW, 1024d, fp32） | Neo4j 堆 |
|---|---|---|---|
| 1 部 100 万字 | 4,000 | ≈ 20 MB | 512 MB 足够 |
| 50 部 | 200,000 | ≈ 1 GB | 2 GB |
| 500 部 | 2,000,000 | ≈ 10 GB（建议换 IVF_PQ/DISKANN 或量化） | 8 GB |

> 超过 200 万 chunk 时，稠密索引从 HNSW 换 `DISKANN` 或 `IVF_SQ8`；此时也应考虑把"每书一 partition"改为"每 50 书一 partition"，避免 partition 数量过多。

## 10. 可扩展预留设计

### 10.1 存储层：本地 → 对象存储（要求 6）

**接口先行的具体落地**：

```python
# adapters/storage/local.py
class LocalStorage:
    def __init__(self, root: Path): self.root = root
    def key_for(self, novel_id: str, filename: str) -> str:
        return f"raw/{novel_id}/{filename}"
    async def put(self, key, data, content_type="text/plain") -> str:
        path = self.root / key; path.parent.mkdir(parents=True, exist_ok=True)
        await anyio.to_thread.run_sync(lambda: path.write_bytes(data.read()))
        return key
    async def presigned_url(self, key, expires=3600): return None

# adapters/storage/s3.py
class S3Storage:
    def __init__(self, endpoint, bucket, ak, sk):
        self.client = boto3.client("s3", endpoint_url=endpoint,
                                   aws_access_key_id=ak, aws_secret_access_key=sk)
    async def put(self, key, data, content_type="text/plain") -> str:
        await anyio.to_thread.run_sync(
            lambda: self.client.upload_fileobj(data, self.bucket, key,
                                               ExtraArgs={"ContentType": content_type}))
        return key
    async def presigned_url(self, key, expires=3600) -> str:
        return self.client.generate_presigned_url("get_object",
            Params={"Bucket": self.bucket, "Key": key}, ExpiresIn=expires)
```

**三条必须遵守的纪律**（否则迁移时会返工）：

1. 数据库只存 **key**（`raw/{novel_id}/{filename}`），**绝不存绝对路径或 URL**
2. 前端下载统一走 `GET /api/v1/files/{key}`（后端 302 到预签名 URL），不直连存储
3. 存储实现里**不允许出现 `Path` 拼接业务逻辑**，路径规则只在 `key_for()` 里

**迁移路径**：改 `STORAGE_BACKEND=s3` → 写一个 `scripts/migrate_storage.py`（按 PG 里的 key 列表批量 `put`）→ 校验 sha256 一致 → 切流量。全程业务代码零改动。

**Milvus 3.0 的额外预留（加分项）**：3.0 的 External Collections 可以直接对对象存储上的 Parquet/Iceberg/Vortex 建索引、零拷贝检索。若未来把历史小说归档成 Parquet，可以在 Milvus 里注册外部集合做"冷数据可查"，不必把老书重新灌一遍向量库。这属于二期以后的能力，但 Schema 设计（纯标量 + 向量，无强依赖）已经为它留好了口子。

### 10.2 服务拆分预留

| 触发条件 | 拆分动作 | 成本 |
|---|---|---|
| 检索 P95 > 500ms 或需独立扩缩 | `retrieval-service` 独立部署，暴露 gRPC/HTTP | 低（接口已在 §7.3） |
| 图谱抽取排队 > 30min | 加 `worker-graph` 副本（Celery 天然水平扩） | 极低 |
| 多租户 | 加 `tenant_id` 字段 + Milvus partition 改 `tenant_id` + Neo4j 全查询加前缀 | 中（需数据迁移） |
| 多模态（封面/插图） | 新增 `image` collection，BGE-VL 编码，`modality` 字段分流 | 中 |
| 多语言 | `EmbeddingProvider` 换 multilingual 模型 + `lang` 字段过滤 | 低 |

### 10.3 模型可替换

`manifest` 里记录 `embedding_model` / `embedding_version`。换模型的正确姿势：

1. 新 collection `novel_chunks_v2`（新维度/新索引），旧 collection 保持在线
2. 后台任务按书重建，双写期间查询走旧库
3. 灰度：按 `novel_id % 10` 分流到新库，对比 Recall
4. 全量切换后删旧 collection

**禁止**在同一个 collection 里混不同模型的向量——维度相同也不行，分布不同会让 ANN 结果崩坏，且这种 bug 极难排查。

### 10.4 图谱能力扩展

- **算法层**：Neo4j GDS（Graph Data Science）做社区发现（人物派系自动聚类）、PageRank（人物重要性）、最短路径（"两人如何认识"）——这些是很好的问答增强，二期做
- **Schema 扩展**：`relation` 用字符串而非枚举类型，新增关系类型只改配置 `graph_relation_vocab.yaml`
- **增量抽取**：新增章节时只抽新章，`MERGE` 天然合并；实体属性用 `ON MATCH` 保留首次出现的描述

### 10.5 接口版本化

- URL 前缀 `/api/v1`，破坏性变更升 `/api/v2`，v1 保留 6 个月
- SSE 事件类型只增不改（前端用 `switch` 默认分支忽略未知事件），保证前后端可独立发布

### 11.4 评测集怎么做（别跳过）

- **规模**：100 条，覆盖 6 类问题：事实型（谁是谁）、时序型（第几章发生）、关系型（两人什么关系）、总结型（这一卷讲了什么）、比较型（A 和 B 谁更强）、不可答型（书中没有，应回答"未提及"）
- **标注**：每条标注标准答案 + 应命中的 `chunk_id` 列表
- **指标**：Recall@10（检索）、答案准确率（人工 1-5 分）、引用正确率（引用段落真的支撑结论）、拒答准确率（不可答型）
- **不可答型必须占 10%**——这是检验幻觉的唯一有效手段，很多项目栽在这

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| `MILVUS_TOKEN` 无对应 endpoint | 完全跑不起来 | 高 | 上线前补 `MILVUS_URI`；启动自检 fail-fast 并打印明确提示 |
| Milvus 3.0 SDK 与 3.0 服务端版本错配 | 索引/写入 API 报错 | 中 | 锁定 `pymilvus` 版本到实测可用版本；启动做能力探测（§6.2） |
| 云端 Milvus 网络延迟/限流 | 写入慢、检索抖动 | 中 | 批写 + 客户端限速 + 重试；检索超时 3s 后降级到本地缓存 |
| LLM 抽取幻觉（编造关系） | 图谱污染，问答胡说 | 高 | 三道闸门（置信度/证据回查/枚举校验）+ 人工审核队列 |
| 同一人物多称谓导致图谱碎裂 | 关系查询不准 | 高 | 别名对齐三件套；管理台提供"合并实体" |
| 章节切分错误（无章节号的长文） | 时序检索失效 | 中 | 多级兜底正则 + 长度约束二次切；管理台支持手动修章节边界 |
| 360 网关限流 / 超时 / 配额不透明 | 抽取中断、问答失败 | **高** | 信号量 4 + 429 指数退避 + 抽取失败转规则抽取；`/health/deps` 暴露能力探测；保留 DeepSeek 备份通道（改 `LLM_BASE_URL` 即切） |
| 中文 token 估算偏差 | 切块超长被截断 | 中 | 用真实 tokenizer 计数，不拍脑袋 |
| 前端 G6 大图卡死 | 可视化不可用 | 中 | 后端强制 `limit`，超过 500 节点返回 `truncated=true` 并提示缩小范围 |
| 成本超预算 | 项目停滞 | 中 | 上下文预算 + 短章合并 + 语义缓存；管理台按场景出 token 与费用报表 |

### 14.3 一句话总结这套架构的判断依据

- **写入异步、查询同步**：长任务绝不阻塞请求，但用户能实时看到进度（SSE）
- **三份标识贯穿全链路**（`novel_id` / `chunk_id` / `chapter_no`）：这是向量库、图谱、关系库能互相对上的唯一原因
- **父子块 + 混合检索 + rerank**：这三件事决定了问答质量的下限，不该省
- **接口先行**：存储、模型、检索器全部走 Protocol，才敢说"可扩展"
- **指标先行**：没有评测集，"优化"就是玄学
- **依赖可复现**：`uv.lock` + `pnpm-lock.yaml` 进 Git，环境差异只允许出现在 `.env`

| **检索实现** | `hnsw.ef_search` + `hnsw.iterative_scan=relaxed_order` 解决"带 novel_id 过滤时候选不足" | §8.5 |
| **运维** | 新增 `tools/install_pgvector.cmd`、`scripts/migrate_to_pg.py`、`make db-migrate / db-shell` | §11、§14 |
| **依赖** | 移除 `pymilvus`（降为迁移期 dev 依赖）与 `aiosqlite`；新增 `asyncpg`、`pgvector` | §12 |

> **关于下文中仍出现的 Milvus 描述**：§6.2 的 collection schema、§5.4 的分层存储、
> §8.5 的 Milvus hybrid search 等段落是 v1.0–v1.4 的设计原文，保留用于追溯决策过程。
> 当前实现以本条的映射为准：
>
> | 原（Milvus 时代） | 现（pgvector） |
> |---|---|
> | Collection `novel_chunks_d1024` | 表 `chunk_vectors` |
> | partition key `novel_id` | 普通列 `novel_id` + btree 索引 |
> | `dense` FLOAT_VECTOR(1024) | `embedding vector(1024)` |
> | `AUTOINDEX` / COSINE | `hnsw (vector_cosine_ops)` |
> | 一致性 `Strong` | 单库事务，天然强一致 |
> | 删除靠 `delete(filter=novel_id==...)` | 外键 `ON DELETE CASCADE` |
> | 服务端 BM25 稀疏向量 | PG `tsvector` + bigram（客户端切分） |
