Technical Architecture · v1.12

长篇小说 RAG 检索 + 知识图谱 双引擎

原始文本 → 向量与倒排 + 知识图谱 全部装在同一个 PostgreSQL → 可视化中台 + 大模型增强问答。 写入异步可重跑，查询同步可降级，正文、向量、词法索引、图谱同库同事务。

PostgreSQL 18.6 + pgvector 0.8.7 · 单库承载正文/向量/倒排/图谱 大模型 360 网关 · glm-5（问答）+ deepseek-chat-v3（抽取） Embedding 本地 int8 · bge-large-zh · 1024 维 / 8 线程 后端 FastAPI + asyncio worker · uv 前端 React + Semi Design · Cytoscape.js + fcose · pnpm

① 存储收敛到一个 PostgreSQL

正文、元数据、向量、词法倒排、知识图谱同库：配置只有 DATABASE_URL。派生表 chunk_vectors / chunk_lexical / entities / relations 全部对 chunks(id) 或 novels(id) 加外键 ON DELETE CASCADE——"书删了向量还在、图还在、worker 还在算两小时"这类孤儿数据，在数据库层面已不可表达。Milvus 与 Neo4j 都是在这一步被砍掉的。

② pgvector 的两个坑必须提前处理

过滤召回不足：HNSW 先取候选再套 WHERE novel_id，单书占比小时会不足甚至返回 0 且不报错 → 必须 SET LOCAL hnsw.iterative_scan = relaxed_order。中文两字词：PG 默认分词器不切中文 → 正文切 bigram 再建 tsvector，启动时用 _probe_cjk() 自检，不通过就关词法通道并降级 dense_only。

③ 大模型按「要不要思考」分工

问答用 z-ai/glm-5（推理模型），结构化抽取用 LLM_MODEL_FAST=deepseek-chat-v3。原因很硬：glm-5 的正文走 reasoning_content、content 为空，thinking:disabled 实测不生效，用它抽取会 100% 拿回空 JSON。换模型只改环境变量，代码里只有一个 model 参数在变。

④ 切片过程必须看得见

按字符数算真实进度，附 token 分布、8 类异常检测、抽样预览。每条告警可跳转原文核查——切片是最容易错、也最难核实的一步。

01 总体架构

四层结构：接入 → 应用 → 能力 → 存储。能力层左右分置"写入管道"与"查询链路"，二者只通过三份共享标识耦合，互不阻塞。

02 双链路数据流

左：上传后自动触发的构建管道，异步、可断点续跑、幂等。右：单次问答的检索增强链路，同步、低延迟、可逐级降级。

WRITE

构建管道（100 万字 ≈ 30 min）

  1. 上传与去重sha256 命中则直接返回已有 novel_id；文件落 raw/{novel_id}/
  2. 解析编码探测（GB18030 兜底）→ 目录剔除 → 章节正则 + 长度兜底 → 清洗
  3. 分层切块parent 1400 tokens / child 400 tokens（overlap 60），对话归属识别
  4. 章节摘要glm-5 并发 8，产出 150 字样章摘要（可选，ENABLE_CHAPTER_SUMMARY）
  5. 向量化 + 倒排本地 bge-large-zh（int8 · 1024 维 · 8 线程）出稠密向量；同一批文本切 bigram 建 tsvector 倒排，两条路径互不依赖
  6. 图谱抽取规则候选（零依赖）→ 按块调 deepseek-chat-v3（温度 0）→ 泛称闸门 + 仅专名别名对齐 → 三道闸门（P1）
  7. 入库PG 批 16-64 条 INSERT … ON CONFLICT；图谱整书先清空再重建，三个唯一约束兜重边
  8. 索引就绪HNSW / GIN 首次自动建；状态置 READY，问答立即可用（图谱略滞后不阻塞）
READ

问答链路（P95 首字 < 2 s）

  1. 问题入参原始问题直接检索（指代消解/改写尚未做，留 P2；多轮追问靠历史消息来兜）
  2. 并行召回稠密 HNSW（iterative_scan，filter novel_id，limit 50）∥ 词法 tsquery（limit 50）
  3. 图谱事实问题点名实体（名字/别名子串命中）→ 一跳关系 ≤6 个实体 → 文本化注入；查不到就跳过，不阻塞
  4. RRF 融合Σ 1/(60+rank)，对分值尺度不敏感，换模型不用调参
  5. 精排bge-reranker-base int8，top50 → top24（约 80 ms）
  6. 回溯父块child 命中 → 按 parent 去重取 8 个，控制在 8K token 内
  7. Prompt 组装固定前缀（字节稳定）+ 图谱事实 + 资料 + 历史，总预算 ≤ 8K
  8. 流式生成SSE 先推 meta（引用+检索计数）→ reasoning（思考增量，首字前不黑屏）→ delta → done；断连立即释放上游连接

04 存储建模边界

PostgreSQL 一个库同时存正文、状态、向量、倒排、图谱。正文是唯一事实源，向量 / 倒排 / 图谱都是「可重建的派生索引」——四类数据同库，全部被外键和级联约束住，删书没有补偿逻辑要写。

chunk_vectors + chunk_lexical 向量与倒排

  • chunk_idPK · FK → chunks(id) CASCADE
  • novel_idbtree 索引 · 过滤键
  • embeddingvector(1024) · HNSW m=16
  • bigramsbigram 串 · 可诊断
  • tsvtsvector · GIN 倒排
  • 检索参数ef_search 100 · iterative_scan
  • 删除级联 · 不会留孤儿

entities / relations / entity_mentions 图谱三表

  • entitiesname · type(6 类) · aliases jsonb
  • importancemention_count 加权 · 决定节点大小
  • relationssrc_id → dst_id · 22 种中文关系
  • evidence原文片段 · 点边可回看
  • statusactive / pending（置信度 < 0.6）
  • entity_mentions实体 × 块 · 热度与时间线
  • N 跳子图递归 CTE · depth < hops 防环

PostgreSQL 正文与状态

  • novelsmeta jsonb · 三计数
  • chapters字符偏移 · 摘要
  • chunks正文 + 父子（level 1/2）
  • jobs状态机 · 进度计数
  • chunk_reports切片告警行
  • chat_sessions / messages会话 · 引用

05 知识图谱：抽取 → 闸门 → 可视化

P1-M5 / M9 已落地。三层抽取逐层收敛，三道闸门在抽取这一层就拦掉编造；图不进 Neo4j，直接是三张 PG 表，N 跳邻域用递归 CTE。
一句话取舍：宁可图小一点、每条边都能点开看原文，也不要一张满是「某人持有某物」的大图。

左栏 · 筛选
实体搜索（名字/别名/描述）· 类型分布条形图 · 关系类型 Top15 ·「显示待确认边」开关 · 重新构建（force）
中栏 · 画布
Cytoscape.js + fcose 力导向：节点大小 = importance、颜色 = 类型、边粗细 = strength；pending 边画虚线；只画有关系的实体，孤立实体数量在左下提示
右栏 · 详情
实体描述与别名 · 关系按证据强度排序、默认 20 条可展开（面板自身滚动，不再被卡片裁掉）· 每条关系带证据原文与方向箭头 · 出现章节时间线；高度按视口剩余空间算，小窗口下不再顶出可视区

06 任务中心与检索调试台

入库、重算向量、图谱构建三类任务共用一条串行队列（4 核机器并发跑只会互相抢线程）。 失败与已取消的任务可以原地重试，跑着的任务可以取消——但取消不等于删除，一个字节的数据都不清。

任务中心
三类任务统一列表 · 按书/状态/类型筛选 · 实时进度与阶段 · 产出统计（块/向量 或 实体/关系）· 耗时 · 取消 / 重试 · 一键跳到切片页或图谱页
两条取消通道刻意分开：cancel(novel_id) 表示书被删了（要清向量）， cancel_job(job_id) 只是"先别算了"（不删任何数据）。
检索调试台
一次查询直接看见链路：召回模式（hybrid / dense_only / sparse_only / empty）· 稠密 / 词法 / 融合 / 回表四段计数 · 每条结果的各通道名次 · rerank 与 RRF 分值 · 父块原文展开
调参时不用猜是哪一路断了——降级是常态，静默降级才是事故。

08 实施优先级与交付标准

六个阶段约 37 人日（1 后端 + 1 前端）。P0 先打通「能问」的闭环，P1 补质量与可视化，P2 做生产化。

P0 · MVP 闭环≈ 13 人日

上传一本书，能基于向量检索问到答案，全程不碰命令行。

  • 上传 / 去重 / 本地存储
  • 解析 + 分章 + 三层切块
  • 本地 bge-large 向量（1024 维）+ 词法倒排入库
  • 切片完成度复核页
  • 纯向量 RAG + SSE 流式
  • 最小管理台（4 页）
验收：100 万字 < 30 min；重复跑实体数不变；切片页可见进度/告警/抽样；20 条问题相关性 ≥ 3.5/5。
P1 · 图谱与质量≈ 15 人日

知识图谱上线（PG 三表，不装图库），检索从单通道升级为混合 + 精排，图谱页可用。

  • LLM 抽取（按块）+ 别名对齐 + PG 三表
  • 混合检索 + RRF + rerank
  • 图谱可视化（Cytoscape.js + fcose，2 跳子图）
  • 图谱事实注入问答（use_graph）
  • 向量降维散点（UMAP 预计算）
  • 完整管理台四模块
验收：Recall@10 ≥ 0.85 且比纯向量基线高 8pt；200 节点子图布局 + 渲染 < 3 s；抽取证据零丢弃（《长夜将明》87 实体 / 164 关系已达标）。
P2 · 生产化≈ 10 人日

从「能演示」到「能长期跑」：评测、审核、监控、切换对象存储。

  • 100 条评测集 + 回归脚本
  • 低置信实体人工审核队列
  • Grafana 看板 + 依赖健康降级
  • S3 适配器（MinIO 验证）
  • 压测 + 限流 + 成本看板
验收：make eval 一键出报表；20 QPS 压测零错误；切 S3 零代码改动。

09 主要风险与对策

风险影响对策
目标库没装 pgvector阻断启动查 pg_extension，缺失即抛带安装指引的 RuntimeError；Docker 用 pgvector/pgvector:pg18
LLM 抽取编造关系高三道闸门：confidence≥0.6 + evidence 原文回查 + 关系枚举校验；低置信进人工队列
人物多称谓导致图谱碎裂高并查集对齐：同名同类型 + 专名别名指向，连通分量上限 6（泛称别名曾把曹操/董卓/诸葛武侯焊成一个 blob，曹操直接从实体表消失）；刻意不做编辑距离/包含关系合并；待确认边进人工队列
HNSW 索引没建（懒建机制）高检索退化为全表扫描、随数据量线性变慢；/health 暴露 index 字段，迁移后查 pg_indexes 补建
过滤检索召回不足中HNSW 先取候选再过滤，单书占比小时不足且不报错；每次检索事务内 SET LOCAL hnsw.iterative_scan=relaxed_order
章节切分错误（无章节号长文）中多级正则兜底 + 长度约束二次切；管理台支持手动修正章节边界
360 网关限流 / 超时高信号量 4 + 429 指数退避；抽取失败转规则抽取并标记 low_confidence；保留 DeepSeek 备份通道（改 base_url 即切）
大图渲染卡死低后端强制节点/边上限（200 / 400），超限返回 truncated=true；前端默认 2 跳、按 importance 取骨架，不在首屏画全书
推理模型抽不出结构化结果高glm-5 正文走 reasoning_content、content 为空（27 次调用全空）；抽取固定用 LLM_MODEL_FAST，返回空时打告警指向该配置
