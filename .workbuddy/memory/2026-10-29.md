## 中优先级三项（v1.16）

### 重新生成
- 语义必须是**先删上一轮再全新走一遍**，不是"再问一遍"——后者让模型看到同一问题被答两遍，会过度自我修正。
- `drop_last_turn(session_id, expect=question)` 必须调在 `rag.prepare()` **之前**，否则要重答的那轮被当成"上文"塞进 prompt。
- `expect` 不匹配时**不删**、退化成普通提问（多标签页并发/切会话会错位）。实测：首轮 2 条 → 重新生成 2 条（答案变了）→ 不匹配 4 条。

### 会话检索与导出
- `?q=` 搜标题**和正文**：标题是首句截断，用户记得的是"我问过 XX"。命中返回 `hit` 片段，取最早命中且 `role.desc()` 让 user 排前（"我问过什么"更好认）。
- 导出走 Markdown 不走 JSON（用户要带走结论，不是备份数据）；文件名 RFC 5987 `filename*=UTF-8''`，`filename=` 直接塞中文会乱码。
- 前端 300ms 防抖；实测搜索 7→4 条、4 个片段、5 处高亮。

## 消息栏图标接真实现 + 正文排版（v1.17）

### Semi Chat 的"假按钮"
- `Chat` 组件**不传回调也照样把五个图标画出来**（复制/赞/踩/刷新/删除），点下去空转——比不显示更糟。
- 对应回调：`onMessageCopy`（Semi 内置，带 toast）/ `onMessageGoodFeedback` / `onMessageBadFeedback` / `onMessageReset` / `onMessageDelete`。
- `showReset = lastChat && role === ASSISTANT`，`showFeedback = role !== USER && status === complete`。status 不是 complete 时整行 `-hidden`（灰的，不可点）。
- Semi 的 `deleteMessage` / `likeMessage` / `resetMessage` 都会**先改内部 chats 再回调**，所以回调里不要自己再改 chats（会被覆盖或错位）。

### 临时 id（"假删除"的唯一成因）
- 前端发送用本地占位 id `a-<ts>-<rand>`；服务端 `cm_xxx` 落库时才生成。拿占位 id 调 `/chat/messages/{id}` **必然 404**，而 Semi 已把消息从列表摘掉 → 看起来删成功了。
- 修法：`save_answer()` 返回 `msg.id` → `_persist_and_housekeep` → `done.message_id` → 前端换 id + 把 5 个以 id 为 key 的 Map（cite/usage/think/ret/ mem）一起搬家（`moveKey`）。
- **坑**：`setChats(prev => prev.map(m => m.id === answerId ...))` 里直接读变量不行——updater 在 React 渲染阶段才执行，那时 `answerId` 已被赋成新值，一条都匹配不上，消息永远停在 loading。先把旧 id 存 `const prevId`。

### 字号不一致
- 根因不是两边样式不同：`p` 两侧都是 **14px/20px**。是 `ul/ol/li` **漏在 Typography 外面**，继承 body 的 **16px + line-height:normal**，AI 回答一用编号列表就整体大一号。
- 修法：只补 `.semi-chat .semi-markdownRender ul/ol/li { font-size:14px; line-height:20px }`。不要改 `.semi-markdownRender` 的 font-size（标题按 em 算会一起缩水）。

## 流式正文"看起来不流"（v1.18）

### 根因一：Semi 按 `status` 决定要不要渲染 content
- `ChatBoxContent`：`status === 'loading'` 时**只画转圈点，把 content 整个丢掉**；否则才渲染 `MarkdownRender raw={content}`。
- 我们一直挂 `loading` 到整段答完 → content 在 state 里逐帧涨、屏幕一字不动，`done` 一到整篇砸下来。
- 修法：首个 `delta` 就把 status 切 `'incomplete'`。**不能切 `complete`**——`ChatBoxAction` 的 `finished = status !== loading && status !== incomplete`，切 complete 会让复制/赞踩/删除在生成中途就亮（复制到半截）。`incomplete` 同时满足"渲染正文 + 隐藏图标行"。
- `error` 也算 finished（图标行会显示），只影响 bubble 模式边框色。

### 根因二：末尾换 id 会让正文闪一下
- Semi 用 `key={item.id}` 渲染每条消息，`done` 里换 id = 卸载重建，正好在答案铺满一屏时重建 → 先空一帧再出现。
- 修法：**开流前预建**。`memory.create_answer(session_id, qseq)` 插一条 content="" 的 assistant 消息并返回 id，随 `meta` 下发；前端在 meta 分支换 id（此时正文 0 字，无感）。`done` 仍带同一个 id 作兜底。
- 配套 `memory.fill_answer(mid, answer, cites)`：answer 为空就**删掉空壳**（否则回放出现空气泡、摘要按多一轮配对）。`save_answer()` 保留为 create+fill 的组合版，给 `save_turn()` 用。
- `_persist_and_housekeep(session_id, qseq, message_id, answer, cites)`：message_id 为空时退化成 save_answer 新建，不能因为一次插入失败丢掉回答。

### 实测（重要，别再猜）
- 一次长回答：`meta` 93.2s → 思考 94.9~105.4s → 正文 105.5~110.1s（85 帧 / 43ms 一帧）→ done。**思考末帧到正文首帧只隔 82ms，没有空白期**。
- DOM 端 63 次渐进变化、平均 173ms 一次 → MDX 逐帧全量编译**不是**瓶颈（Semi 的 MarkdownRender 每次 raw 变化都跑一次 `@mdx-js/mdx` 的 async evaluate，实测扛得住）。
- **真正的等待在 meta 之前**：检索 51~93 秒，其中精排（`bge-reranker-base`，50 条 × 512 token，CPU）占 64~76 秒。embed 0.7s / pgvector 0.45s / 词法 0.02s。这是独立待办。
