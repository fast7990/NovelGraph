## v1.2：向量维度 512 → 1024，CPU 4 → 8 线程

**改动**
- 模型：`BAAI/bge-small-zh-v1.5`(512) → **`BAAI/bge-large-zh-v1.5`(1024)**，权重用 `Xenova/bge-large-zh-v1.5` 的 **int8 动态量化 ONNX**（ModelScope 上 `onnx/model_quantized.onnx`，326MB，fp32 是 1.3GB）。
- 新配置项：`EMBEDDING_MS_REPO` / `EMBEDDING_ONNX_FILE`，换模型不再改代码（`OnnxEmbedder` 已泛化，去掉了 bge-small 硬编码）。
- `MILVUS_DIM=1024`、`EMBEDDING_THREADS=8`、集合换 **`novel_chunks_d1024`**（Milvus 维度不可原地改，旧的 `novel_chunks_v1` 仍是 512 维、17936 行）。

**实测（干净环境，8 线程）**
| 场景 | 结果 |
|---|---|
| 模型加载 | 2.8s，输出 `last_hidden_state`，CLS 池化后 norm=1.0 |
| 真实切片（311 字 / 374 token） | 16 条 2.33 块/s、32 条 1.71、**64 条 0.20**（断崖） |
| 小样本 38,485 字 / 144 块 | 54s，检索与问答均正常（答案带 [资料N] 引用） |

**新踩的坑（关键）**
1. **内存是硬约束，不是 CPU**。机器 15.7GB 物理内存但只剩 3.4GB 可用、页面文件已用 7.6GB。bge-large 激活内存随 batch×seq 线性涨，batch 从 16 提到 64 时直接掉进 swap，吞吐从 2.33 → 0.20 块/s。**`EMBEDDING_BATCH` 不要超过 32**。
2. **tokens/chars ≈ 1.18**（真实小说 311 字 → 374 token），比合成文本（0.95）高，估时按 1.2 算。
3. **ModelScope 单连接下载很慢**（327MB 单线程 12 分钟才 30MB）。支持 Range，**8 路并发分段 11 分钟拉完**。
4. `ModelScope` 上 `BAAI/bge-large-zh-v1.5` 只有 pytorch 权重，ONNX 必须用 `Xenova/` 镜像仓库。

**新增的健壮性（都是被真实故障逼出来的）**
- **断点续跑**：`rebuild_vectors(resume=True)` 用 `query_iterator` 拉已入库 id 跳过（offset 分页有 16384 上限）；`POST /chunks/rebuild?mode=vectors|full&force=`。实测中断后重启，跳过 512 条继续。
- **僵尸任务清理**：`runner.recover_stale()` 在启动时把残留 `RUNNING/PENDING` 翻成 FAILED 并写明中断点。起因：停服务时《赘婿》任务停在 84.5%，UI 显示永远在跑。
- **维度三道闸**：①`MILVUS_DIM ≠ EMBEDDING_DIM` → pydantic `model_validator` 启动失败；②模型实测维度 ≠ `EMBEDDING_DIM` → `FatalModelError` 不参与 auto 降级；③collection description 记 `embedding=<model>|dim=<n>`，拦"同维度换模型"混用。
- **embedder 同步预热**：原来丢在后台 task 里被 `except` 吞掉，配置错了服务照样起来，等第一次入库才炸。

**进行中**：《赘婿》582 万字 / 21552 块 → 1024 维重算，2.3 块/s，约 2.5 小时。

## 修僵尸任务根因 + 重启（15:35）

**现象**：worker 卡住，新上传的《长夜将明》一直 PENDING；进程 36 分钟烧了 11782s CPU（≈5.4 核满载），Milvus 行数在涨，但 DB 里只有 1 本待处理的书。

**根因**：`DELETE /novels/{id}` 只删 DB + 向量，**没有通知 worker**。worker 正按 chunk 列表给一本已删除的书（nv_9b2c0df8caec479f，582 万字）做 1024 维重算，`Progress.update` 因 `db.get(Job, id)` 返回 None 而静默 return，所以界面上一点进度都没有。队列还串行，后面的任务全堵死。

**修复**（3 处）
1. 新增 `app/workers/cancel.py`：内存 set + `IngestCancelled` 异常 + `cancel/clear/is_cancelled`。
2. `pipeline.py` 两个向量化循环（run_ingest / rebuild_vectors）每批开头检查 `is_cancelled(novel_id)`，命中抛 `IngestCancelled`。
3. `runner._loop` 捕获 `IngestCancelled`：日志 + 再删一次残留向量（取消前的批次可能已写入）+ `clear()`；`novels.delete` 在删库前先 `cancel(novel_id)`。
4. `recover_stale` 区分对待：**PENDING 且 started_at is None 且 progress==0** 的任务重新 `submit()` 入队，不再误判成 FAILED（否则用户刚传的书白挂）；只有 RUNNING/有进度的才标 FAILED。

**验证**：重启日志出现 `重新入队 1 个未开始的任务`，任务从 35% 跑到 COMPLETED（144 切片 / 144 向量），`POST /search` 检索正常。清掉孤儿向量 `nv_9b2c0df8caec479f` 2304 条，collection 从 2304 → 144。

**遗留**：取消是**进程内内存信号**，多 worker / Celery 化时要换成持久化广播；`DELETE` 时若 worker 刚好在 `embed_documents` 里，最坏要等一个 batch（128 块）才退出。

- 前端：Chat 引用面板加「混合检索/仅向量/仅词法」徽标 + 每条引用的「向量#n/词法#n/精排分」标签。

**踩坑**
1. **BM25 的 IDF 会归零**：词在 >50% 文档出现时 `bm25()` 返回 0 → 全部命中并列 → 排序退化成 rowid 序，喂给 RRF 是纯噪声。必须过滤 ≤1e-6 的命中；全 0 就判定"词法无区分度"放弃该通道（mode 退 dense_only）。144 块的小语料极易触发。
2. 精排模型未就绪时**必须能缺席**：`ready=False` → 退回 RRF 排序并在 `detail.rerank_error` 说明，问答不中断。
3. `/health` 新增依赖项必须带 `status` 字段，否则前端/脚本按 `d['status']` 取值直接 KeyError（之前 `reranker.health()` 漏了）。
4. 词法索引在**切片落库后**就建（不等向量化），大书向量化期间 `mode=sparse_only` 仍可检索。
5. 重启服务器会打断大书向量化，但 `POST /chunks/rebuild?mode=vectors` 能断点续跑——实测跳过 5120/21552。

**评测（长夜将明 144 块 / 25 题，机器生成文本）**：dense 0.920 → rrf 0.960 → hybrid 0.960；p50 442–485ms、p95 524–586ms（期间向量化任务占满 8 核）。样本文本句式重复，稠密本身接近天花板，+4pt 不代表真实长篇收益，需等《赘婿》跑完复测。

**运行态**：6 个依赖全 ok（database/milvus/onnx/llm/lexical/rerank），词法索引 21696 = child 块数，精排 ready。pytest 15 passed，ruff 干净。

**背景**：用户要求"SQLite 想换成 PostgreSQL + pgvector，先不用 Milvus 了"。

**环境事实（重要）**
- 本机已有 **PostgreSQL 18.6**，装在 `D:/Program Files\PostgreSQL\18`，服务名 `postgresql-x64-18`，5432 在听
- **没有 pgvector 扩展**，只有 pg_trgm；安装目录不可写（要管理员）

**代码改动**
| 文件 | 改动 |
|---|---|
| `app/db.py` | asyncpg + 连接池 8/16；启动时校验 `pg_extension` 有 vector，缺失抛带安装指引的 RuntimeError |
| `app/models.py` | JSON→`JSONB`；时间列统一 `DateTime(timezone=True)`（SQLite 时代是 naive，直接迁会炸）；新增 `ChunkVector`(`vector(1024)`, FK CASCADE)、`ChunkLexical`(`tsvector`, FK CASCADE) |

| `app/config.py` | 删 milvus_*，加 pgvector_*（hnsw_m/ef_construction/ef_search/iterative_scan）；`_must_be_postgres` 校验 |

| `tools/install_pgvector.cmd` | 新增，管理员复制扩展文件 |
| 前端 | 文案 Milvus → PostgreSQL + pgvector；`cfg.milvus_collection` → `cfg.vector_table` |

**设计要点**
1. **向量单独表 `chunk_vectors`**，不塞进 chunks：入库是"先写正文、再逐批补向量"，向量 4KB/条会触发 TOAST 与整行重写；分开后 chunks 只读。
2. **FK ON DELETE CASCADE 根治孤儿向量**——Milvus 时代"书删了 worker 还在算两小时"的根因就是两个库无约束。
3. **HNSW + `WHERE novel_id=?` 会召回不足**（先全局取 ef_search 候选再过滤），用 pgvector 0.8 的 `SET LOCAL hnsw.iterative_scan=relaxed_order` 解决。
4. **CJK 分词**：沿用 bigram（空格分隔）→ `to_tsvector('simple', bigrams)`。PG 默认分词器不切中文，但按空格分隔后能当独立 token。写了 `_probe_cjk()`：`to_tsvector('simple','陆沉 沉把 把刀')` 的 lexeme 数 <3 就关闭词法通道、检索降级 dense_only，绝不返回错排序。
5. 向量参数以 `CAST(:q AS vector)` 字符串传，不注册 asyncpg codec（SQLAlchemy 的 asyncpg 方言在 connect 阶段没法 await 注册类型）。

**数据现状**：SQLite 里只剩《长夜将明》1 本（192 chunks / 144 child）；《赘婿》(nv_1f976a26a5a14422) 记录已不在库中，但上传目录还在（Milvus 里可能仍有其孤儿向量，迁移脚本按 chunk_id 白名单过滤会自动跳过）。

**待办**：等用户装扩展 + 给 postgres 密码 → 建库、`CREATE EXTENSION vector`、迁移、重启验证。
